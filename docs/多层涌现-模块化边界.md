# 多层涌现 · 模块化边界

问题：「这一块可以模块化吗？因为涉及使用方向 —— 如果打算做通用，按哪个方向都会不满意。」
标准：读过正文才标「已核」。本机副本在 `sources/`。

---

## 〇、结论

**能模块化，而且这个模式有名字，三十年前就解过。**

但「按哪个方向都会不满意」这句话虽然对，**结论要反过来**：
不是「所以别做通用」，也不是「挑一个方向」，而是 —— **「通用」的对象搞错了**。

> 通用的**不是方向**，是**内核**和**接口**。方向必须由使用者声明。

---

## 一、这个模式有名字：GiST

Hellerstein / Naughton / Pfeffer, *Generalized Search Trees for Database Systems*, VLDB 1995

> This paper introduces the Generalized Search Tree (GiST), an index structure supporting an
> **extensible set of queries and data types**. … In a single data structure, the GiST provides
> **all the basic search tree logic required by a database system, thereby unifying disparate
> structures such as B+-trees and R-trees in a single piece of code**

> To illustrate the flexibility of the GiST, we provide **simple method implementations** that
> allow it to behave like a B+-tree, an R-tree, and an RD-tree

**GiST 的主张就是你这个问题的答案**：一棵树、一套平衡与并发逻辑留在内核里，
把「**什么算近、什么算包含**」全部暴露成用户实现的方法。

> The grouping of data into categories may be controlled by a **user-supplied node splitting
> algorithm**, and the characterization of the categories can be done with **user-supplied search
> keys**. Thus by **exposing the key methods and the tree's split method to the user, arbitrary
> search trees may be constructed**

---

## 二、内核 / 插件的分界

GiST 的接口是 **六个方法**（原文：「the following set of **six methods** required by the GiST」）：

| GiST 方法 | 语义 | 对应到你的设计 |
|---|---|---|
| `Consistent(E, q)` | 这个子树上有没有可能命中 | **命中(方向, 查询) → bool** |
| `Union(P)` | 把一组键合成一个更粗的键 | **合并(一组方向) → 更粗的方向** ← 就是「更清晰的方向」那个包含关系 |
| `Penalty(E₁, E₂)` | 把 E₂ 放进 E₁ 子树的代价 | **代价(方向, 待放入项) → 数** ← **目标函数藏在这里** |
| `PickSplit(P)` | 一个节点太满时怎么劈开 | **劈开(父方向, 一组项) → None \| 一组方向（≥2 个）** |
| `Compress` / `Decompress` | 键怎么存 | 方向的编码 |

### ★ 由此得到一条重要的设计结论

**你不需要「定一个全局目标函数」。** GiST 里没有全局目标 —— 权衡全部由 `Penalty` 和
`PickSplit` 这两个**局部方法**表达。

上一轮我说「先定一件事：层的目标函数用哪个量」。**这句话是错的** ——
一旦定了全局量，就回到「按哪个方向都会不满意」。
正确的做法是：**把权衡下放给插件，内核只定义权衡被调用的位置。**

---

## 三、★ 插件允许不准 —— 这才是模块化安全的原因

GiST 对 `Consistent` 的规定，是本轮最有价值的一句：

> Note that an **accurate test for satisfiability is not required** here: Consistent **may return
> true incorrectly without affecting the correctness of the tree algorithms**. The penalty for
> such errors is in **performance**, since they may result in exploration of irrelevant subtrees
> during search.

拆开看，这是一个**不对称的契约**：

| | 允许？ | 后果 |
|---|---|---|
| **假阳**（说可能命中，其实不命中） | ✅ 允许 | 多走一棵子树 —— **只损失性能** |
| **假阴**（说不可能命中，其实命中） | ❌ 禁止 | 漏掉结果 —— **破坏正确性** |

**这就是模块化安全的全部理由**：方向函数在结构上只是一个**过滤器**，
过滤器的错**只损失性能，不损失正确性** —— 所以插件可以是不准的、可以是笨的、
可以先用一个粗糙版本。

⇒ 上一轮那句「开始我们不用直接创建最完美的规则」，在这里得到了**结构性依据**：
不是「先凑合用」，是**内核的契约允许它不准**。

⇒ 而且这是一个**可测的契约**：拿 ground truth 测插件有没有**假阴**即可。
假阴是可以自动检出的；假阳只需要报出来当度量。

## 四、两条路线（同一个问题的两种答案）

Stonebraker & Çetintemel, *"One Size Fits All": An Idea Whose Time Has Come and Gone*,
ICDE 2005

> we argue that this concept is **no longer applicable** to the database market, and that the
> commercial world will **fracture into a collection of independent database engines**, some of
> which may be **unified by a common front-end parser**

**注意：这两篇是同一个问题的两种对立答案，而你正站在这个叉上。**

| 路线 | 主张 | 对应到你的设计 |
|---|---|---|
| **分裂**（Stonebraker） | 一个方向一个引擎，共用一个前端 | 每个使用方向一套层结构 |
| **可扩展内核**（GiST） | 一个内核，把「什么算近」暴露成方法 | 一个层机制，方向函数是插件 |

Stonebraker 讲的是**产品分线**（维护成本、兼容性、销售、市场四个问题）。
GiST 讲的是**代码分线**。**你要做的是后者** —— 因为你的成本瓶颈不在销售，
而在「一套机制能不能同时容纳多种方向」。

## 五、★ 递归停在哪里：内生 / 外生

模块化有一个真实危险，必须现在划界：

    方向函数是插件
    ⇒ 选哪个方向函数，能不能也按使用优化？
    ⇒ 那「优化方向函数」需要目标
    ⇒ 那个目标又按使用优化？
    ⇒ 无限递归

**这个递归必须在某处停住。停的地方就是模块化的边界。**

### 判据：反馈信号的内生 / 外生

| 反馈信号 | 能否由 usage 估计 | 处置 |
|---|---|---|
| 层内：哪个方向更值得展开 | ✅ 内生 | **可模块化、可自我优化** |
| 层内：收益 / 开销的局部权衡 | ✅ 内生 | **可模块化**（放进 `Penalty`） |
| 方向函数本身：什么算一个方向 | ❌ 外生 | **必须由人声明，不能自我优化** |
| 最外层意图：为谁、为什么服务 | ❌ 外生 | **必须由人声明** |

**⇒ 模块化的边界 = 反馈信号的内生/外生分界。**

外生部分一旦允许自我优化，你就同时失去了两样东西：
**可复现性**（同一份数据，不同历史 ⇒ 不同结构）和**可解释性**（说不出为什么长这样）。

## 六、「通用」的准确含义

回到你的原话：「如果打算做通用的话，按哪个方向都会不满意」。

**这句话对，但「通用」的对象错了。**

| 说法 | 成立？ |
|---|---|
| 「一个方向通用」 | ❌ 必然有人不满意 —— 你说得对 |
| 「内核通用 + 接口通用」 | ✅ 这才是可做的 |

具体地：

    内核（通用、固定）：
      层的存在与秩、包含关系的形式、见证与支撑锥、
      失效不删除（0 ≠ 没有）、倾向权重的记账位、遍历循环、
      以及「假阴禁止 / 假阳只损失性能」这条契约

    插件（按方向换）：
      什么算一个方向、两个方向怎么合、一个东西该进哪个方向、
      方向太满怎么劈、方向怎么存、局部权衡怎么算

**方向由使用者声明（外生）⇒ 不存在「按哪个方向都不满意」的问题，
因为内核不替你选方向。** 它只保证：无论你选哪个方向，层的机制都成立。

---

## 七、风险：内核接口是一个赌注

GiST 不是万能的。PostgreSQL 里同时存在 **GiST / SP-GiST / GIN** 三种可扩展索引 ——
**说明「一套内核接口通吃」这个赌注，工业界自己都押了三次。**

⇒ 风险是具体的：**如果内核接口押错了结构不变量，就需要第二个内核。**
押对的表现是「多数方向只需要写插件」；押错的表现是「为了某个方向不得不改内核」。

**所以第一版该做的不是支持很多方向，而是：**
**用两个差异足够大的方向去试同一个内核** —— 如果两个方向都只用写插件，
接口就是对的；如果有一个逼着改内核，就知道押错了。

## 九、一句话

**能模块化，接口就六个方法，而且插件允许不准 —— 因为方向函数只是个过滤器，
假阴才致命，假阳只损失性能。**

「通用」的正确定义是**内核通用 + 接口通用**；
方向必须由人声明（外生），方向内部的参数才交给使用去调（内生）。
**这条界线就是模块化的边界。**
