# 壳层选型：哪些自研该换成成熟方案（2026-10-29）

**为什么写这份**：P1 + agent 面一共写了 **2095 行**壳代码（`serve.py` 1028 / `serve_auth` 205 /
`serve_sched` 177 / `serve_tenants` 162 / `e2e_agent` 523），其中**有六处是可以不自己写的**。
按「先查、查到就用、查不到再自研」的顺序重过一遍，逐条给出**结论 + 证据 + 触发条件**。

⚠️ **本次没有安装任何第三方库**。`pip download --no-deps` 到临时目录只为两件事：
确认**拿得到**、以及确认**当前版本号**（下表都是今天实测的）。下面每个「换」都写清成本。

## 0 一页结论

| # | 我们自研的 | 成熟方案（实测可得的当前版本） | 判定 |
|---|---|---|---|
| 1 | 手写计数字典 + 自家 JSON `/metrics` | `prometheus-client` **0.26.0** | ✅ **建议换**（成本 1 小时） |
| 2 | 固定窗口 60 S 配额 | `pyrate-limiter` **4.5.1** / `limits` **5.8.0** | ⏸ 不换（精度问题已知，见 §2.2） |
| 3 | 槽位幂等调度器 | `APScheduler` **3.11.3** | ⏸ 不换，但**照抄它的一条语义**（见 §3.2） |
| 4 | `http.server` 手写路由 | `FastAPI` **0.162.0** + `uvicorn` **0.54.0** | ⏸ 暂不换（P2 再换，见 §5） |
| 5 | 内存任务表 + 线程 | `huey` **3.5.3**（SQLite 后端）/ RQ / Celery | ⏸ 不换（P3 用 SQLite 单表即可） |

## 1 指标：`prometheus-client`（**已换**，2026-10-29）

**现在**：`Metrics` 类 + `/metrics` 返回自家 JSON（`计数: {提问: 3, 响应 2xx: 12, …}`）。
判据读它，端到端也读它。能用，但**只有我们自己看得懂** —— 接任何现成看板都要写适配。

**成熟方案**：`prometheus-client`，官方文档给了两种暴露方式：
- 自己的 WSGI/ASGI 应用里 `generate_latest(registry)` 直接输出文本（最轻）；
- FastAPI 用 `make_asgi_app()`（需 **> 0.26.0**，0.26.0 及更早会 `TypeError`）。

多进程部署要开 `PROMETHEUS_MULTIPROC_DIR`，且文档明说这模式有**一串限制**
（自定义 collector 不可用、`Info`/`Enum` 不可用、Gauge 要用 `multiprocess_mode` 选聚合方式）。
我们把 `/metrics` 当「本进程发生了什么」用，先**不开多进程模式**就不会碰到这些限制。

**实际怎么做的**（2026-10-29）：`/metrics` 出文本、`/metrics.json` 留 JSON，
判据与端到端改读 `.json` —— **一条判据都没删**，只多了一条「文本出口是标准的」。

★ 落地时踩到**两个文档没写的坑**（都写进 `serve.prometheus_text` 的注释了）：
1. `CounterMetricFamily` **不在顶层**，在 `prometheus_client.core` 里（照文档 `from prometheus_client import …` 会 ImportError）；
2. 直接 `registry.register(fam)` 会 `TypeError: unhashable type: 'CounterMetricFamily'` ——
   0.26.0 里这个对象不可哈希，注册表拿它当字典键就炸；**必须**包一层 `collect()` 返回它的 collector。
   （文档示例用的是 `Counter(...)`，那类对象可哈希，照抄到 MetricFamily 上就翻车。）

## 2 限流：`pyrate-limiter` / `limits`（不换，但把已知误差写清）

### 2.1 我们的实现

固定窗口：`slot = now // 60`，计数落在 `(principal, slot)` 上，超了返回 `Retry-After`（`serve_auth.Quota`）。

**它是准的**（有判据 ⑳ 62 钉着），误差是**算法本身的**：窗口边界前后各打满一次，
最坏 **1 秒内用掉 2× 配额**。这一点我写在 `serve_auth.py` 的文件头里，没藏着。

### 2.2 成熟方案怎么说

`pyrate-limiter` 的算法对照表把这个误差写得很直白：

| 算法 | 存储 | 代价 |
|---|---|---|
| SlidingWindowLog（默认） | 每消耗一个单位存一条 | 精确，滚动窗口内**永不超过** limit |
| FixedWindow | 每消耗一个单位存一条 | 粗：**边界处可过 2×limit** |
| GCRA / TokenBucket | 每个 rate 存**一个数** | 常量内存、输出平滑；需要 `StateBucket` |

它还直接演示了我们这个 bug 的形状：`Rate(3, SECOND)` 配 `FixedWindow()` ⇒
「边界前 3 个、边界后 3 个，**100 ms 内过 6 个**，两个窗口都没超」。

### 2.3 为什么不换

- 现在的调用方只有端到端脚本与判据，**没有真实多客户端**（用户 2026-10-29：「多人服务暂时不重要」）；
- 换算法要改判据 ⑳ 62（它现在断言的正是固定窗口的边界行为），而判据刚被端到端复核过；
- GCRA 的好处（常量内存）在**单进程内存态**上体现不出来 —— 我们本来就不落 Redis。

**触发条件**：一旦对外暴露（反代后面挂真调用方）⇒ 换 `pyrate-limiter` 的 `StateBucket` + `TokenBucket`
（等价 GCRA），或者**更彻底**：把限流推到 nginx/Envoy（`limit_req`），壳里那 60 行删掉。

## 3 调度器：`APScheduler 3.11.3`（不换，但要照抄一条语义）

### 3.1 对照

`add_job` 的三个参数正好对应「重复 tick 会催熟 k」这件事：

| APScheduler 参数 | 文档原文（节选） | 我们对应的东西 |
|---|---|---|
| `coalesce=True` | 「如果调度器发现同一任务欠了多次执行，**只触发一次**」 | 槽位：同一槽只 tick 一次 ✅ 等价 |
| `max_instances=1` | 「同一任务最多 1 个实例同时跑」 | 调度线程单线程 + 槽位锁 ✅ 等价 |
| `misfire_grace_time` | 「晚了多少秒内还允许跑；`None` = 多晚都跑」 | **没有** ❌ 见 §3.2 |

而且它没有任何分布式选主 —— 有中文资料直接写「禁止在分布式环境直接运行 APScheduler：
多实例共用同一数据库会导致脑裂」。这跟我们 P1 文档里「不做租约 ⇒ 单实例是前提」是同一个结论。

### 3.2 我们没有的那条：`misfire_grace_time`

我们的行为是「停了 3 小时再起来，下个槽照常走一格，**不补票**」。
APScheduler 的行为是「欠的执行按 grace 窗口判：窗口内补一次，窗口外**丢弃**」。

两者在「不重复 tick」上一致，但**语义不同**：我们是「永远不补」，它是「窗口内补」。
当前选择（不补）更适合 `k` 的算法 —— `k` 是按**账本时间**算的，补票只会把账本写乱。
⇒ **不换，但把这条写进文档**（已在 `docs/P1落地.md` §4「不承诺」里），避免以后有人以为
「停了三天，起来应该补三格」。

### 3.3 为什么不换

- 3.x 是成熟线，**4.0 是重写**（社区实测帖：`BackgroundScheduler` / `BlockingScheduler` 被移除、API 不兼容；⚠️ 这条来自 Stack Overflow 而不是官方迁移文档，所以只当**风险提示**用）——
  现在就换，等于赌一个还在改的 API；
- 我们那 60 行有 **4 条判据**（⑳ 70 / 71 / 72 / 73，含一条反向对照），换成 APScheduler
  要把这 4 条重写成「对第三方行为的断言」，判据反而变弱（判的是它的实现细节）；
- 单实例 + 落盘 + 槽位这套，依赖面是 **0**。

## 4 认证：**没有库可换，因为我们已经在行业做法上**

`serve_auth.py` 逐条对上业界清单（来源：OWASP API Security Top 10 2023 +
Secrets Management Cheat Sheet 的工程化总结）：

| 业界要求 | 我们的实现 | 对上没 |
|---|---|---|
| CSPRNG、**≥256 bit** 熵、不许用 UUID/时间戳/人想的词 | `secrets.token_urlsafe(32)`（≈256 bit） | ✅ |
| **只存哈希**，明文只出现一次 | `tokens.json` 存 `sha256`，`--mint-token` 打印一次 | ✅ |
| 传输走头、**不进 query** | `Authorization: Bearer` | ✅ |
| **按 key 限流** | `Quota`（每秒/每分钟） | ✅ |
| **最小权限 / 按范围发放** | `tenant` 字段绑定单租户，`*` 才是管理员 | ✅ |
| **有轮换与过期，且支持双 key 重叠** | **没有** | ❌ |

⚠️ 一处要说明白的**细节**：业界清单说「用 bcrypt / Argon2 / BLAKE3-HMAC 这类**口令安全**的哈希」。
那是给**低熵**密钥（人想的口令）用的。我们的 token 是 256 bit 随机，
离线爆破的代价本身就是天文数字 ⇒ **快哈希（sha256）在这里是合理的**，
和 GitHub PAT / Stripe 存 key 哈希是同一档做法。
**但如果哪天允许人手填 token**，就必须换成 Argon2 —— 这条差别写进代码注释。

**真缺口：过期与轮换**。现在 token 永不过期，改 token 要重启（重启丢任务表）。
建议（约 10 行 + 2 条判据）：

```
tokens.json 每条加 "expires_at": "2027-01-31"（缺省 = 不过期，但启动时打印警告）
过期 ⇒ 401 + X-Ldv-Error: unauthorized（与"认不出"共用状态码，正文分开写）
--rotate NAME ⇒ 生成新 token，旧条目保留到 expires_at（双 key 重叠）
```

## 5 HTTP 框架：`FastAPI 0.162.0 + uvicorn 0.54.0`（暂不换，**且现在换会静默坏一件事**）

### 5.1 收益（真收益，不是空话）

- `openapi.json` 自动生成 ⇒ 契约 `ldv-http/1` 从「文档里的一张表」变成**机器可校验的 schema**；
- 中间件生态：请求 id、耗时、异常映射、CORS 都是现成的；
- 依赖注入能把「认证 → 授权 → 配额 → 租户加载」这条链写成显式依赖，而不是我手写的四道 `if`。

### 5.2 代价（比看起来大）

1. **判据要重写**：25 + 13 条判据都打在 `serve.Handler` 上（进程内起 `ThreadingHTTPServer`、
   改 `Handler.root` / `Handler.store`）。换框架 = 这 38 条全部改写成 TestClient 版；
2. **部署形态变了**：从 `python serve.py` 变成 ASGI 进程管理（`uvicorn --workers N`）；
3. ★ **最要命的一条**：`AppCache` 是**进程内**状态（`_last_shown` / `_tendency`）。
   `uvicorn --workers 4` 之后，`/ask` 落在 worker A、`/drill` 落在 worker B ⇒
   `_last_shown` 是空的 ⇒ **使用记录时有时无**，而且文案仍然说「这一支不在刚展示的候选里」
   —— 又是一个「功能断了但看起来像业务判断」的坑。

⇒ **换框架的前提是先把 App 状态外置**（落盘或 Redis）。在那之前，多 worker 是**负收益**。
这条正是「成熟方案不一定适配」的例子：框架是对的，我们的状态形状还没准备好。

### 5.3 触发条件

P2（多客户端 / 要给外部出 OpenAPI）时换，且**先**把 App 状态外置。

## 6 任务表：`huey 3.5.3` / RQ / Celery（不换）

现在的 `TaskTable` 是内存 + 线程 + 条件变量，`MAX_PER_TENANT=1` 的排队/限流是**同一个计数**
（设计文档 §1 第 3 条），有 5 条判据（⑩–⑫ + 失败路径）。

成熟方案的门槛：RQ / Celery **要 broker**（Redis/RabbitMQ）；`huey` 支持 SQLite 后端，
是这批里唯一「不引入额外服务」的。

**为什么不换**：引入 broker = 多一个要部署、要监控、会挂的东西，而我们的任务粒度是
「一个租户同时最多 1 个构建」—— 这个规模用 SQLite 单表（`id / tenant / status / 提交时间`）
就能做到落盘 + 重启可恢复，比 Celery 少两个数量级的运维面。

**触发条件**：P3（任务表要跨进程/跨重启）→ SQLite 单表 + 一个 worker 循环；**不到需要
异步任务重试/定时重试的程度，不用 Celery**。

## 7 缓存失效：`watchdog 6.0.0`（不换）

`AppCache` 现在按**目录 mtime** 判失效（加/删/改名会重建，原地改要 `?refresh=1`）。

成熟方案是 `watchdog`（Windows 下 `ReadDirectoryChangesW`、Linux 下 inotify）做事件驱动失效。
**不换的理由不是"少写几行"，是事件驱动在这里更差**：

- 我们只需要知道「该不该重建」，**不需要知道改了哪个文件** ⇒ 一次 `stat` 就够，O(1)；
- 批量写入（一次喂 800 个节点）会触发 800 个事件，inotify 队列会溢出（`IN_Q_OVERFLOW`），
  溢出后**要么漏重建、要么退化成轮询** —— 两个结果都比现在的 mtime 差；
- 多一个后台线程 + 一个平台相关依赖，换来的只是「原地改内容也能立刻看到」。

**触发条件**：真的需要「秒级热更新同一批节点」时，用 watchdog 做**提示**（收到事件就置脏），
重建仍由请求路径触发 —— 这样溢出只是晚一点重建，不会漏。

## 8 喂料：不需要方案

`/tenants/<名>` 建出来是空库，喂料 = 往 `<租户>/nodes/` 放 `.md`。这不是偷懒：
约束②定的是「一租户一目录，**备份 = 拷目录**」，文件落盘**就是**这个设计的摄入接口。

真要给远程 agent 写入，成熟做法是 tus（断点续传）或普通 `PUT /<名>/nodes/<id>`
（幂等 + 内容校验）。后者 20 行就够，引库不值。**现在不做**。

## 11 三条「明知有成熟方案也不换」的共同理由

1. **判据是资产，换实现等于把资产清零。** 38 条判据 + 27 步端到端刚刚把行为钉住；
   换框架/换调度器都要重写它们，而重写后的判据往往只能断言「第三方是这么做的」——
   比断言「我们的行为是这样」更弱。
2. **依赖面 = 故障面。** 内核零依赖、壳零依赖，`python serve.py` 一条命令起服务，
   这是能在这台网络极不稳定的机器上反复跑通 27 步端到端的前提。
3. **收益窗口不对。** FastAPI 的收益（OpenAPI、中间件、DI）在「只有一个客户端」时换不来；
   等 P2 真来了，收益才成立 —— 那时换，成本还更低（状态已经外置了）。

**唯一我建议现在就补的两件**（§10 ①②），都不是「选型」，是**缺口**：
token 没有生命周期，指标没有标准出口。
