# 与普通检索系统的质量对照（**不比效率**）

**配套**：`分层方向视图-设计文档.md`（v0.1.21）§4.3 / §K8；`分层方向视图-检索器层.md` §14.6
**用途**：回答「它和普通检索系统比，好在哪」—— **只比交付物的质量，不比效率**。
**实跑**：`python -m ldv.tools.compare_bm25`（零第三方，标准库跑完；本文的数全部来自它）
**引文纪律**：本文的英文引文全部回源文逐字比对。网页源的**缓存路径写在出处行里**
（`<工作区根>/.webcache/`，登记见 `docs/prior-art/README.md`）。

对照对象两类：**经典 IR**（倒排 / BM25 —— 本文**实跑**）与
**向量 / embedding 检索**（RAG 那一套 —— 需要模型 ⇒ 与「零第三方依赖」冲突 ⇒ **只引文献**）。

---

## §0 一个必须先说清的前提

**ldv 不是检索系统。** 这不是谦辞，是它自己写死的边界（README「它不是什么」逐字）：

> - **不排序、不打分。** 排序即推荐，本层不做推荐器
> - **不做匹配。** 把一段处境映射到方向是**检索系统上层**（**检索器层**）的事

⇒ 拿 **nDCG / MAP / Recall@K** 去量 ldv，量的是**它没有的东西**。
「比质量」只能比**交付物的质量维度**，不能比排名。

★ 而且这条口径 v0.1.15 自己已经钉过（检索器层 `§14.6`）：

> **收益 = 影响**，不是检索效率。……**访问量是读数、不是收益**，两者不许互相冒充

—— 正好对得上「比质量不比效率」。

## §1 逐维对照

| 质量维度 | 普通检索（BM25 / 向量） | ldv | 可比吗 |
|---|---|---|---|
| **相关性排序** | **有定义**：nDCG@k / MAP / MRR，要标注集 | **不定义** —— 不排序、不打分 | ❌ **不可比**（ldv 不产出排序） |
| **召回 / 不漏** | **统计**：Recall@K（K 由人拍）；漏了**不报错** | **判据**：`B1` 假阴禁止，**批建 / 维护两条路径各一条** ⇒ 破了**红** | ✅ 可比，但是**两种不同性质**的东西 |
| **精确 / 假阳** | Precision@K；假阳**拉低分数** | `§K8`：假阳**允许**，但**必须计量**（十个度量里三个在量它）⇒ **不进退出码** | ⚠️ 口径不同 |
| **可核验 / 可解释** | 解释性检索有研究；常规做法是**分数分解**（哪几个词贡献多少） | 每条读数**独立重算**（`§A4`）；账**逐条可指认**（`§A5`）；`T3` 解释指得到**实际结果** | ✅ ldv 更严（**可复算** > 可读） |
| **歧义 / 多解** | 给一个 top-k 列表（**把多解压成一维顺序**） | 给**方向分解**：块级三态画像 + 「下一步往哪看」的块级建议 | ⚠️ 交付物不同 |
| **越界 / 判不了** | 总返回 top-k（哪怕全是垃圾） | 「判空」**显式报**（`§K2`）；`T4` 把「已细分过 / 分不开 / 还没长出来」**分三档** | ✅ ldv 有「停下来」这一档 |
| **结果集本身** | 由打分决定 | **`T1`：候选集 ≡ 不用视图直接遍历** ⇒ ldv **不改结果集**，改的是**判断与解释** | ❌ 结果集相同 ⇒ **差别不在结果** |

★ 最后一行是这份对照的**结论所在**：
**ldv 在结果集上不比普通检索多给任何东西**（`T1` 是定理），
它多给的是**「这份结构漏没漏、粗不粗、说不说得清」**。

## §2 实跑：同一份语料、四个需求

**装置**：随仓库那份语料（`ldv/corpus/nodes/`，**36 项 / 47 边**）。
BM25 自写（`k1=1.2` / `b=0.75`，中文走**字符二元组** —— 不引 jieba）。
索引的文本 = 正文 + `title` / `scope` / `notes` / `aliases` / `cues`（**不含栏位值**）。

**真值**由**栏位取值逐项筛**得到（`key ∈ item.keys`）—— 不拿任何一方的输出当答案。

⚠️ 下面每块都是 `python -m ldv.tools.compare_bm25` 输出的**逐字摘录**：
只去掉了分隔线（`────`），`…` 处是省略，**其余一字未改**。

     'judge-0012']｜**多 1** ['con-0006']

  **项级答案**（`hit_items`，状态 是）：14 项 [… 14 个 judge-0001…judge-0014 …]
  ★ 与真值比对：**完全一致**（真值 14 项）

词袋匹配找不到「没写出来的属性」。多出来的 `con-0006` 则是**正文提到**「判断点」但**自己不是**判断点。

## §3 公平起见：普通检索**也能**做字段过滤

上面的对照**不能**读成「BM25 做不到」。Elasticsearch / OpenSearch 的 `term` 查询
**就是**「字段等于 X」，而且它是**完整的**（不像 top-k 那样截断）。
⇒ 所以真正的差别**不在「能不能」**，在这三处：

1. **交付物的层级不同。** 字段过滤给你**一串项**；ldv 给你
   **「哪些方向盖住了这一带 + 每个方向盖住什么 + 盖住的东西有没有漏」**。
   同一个需求，前者是**答案**，后者是**一份可核验的判断**。
2. **「不漏」的性质不同。** 字段过滤的不漏是**实现承诺**；ldv 的不漏是**判据**
   （`B1` 假阴禁止，**两条路径各一条**，破了当场红）。
   ——「承诺」与「每次跑都在判」是两件事。
3. **可核验性不同。** 普通检索告诉你**分数**；ldv 的每条读数**能独立重算**
   （`§A4` 的 oracle 从成员集现算、不读账本自己的说法），账**逐条指得到方向 + 项**
   （`§A5`）—— 那是 `false-green` 形状 3「共享盲点」的防线。

★ 而**词袋那一侧的结论**，外面早就说过了 —— 这不是本项目的新发现：

> 「BM25 is fundamentally a bag-of-words model. It has no understanding of meaning.」
>
> —— *BM25 vs. Vector Search: Choosing the Right Retrieval Strategy for Production Systems*
> （dev.to，2026-04-07；缓存 `<工作区根>/.webcache/devto-bm25-vs-vector-search.html`）

它自陈的失败面正是本文实测到的两面：**vocabulary mismatch**（漏）与
**conceptual similarity**（把「提到」当成「是」）—— 这两条也在同一篇的
「Breaks down at」列表里。

## §4 向量 / embedding 检索（RAG 那一套）

**为什么不实跑**：向量检索要一个 embedding 模型。本项目的硬约束是
**零第三方依赖**，且立项根基是**禁止模型代填内容**
⇒ 引模型进来就**推翻了前提**，不是一个可以商量的取舍。

### 4.1 它那边的质量维度（权威口径）

RAG 这套评测框架把检索质量与生成质量**分开**量，检索侧两个：

| 指标 | 定义（逐字） | 要真值吗 |
|---|---|---|
| **Context Recall** | 「measures the extent to which the retrieved context aligns with the annotated answer, treated as the ground truth」，值域 0–1 | **要**（`question` + `ground truth` + `contexts`） |
| **Context Precision** | 「evaluates whether all of the ground-truth relevant items present in the `contexts` are ranked higher or not」—— 对每个 k 算 `Precision@k` 再取均值 | **要** |

—— 来源：Ragas 官方文档 *Context Recall* / *Context Precision*，
**v0.1.21** 的正文（缓存 `<工作区根>/.webcache/ragas-v0.1.21-context_recall.md` /
`ragas-v0.1.21-context_precision.md`）。
⚠️ **写清版本号是必须的**：Ragas 的现行文档已经把这两段改写了
（现行 *Context Recall* 讲的是「how many of the relevant documents … were successfully retrieved」）
⇒ 只写「Ragas 官方文档」会让人拿现行页面对不上，**把一条对的引文读成错的**。

★ 两者**都要真值**，而且 **Context Precision 整个是「排得高不高」**。

### 4.2 与 ldv 的关系：**三条可比、两条不可比**

| | 结论 |
|---|---|
| **「漏」这一维可比** | `Context Recall` 与 `B1`（假阴禁止）问的是同一件事：**该命中的有没有全命中**。区别在**谁定真值** —— RAGAS 要人给 `ground_truth`，ldv 的 `ideal` 也是**外生声明**（内核不猜，`B1` 才有得比）。**这一条同构。** |
| **「精确」这一维口径相反** | RAGAS 的 Context Precision 是**排序质量**（`Precision@k`）；ldv 的 `§K8` 说**假阳允许**、代价是**性能**，所以它**只计量、不进退出码**。⇒ 拿 `Precision@k` 量 ldv 会得到一个**它有意不优化**的数 |
| **「不排序」这一维不可比** | Context Precision **整个**建立在「排得高不高」上；ldv **明令不排序**（排序即推荐）⇒ 这一维**没有公共尺子** |
| **「可核验」这一维 ldv 更严** | RAGAS 的两个指标都**由模型判**（claim 能不能归因到 context、chunk 相不相关）；ldv 的 oracle 是**独立重算**的整数判据（`§A4` 无 ε）、账**逐条指得到**（`§A5`）。⇒ 前者是**判官**，后者是**复算** |
| **「结果集」这一维无差别** | `T1` 定理：ldv 的候选集 ≡ 不用视图直接遍历 ⇒ 向量检索多召回的，ldv **一条也不会多**（也不会少） |

### 4.3 一条外面反复强调的纪律，本项目早就在做

> 「Not evaluating retrieval independently — teams blame the LLM when retrieval
> is the actual failure point. Measure Recall@K and MRR before debugging generation.」
>
> —— 同上（dev.to，2026-04-07；缓存同上）

ldv 的对应物是：**判据与度量分工**（`B18` 报「漏」、`B17` 报「分辨率下界」、
`§A4` 报「读数类别」），而且**判据进退出码、度量不进**。
「别把上游的漏读成下游的错」—— 这条在本项目里是一条**写在文档里的分工**，
不是一个要靠自觉的提醒。

## §5 结论

**在结果集上，ldv 不比普通检索多给任何东西**（`T1` 是定理，实测候选集 ≡ 直接遍历）。

**它多给的是三件**：

1. **「不漏」是判据不是承诺** —— `B1` 假阴禁止，**批建 / 维护两条路径各一条**，
   每次跑都在判，破了当场红。普通检索的 Recall@K 是**统计读数**。
2. **交付物从「一串项」变成「一份可核验的判断」** —— 方向级候选 + 每条解释**指得到实际结果**
   （`T3`）+ 块级三态画像（「你那一带是什么」）+ 「下一步往哪看」的块级建议。
   读数**能独立重算**（`§A4`）、账**逐条指得到方向与项**（`§A5`）。
3. **有「停下来」这一档** —— 判空显式报（`§K2`）；「已细分过 / 分不开 / 还没长出来」
   **分三档**（`T4`），不让「不知道」与「已经到底了」长得一样。

**它不参与的**：话题性 / 语义匹配（§2.4）、排序与打分、以及**效率**（访问量零变化，
那是**读数**不是收益）。

**一句话**：普通检索优化的是**「列表排得好不好」**；ldv 优化的是
**「这份结构漏没漏、粗不粗、说不说得清」**。
两把尺子量的不是同一个东西 —— 而**混用**它们，会把 ldv 读成「一个排得不好的检索器」。
