# 谓词推导 · 反思层 · 记忆分层

**版本** v0.1.32 ｜ **状态**：🟢 **已落地**（2026-10-17，三个**可选入口**）
`--predicates`（谓词推导）· `--reflect`（反思层，只调展开顺序）· `--index`（记忆分层，跨进程索引）· **缓冲区**（谓词三段 + 记忆 `_staging/`）

> **它是什么**：让系统**从材料推导谓词**（不是生成方向），并把内生量汇总成
> **机器可读的报告**，用报告调展开顺序。
> **它不是什么**：不是「自动生成方向」—— 方向函数仍然由人声明（外生不破）。

---

## §0 一句话边界

    §5 的表：  什么算一个方向        → 外生，必须人声明     ← **没碰**
               层内哪个方向值得展开   → 内生，可自我优化     ← **只碰这个**

本文件做的两件事都落在「内生」那一侧：**参数从材料算**、**顺序按内生量调**。

---

## §1 ★ 三层区分（骨架）

以出度为例：

| 层 | 内容 | 内外生 | 谁能改 |
|---|---|---|---|
| **规则** | 「按 out_degree 取切分点，零值单列 + 非零三分」 | **外生** | 人（写进 `predicates.json`） |
| **参数** | 切分点 `[0, P33, P67]` = `[0, 2, 5]` | **内生** | 从材料算，**可复现** |
| **谓词** | `出度档>0` / `>2` / `>5` | **确定** | 规则 + 参数唯一确定 |

⇒ 同一份材料 ⇒ 分位数唯一 ⇒ 谓词唯一 ⇒ 划分唯一。
**换材料才变** —— 那正是「结构是材料的函数」这个卖点本身。

### 与现状的差别

现状：`type: 出度0` / `出度1-3` / `出度4-15` / `出度16+` 这四个字符串是
**摄入脚本里硬编码的**（人拍的），参数层是空的。

本层：档位边界从材料的**分位数**算出来。**规则没变，值从材料来。**

---

## §2 ★ 为什么谓词必须是「二分」

第一版按**档位标签**产出（`出度档=低` / `=中` / `=高`），**错了**：

- 同一条规则的两个档是**互斥**的（一个节点不可能同时在「低」和「中」）
- 预算截断按区分度挑，很可能**同时选中两个互斥档** ⇒ 合取是空方向
  （`§K2` 判空会报，但报的是症状不是病）

改成**二分切分点**（`出度>2`）后：任意两个谓词可组合，零值单列 = 切分点 0。
判据 `⑲ 可组合` 钉这一条（任意两个采用谓词的合取非空）。

## §3 谓词预算：N = 3（**外生定死**）

```
每个方向切分时最多用 N 个谓词 ⇒ 子方向上界 2^N = 8
超预算的谓词**记录在案**（`predicates.json` 的 `超预算` 段），不静默丢弃
```

★ **N 不交给系统调**。理由：像「让 `B19` 不报红的最大 N」这种自适应，
会让 **N 依赖历史** ⇒ 外生项自我优化 ⇒ 同材料不同历史得到不同结构。

⚠️ **「区分度」只用于排序**，不用于判断好坏（`评估标准.md` 的「不作分」）。
排序选 N 个是合法的；一旦变成「区分度低于 X 的删掉」，就是系统在当裁判。

## §4 反思层：只调展开顺序

```
外生判据（run_checks 97 条 + 注入 71 条）
        ↓ 只读，不改
反思报告（JSON，字段全是内生量）
        ↓ 系统消费
展开顺序（`--reflect` 预展开）
        ✗ 不许碰：方向函数 / 判据 / 外生项
```

### 报告字段（白名单，判据 `㉕` 钉死）

| 字段 | 含义 |
|---|---|
| `方向数` / `待展开数` | 结构规模 |
| `展开序` | 建议先展开的方向 id（**外生规则**排序：成员数降序、did 升序） |
| `逐方向` | 每个方向的成员数 / 子方向数 / 是否待展开 |
| `排序规则` | 写死的那条规则名（可审计） |

⚠️ **没有**「分数 / 健康度 / 优先级分」—— 有意为之（「不作分」红线）。

### ★ 前提是一条实测

「只调顺序」安全，前提是**顺序不影响最终结构**。2026-10-17 实测：

    同一份语料，按正序 / 反序跑完全部查询
    ⇒ 方向数 19 / 19，结构签名（did / parent / 子数 / 成员数）**逐字相同**

⇒ 判据 `㉔ 结构不变`：预展开后方向树与不预展开逐字相同。

### ⚠️ 一个如实记录的读数

实测 `--reflect` 与默认路径的**终态完全相同**（25 个方向 / 判空 7 /
使用记录 72 条）—— 因为预展开的那些方向，查询本来也会展开。

⇒ **在当前查询集下，「展开顺序」不是这个系统的瓶颈**。这不是缺陷，
是读数：报告的价值在**可观测**（知道哪些方向待展开），不在改变结果。

## §8 记忆分层：短期 / 长期两层缓冲（2026-10-17）

### 8.1 先实测「压力在哪」—— 结论和预想不一样

| 实测（ext-coauth 9875 节点） | 读数 |
|---|---|
| 首次装载 | **4.69 s** |
| 二次装载（进程内缓存命中） | **0.268 s**（17×） |
| 拆解：每万节点 **读盘** | **3.90 s** |
| 拆解：每万节点 **解析** | **0.14 s**（仅 3.5%） |
| 查询（3 条） | **0.02 s**，**新长 0 个方向** |

⇒ **压力在「重复读盘」，不在「查询期工作集」**。
「工作区换入换出」在这个系统里没有压力 —— 查询只花 0.02 秒、一个新方向都不长。

⇒ 所以「短期/长期」的正确形态是：

    短期（工作区）  `loader._NODE_CACHE` —— 进程内，按 (路径, mtime, size)
    长期（存档）    `<缓存目录>/<语料>.index.json` —— **跨进程派生索引**

### 8.2 索引里存什么、不存什么

存：`id` / `fields` / `keys` / 每个文件的 `(mtime_ns, size)`
**不存**：`body`（Markdown 正文）

⚠️ 主流程（kernel / checks / cli）**一处都不用 body**（唯一用它的
`tools/compare_bm25.py` 是独立对照工具）⇒ 索引路径的 `Node.body` 是空串。
**等价判据只比 id / keys / fields**，body 差异如实标注。

### 8.3 为什么索引不进语料目录

「一租户一目录 + 备份 = 拷贝目录」是服务化的地基。索引写进语料目录会
污染备份、也会进 git ⇒ 写到 `~/.cache/ldv/`（`LDV_INDEX_DIR` 可覆盖），
**随时可删、可重建**。

### 8.4 失效规则（可复现）

    stat 全量 → 与索引里的 (mtime_ns, size) 逐个比
    全部匹配 ⇒ 直接用索引（**不读任何 .md**）
    任一不匹配 ⇒ **只重读那几个文件**，其余仍用索引
    索引里有、目录里没有 ⇒ 丢弃；目录里有、索引没有 ⇒ 新文件，读

stat 成本：9875 个文件 **0.47 s**（vs 读盘 4.69 s）⇒ 校验本身不是瓶颈。

### 8.5 数据验证（四份真实语料，`evidence/_probe_index_verify.py`，RC=0）

| 语料 | 节点 | 直读 | 首次 | 二次 | 加速 | 等价 |
|---|---|---|---|---|---|---|
| `pypi-deps` | 60 | 0.03 s | 0.02 s | 0.01 s | 2.7× | ✓ |
| `snap-email-eu-mini` | 120 | 0.06 s | 0.03 s | 0.01 s | 4.8× | ✓ |
| `ext-coauth` | 9875 | 4.59 s | 5.16 s | 0.68 s | 6.7× | ✓ |
| `ext-enron` | 36692 | 20.94 s | 22.47 s | **2.26 s** | **9.3×** | ✓ |

- **等价**：四份语料的 id / keys / fields **逐字相同**
- **失效**：改一个文件 ⇒ `重读 1`、其余全命中
- **端到端**：`--index` 与默认正文（从「═══ 方向」起）**逐字相同**

⚠️ **一个如实记录的读数**：`ext-enron` 直读在**磁盘冷**时是 **228 s**，
**页缓存热**时是 **20.9 s** —— 相差 11 倍。⇒ 索引的收益**在冷启动时最大**
（228 s → 2.3 s ≈ 99×），热缓存下是 9.3×。引用耗时必须连「冷/热」一起说。

### 8.6 判据（`run_tests.test_memory_index`，4 条）

| 编号 | 判据 |
|---|---|
| ㉖ | **等价**：索引路径 vs 直读 ⇒ id / keys / fields 逐字相同 |
| ㉗ | **命中**：二次装载全命中、零重读（**加速比只作读数** —— 小语料上被固定开销吃掉） |
| ㉘ | **失效**：改一个文件 ⇒ 只重读它 |
| ㉙ | **不污染**：索引在缓存目录，语料目录里没有索引文件 |

## §9 缓冲区：谓词三段 + 记忆 `_staging/`（2026-10-17）

### 9.1 为什么要缓冲

「推导出来就用」有两个问题：**没经过检查**（空谓词、id 撞车会静默进结构）、
**看不出进来过什么**（拒收的、待处理的，事后无从追溯）。

⇒ 缓冲区分三步，**谓词与记忆用同一个形状**：

    候选 → （判据自动筛选）→ 采用 / 拒收（带理由）

### 9.2 谓词缓冲（`predicates.json` 四段）

| 段 | 含义 | 是否进划分 |
|---|---|---|
| `候选` | 所有推导出来的谓词（不筛） | ✗ |
| `采用` | 过判据 + 排进预算的 | ✅ **只有这一段** |
| `超预算` | 过判据、但排在预算外的 | ✗ |
| `拒收` | 判据不过的 + **理由** | ✗ |

**提交判据**（自动、可复现）：

    ① 真二分：`0 < 满足数 < 总数` —— 切出两个非空子集
       （`== 0` ⇒ 空谓词；`== 总数` ⇒ 一个都切不开）
       ★ 这是 `§K2 判空` 与 `B19 变细守卫` 在**谓词层**的前置检查
    ② 预算：过 ① 的按区分度降序取前 N（区分度**只排序**，不当阈值）

**实测（三份语料）**：

| 语料 | 候选 | 采用 | 超预算 | 拒收 |
|---|---|---|---|---|
| `pypi-deps` | 6 | 3 | 3 | 0 |
| `ext-coauth` | 6 | 3 | 1 | **2** |
| `snap-email-eu-mini` | 6 | 3 | 3 | 0 |

`ext-coauth` 的两条拒收是 `出度档>0` / `入度档>0` —— 该语料**没有孤立点**
（满足数 9875 = 总数）⇒ **切不开** ⇒ 理由「所有节点都满足（切不开）」。
★ 这正是缓冲区的价值：**如果不缓冲，这两条会被当成正常谓词用掉**。

### 9.3 记忆缓冲（`<语料>/_staging/`）

```
<语料>/
├── nodes/             ← 正式（参与结构）
├── _staging/
│   ├── nodes/         ← 待提交（**不参与结构**）
│   └── rejected/      ← 拒收 + `<文件名>.理由.txt`
└── view_spec.json
```

**提交判据**（四条，确定性）：

    ① front matter 能解析
    ② 有 id（没有就用文件名 —— 与 `loader` 的约定一致）
    ③ id 不与已有节点重复
    ④ 文件名不与已有节点重复

⚠️ `load_nodes()` **只读 `nodes/`**，不碰 `_staging/` ⇒ 缓冲区里的东西
**不影响任何结构与读数**。这是「暂存 ≠ 已提交」在结构上成立的原因。

**实测（pypi-deps 端到端，跑完还原）**：

    暂存 2 个（1 正常 / 1 id 撞）→ 缓冲期结构仍是 60 个节点
    → 提交：1 个进 `nodes/`、1 个进 `rejected/` 并写理由「id 与已有节点重复」
    → 结构 60 → 61 → 还原回 60

### 9.4 判据（`run_tests.test_buffer`，6 条）

| 编号 | 判据 |
|---|---|
| ㉚ | **三段不重不漏**：候选 = 采用 ∪ 超预算 ∪ 拒收（两两不交） |
| ㉛ | **拒收有理由**：每条都带非空理由 |
| ㉛b | **拒收理由成立**：满足数 = 0 或 = 总数 |
| ㉜ | **缓冲不参与结构**：`_staging/nodes/` 不进 `load_nodes` |
| ㉝ | **提交判据**：正常进、id 撞的拒收 + 理由文件 |
| ㉞ | **提交后结构包含**：新节点出现在 `load_nodes` 结果里 |

### 9.5 真实数据测试（6 份语料 + 边界 + 与索引交叉验证）

留档：`evidence/_probe_buffer_real.out.txt`（探针 `evidence/_probe_buffer_real.py`，RC=0）

#### A 谓词缓冲：拒收率从 0% 到 50%

| 语料 | 节点 | 候选 | 采用 | 超预算 | 拒收 | 拒收率 |
|---|---|---|---|---|---|---|
| `pypi-deps` | 60 | 6 | 3 | 3 | 0 | 0% |
| `ext-coauth` | 9875 | 6 | 3 | 1 | 2 | 33% |
| `snap-email-eu-mini` | 120 | 6 | 3 | 3 | 0 | 0% |
| `arxiv-taxonomy` | 155 | 5 | 3 | 1 | 1 | 20% |
| **`gh-langs`** | 56 | 4 | 2 | 0 | **2** | **50%** |
| `crossref-journals` | 74 | 4 | 3 | 0 | 1 | 25% |

★ **拒收明细揭示了两类真实的结构退化**（都不是 bug）：

| 语料 | 被拒的谓词 | 满足数 | 为什么 |
|---|---|---|---|
| `ext-coauth` | `出度档>0` / `入度档>0` | 9875 / 9875 | **没有孤立点** ⇒ 阈值 0 切不开 |
| `arxiv-taxonomy` | `出度档>1` | 0 / 155 | **出度全 ≤ 1**（稀疏）⇒ 阈值 1 全不满足 |
| `gh-langs` | `出度档>1` / `入度档>10` | 0 / 56 | 同上，且入度也窄 |
| `crossref-journals` | `出度档>1` | 0 / 74 | 同上 |

⇒ 小语料的**度数分布退化**会让切分点退化（切不开或全满足）。
**缓冲区的价值就在这里**：不缓冲的话，这些谓词会切出一堆空方向，
而 `§K2 判空` 只会报「有 6 个方向是空的」—— **报的是症状，不是病**。

#### B 记忆缓冲：真实节点跨语料提交

副本上做（不碰原件）：从 `ext-coauth` 搬 **20 个真实节点** 进 `pypi-deps` 副本
→ 缓冲期结构仍 60 → 提交 **20/20**（id 格式不同、无冲突）→ 结构 **60 → 80**。

#### C 边界

| 场景 | 结果 |
|---|---|
| 空缓冲区 | `commit` 不报错，返回 `{已提交: [], 拒收: [], 说明: 缓冲区为空}` |
| **全拒收**（10 个全撞 id） | 0 提交 / **10 拒收** / **10 个理由文件** |
| **大批量**（100 个真实节点） | 全提交，结构 **60 → 160** |

#### D ★ 与索引交叉验证（两个机制正确协同）

| 步骤 | 读数 |
|---|---|
| 首次建索引 | 重读 **80**（全读）/ 命中 0 |
| 二次装载 | 重读 0 / 命中 **80** |
| **再提交 1 个节点** | **只重读 1 个**（其余 80 仍命中） |

⇒ 缓冲区提交（新增文件）会让索引**精确地**只重读新增的那一个 ——
两个机制不打架，也不互相掩盖。

### 9.6 它解决的是哪个问题

你之前问过「自主划分会不会导致方向分得过细」。缓冲区分担了一半：

- **预算 N** 管**数量**（最多 3 个谓词进划分）
- **缓冲区判据** 管**质量**（切不开的进拒收，不占预算）

⇒ 两者合起来：**系统可以自由推导，但只有「真的能切」且「排得上号」的才进结构**，
其余全部留痕。这就是「自动涌现」的安全阀。

## §10 组合谓词 · 矛盾报告 · 缓冲区容量（2026-10-17 第二批）

### 10.1 组合谓词：复杂度阈值 K=2，超了**报给人命名**

从**已采用的单谓词**做合取（`出度档>2 ∧ 入度档>5`）：

| 段 | 条件 | 进划分 |
|---|---|---|
| `待命名` | **复杂度 > K**（K=2 ⇒ **3 项及以上**） | ✗（**请人起名**） |
| `组合候选` | 复杂度 ≤ K | ✗（可读，不需要命名） |
| `组合拒收` | 切不开 / **同量冗余** | ✗ |

**为什么组合谓词一律不进划分**：预算 N=3 管的是「进划分的谓词数」；
组合也进划分会让预算失控，而且会加剧细化（用户明确担心过）。
**进划分的只有单谓词（预算内）与人命名后的基础谓词。**

★ **同量冗余**：`出度>0 ∧ 出度>2` —— 后者蕴含前者 ⇒ 组合退化成单项。
这类必须滤掉（判据 ㊲），否则待命名里全是假组合。

★ **基础谓词（人手写）**：人给组合起名后写进 `predicates.json` 的
`基础谓词` 段（名字 + 合取定义），程序重写文件时**原样保留**（判据 ㊴）。
命名后才作为键进划分（判据 ㊵）。

⚠️ **一个如实记录的读数**：在现有 6 份语料 + 预算 3 下，**`待命名` 是 0 个** ——
因为预算按区分度选出的 3 个谓词里常含**同量的两个切分点**（`出度>0` / `出度>2`），
3 项组合必然触发同量冗余。⇒ **K=2 的阈值在当前参数下不触发**。
机制本身可用（判据 ㊱ 用构造的 3 个不同量谓词验证过会触发）。
要让它真的触发，需要加量（扇出 / 可达深度）或调预算选法 —— **这本身是个读数，不是缺陷**。

### 10.2 矛盾报告：**只在结构层**

| 类型 | 判据 |
|---|---|
| 边打架 | 方向声明了 `parent=p`，但不在 `p` 的子列表里（`B13` 同一件事） |
| 子覆盖越出父 | 子方向成员并集 ⊄ 父方向成员（`§I4` 同一件事） |
| 孤立方向 | 没有父、也不是根 `D0` |

⚠️ **语义矛盾不做**（材料互相冲突要理解内容 ⇒ 撞「禁止模型代填」）—— 用户拍板「就在结构层」。
⚠️ 只**聚合**已有检查的读数，**不新增判据**（`checks/` 里各管各的）。
⚠️ 清单为空时**也要报查了什么**（`覆盖读数`：方向数 + 三项计数）——
否则「没查」与「查了没发现」长得一样。

### 10.3 缓冲区容量：超限**报出来**，淘汰只碰未提交

| 规则 | 值 |
|---|---|
| 容量上限 | `CAPACITY = 100`（外生） |
| 超限 | **报出来**（`capacity_status.超限`），不静默淘汰 |
| 淘汰顺序 | **按进缓冲区时间 FIFO**（`stage` 用 `copy` 不用 `copy2` —— 让 mtime = 进缓冲区时刻） |
| 不淘汰 | `_staging/rejected/`（审计链）· `nodes/`（已提交） |

⚠️ 淘汰**不按访问次数** —— 那依赖历史，会破坏可复现（`§5`）。

## §11 影响分析（反事实）—— 结构推理的最后一层（2026-10-17）

### 11.1 它回答什么

维护时最常问的两句：

    删掉这几个节点，哪些方向会**变空**？
    某个方向要是崩了，**影响面**多大？

### 11.2 为什么这是「推理」而不是「统计」

    预测：删掉 x ⇒ D3 的成员集减去 {x} 是空集 ⇒ **D3 会变空**
    实测：真删 x ⇒ D3 确实空了

**预测与实测对得上**，才叫推理。判据就是拿这两者比（㊿）。

### 11.3 三个接口（`ldv/core/impact.py`）

| 函数 | 作用 |
|---|---|
| `removal_impact(kernel, ids)` | 删这些项 ⇒ 会变空的方向 / 会缩的方向 / **不在结构里的项** |
| `blast_radius(kernel, did)` | 一个方向的**整个子树**：方向数 / 覆盖项数 |
| `compare_prediction(kernel, ids)` | **预测 vs 实测**（会改内核，调用方给副本） |

⚠️ **不报「占比」** —— 2026-10-17 写了 `占全树 = 子树方向数 / total`，
**当场被 `B12`（无全局标量分）抓住**：那个分母是「跨方向的全局总数」，
而**归一化就是打分的第一步**。⇒ 只报绝对数，比例由调用方自己算。
★ 这是「不作分」红线**真的在工作**的一次实证 —— 不是文档里的一句话。

### 11.4 数据验证（4 语料 × 3 规模）

留档：`evidence/_probe_impact_verify.out.txt`（RC=0）

| 语料 | 删 1 | 删 3 | 删 8 |
|---|---|---|---|
| `pypi-deps` | ✓（缩 2） | ✓（缩 5） | ✓（缩 9） |
| `snap-email-eu-mini` | ✓（缩 5） | ✓（**空 1** / 缩 30） | ✓（空 1 / 缩 34） |
| `ext-coauth` | ✓（缩 2） | ✓（缩 5） | ✓（缩 7） |
| `arxiv-taxonomy` | ✓（缩 2） | ✓（缩 2） | ✓（缩 2） |

**12/12 组预测与实测一致**。规模读数：`ext-coauth`（9863 项 / 9 方向）
删 10 项的影响分析 **0.004 s**。

### 11.5 判据（4 条，`run_tests` 658 → 662）

| 编号 | 判据 |
|---|---|
| ㊾ | **只读**：调用前后结构签名逐字相同 |
| ㊿ | **预测 == 实测**：会空 / 会缩的方向集与真删后一致 |
| ⑤① | **可复现**：同结构两次调用逐字相同 |
| ⑤② | **影响 0 明说**：删不在结构里的项 ⇒ 明确报「没有任何方向受影响」 |

### 11.6 到这里，结构推理的三层齐了

| 层 | 能力 | 判据 |
|---|---|---|
| 判断 | 项属不属于方向（`hit`，健全） | `B1` 假阴 0 |
| 传递 | 可达闭包（`reach`）· 递归分割（`expand`） | `B13` / `§K2` |
| **反事实** | **删了会怎样 / 影响面多大**（本节） | ㊾–⑤② |

再往上就是**语义推理**（「A 意味着 B」）—— 那要理解内容，撞「禁止模型代填」。
**这已经是这个架构能到的结构推理的天花板。**

## §12 方向请求：系统**只提问、不回答**（2026-10-17）

### 12.1 它在边界内的哪一侧

§5 说「什么算一个方向必须**人声明**，不能自我优化」。本节的形态是**线内侧**的：

    系统：发现「材料里还有差异，但你给我的键抓不到」⇒ 递**证据**
    人：  加不加、加什么，写进 `directions.json` ⇒ **拍板并留痕**

请求的是**新维度**（一个 front matter 字段，或一个新度量量），
**不是**新方向函数（那要人写代码，门槛高且撞外生线）。

### 12.2 数据形状：`<语料>/directions.json`

三段：`请求`（系统生成）· `已批准` / `已拒绝`（**人写，程序重写不覆盖**，
同 §10.1 `基础谓词` 的纪律）。字段一个不能少：

| 字段 | 为什么必须有 |
|---|---|
| `涉及的项` + `项数` | **证据**：到底是哪几个项切不开 |
| `已经试过` | 含谓词推导结果 —— 防「你不是已经有谓词推导了吗」 |
| `当前状态` | 一句话说清卡在哪（不是「没变细」，是「这些键切不开这 N 项」） |
| `请求` | 请求的是**新维度**，不是方向定义 |
| `判据编号` + `阈值` | 可指回 `B19` 的原始读数；阈值 N=10 是外生的，人能申诉 |

### 12.3 信号 ①：`B19` 连续 N 次展开没变细

复用 `checks/coverage.py` 的 `progress_profile` —— 与 `B19` **同一口径**，
不另造一套「连续」算法（否则会出现「请求说触发、判据说没触发」）。

⚠️ **「连续」是树链，不是调用次数**（2026-10-17 实现时踩到）：
沿根→叶、连续多少个**已展开方向**没变细，**不含叶**。
初版设计稿按「反复 expand 同一个方向的次数」写，得出「留 4 个键 ⇒ 连续 13」——
**那是错的**，已在设计稿 §4② 修正。

### 12.4 实测：现有语料**一律不触发**

| 语料 | 已展开方向 | 最长没变细连续段 | 阈值 N | 触发？ |
|---|---|---|---|---|
| 默认 36 项（三条方向） | 12 / 35 / 5 | **0 / 0 / 0** | 10 | 否 |
| 全量 3907 项（docstring 留档） | 3906 | **9** | 10 | 否（差 1） |

⇒ 36 项上**不可能**触发（树只有 9–19 个方向，链长够不到 10）。
真实样例（构造 11 连的链）留档 `evidence/_probe_direction_request.sample.json`：

```json
{"信号": "B19：连续 11 次展开没变细", "方向": "D10",
 "链": ["D0", … "D10"], "阈值": 10, "涉及的项": ["a","b","c"],
 "已经试过": [], "当前状态": "这 3 个项在当前键集下**无法二分**…",
 "请求": "需要一个能切开这批项的**新维度**…", "判据编号": "B19"}
```

### 12.5 判据（`run_tests.test_direction_request`，8 条）

| 编号 | 判据 |
|---|---|
| ㊀ | **只读**：生成请求前后结构签名逐字相同 |
| ㊀b | **会响**：构造 11 连的链 ⇒ 必须触发（否则机制是死的） |
| ㊁ | **可复现**：同结构两次逐字相同 |
| ㊂ | **每条带证据**：`涉及的项` 非空 + `判据编号` + `已经试过` |
| ㊃ | **处置过的不再请求**：人写进 `已拒绝` 后不再出现 |
| ㊃b | **写盘**：`请求` 与 `本趟查了` 都落文件 |
| ㊄ | **人写段不被覆盖**：重写后 `已批准` / `已拒绝` 原样保留 |
| ㊅ | **不触发时也要说**：请求为空，但 `本趟查了` 说清查了多少 |

### 12.6 边界

- 系统**只提问不回答**；方向函数的决定权仍**只**在人（§5）
- **不引入**「优先级 / 严重度 / 置信度 / 建议的新方向」——
  前者是打分（`B12` 扫源码），后者会让系统滑向定义方向
- 「连续」**只在会话内**，不跨运行累积（否则请求依赖跑过多少次 ⇒ 破可复现）
- **拒绝必须留痕**（否则同一请求反复冒 ⇒ 人把系统关掉）
- `directions.json` **每语料一份**（键集是语料的属性）

## §13 入口与过程优化：28 万节点教会的事（2026-10-18）

### 13.1 起因：一份「更大」的语料把入口撞穿了

下载 SNAP `web-Stanford`（**281903 节点 / 2312497 边**，网页链接图 —— 新领域，
比此前最大语料大 4.8×），摄入成扁平目录后：

    ls -S 列目录：300 s 超时被杀
    load_nodes：跑 1 小时 48 分仍未完成（被手动终止）

### 13.2 两个瓶颈，两个不同的解法

| 瓶颈 | 实测 | 解法 |
|---|---|---|
| **目录项数** | 扁平 28 万文件，枚举 + stat 就要几分钟 | **分片**：`nodes/<id 后两位>/` ⇒ 100 个桶、每桶约 1000 文件，枚举 **0.6 s** |
| **首次读盘** | 分片后读 2000 个新写入文件要 **13.13 s**（6.5 ms/个）⇒ 10 万个 656 s | **索引**：第一次付掉，之后秒级（已是既有机制） |

★ 一个**被数据推翻的假设**：一开始以为慢是「hub 节点 `relations` 巨大」。
实测出度 top10 **只有 255**、中位数 5、平均 8.2 ⇒ **文件大小不是问题，
是目录项数**。（入度确实有 38606 的巨无霸，但入度只写一个字符串，不占 `relations`。）

### 13.3 改了什么（四处）

| 文件 | 改动 |
|---|---|
| `ldv/corpus/loader.py` | `load_nodes` 用 **`rglob("*.md")`**（原来 `glob` 只读一层）⇒ 分片目录可读 |
| `ldv/corpus/index.py` | 同样改 `rglob`；索引 key 从**文件名**改成**相对路径**（分片后文件在子目录里）；**空目录抛 `CorpusError`**（原来静默返回空） |
| `evidence/_intake_web_stanford.py` | 加 `--max-nodes`（默认 100000，实验量级）· `--flat`（对照组）· 按度数取前 N（保度分布形状，不按 id 顺序取）· 分片写入 |
| `evidence/_probe_new_data_full.py` | 装载改走**索引**（第一次付掉、后续秒级）；加 **0 节点守卫** |

### 13.4 ★ 一次假绿（本节最该记的）

改完 `loader` 忘了改 `index.py` ⇒ 分片语料被 `glob` 读出 **0 个节点**，
而 `load_nodes_indexed` **不报错** ⇒ 探针五条判据在空语料上**全部「通过」**，
输出还写着「全过」。

⇒ 三处一起修 + 判据钉住（`test_loader_sharded` 三条）：

| 编号 | 判据 |
|---|---|
| ㊏ | **分片 == 扁平**：同一批节点，两种布局装载结果逐字相同 |
| ㊐ | **索引也读分片**：命中数 == 节点数（不再读出 0 个） |
| ㊑ | **空目录要报错**：索引路径遇到没有 `.md` 的目录 ⇒ `CorpusError` |

⚠️ 探针侧也加了「0 节点就是红」的守卫 —— **宁可红，不可静默跳过**。

### 13.5 工具层两个坑（都记在案）

1. **补丁模板漏 `+ ob`**：写 `b.replace(anchor, FUNC)` 会把**锚点那一行替掉**
   ⇒ 锚点函数消失、`main()` 里 `NameError`。正确写法恒为 `FUNC + anchor`。
2. **`_drop_test_fn.py` 会多删**（一次吃掉相邻函数）⇒ 暂停使用；
   恢复一律用 `git checkout <commit> -- <file>`（可靠兜底）。

### 13.6 实验量级的默认值（入口从此这样）

    摄入：python evidence/_intake_web_stanford.py            # 10 万节点 + 分片
    全量：python evidence/_intake_web_stanford.py --max-nodes 0   # 夜里跑，建一次索引
    测试：python evidence/_probe_new_data_full.py            # 走索引装载

⇒ 「第一次付 10 分钟建索引，之后每次几分钟」—— 这也是索引机制存在的理由。

### 13.7 十万节点的完整读数（SNAP `web-Stanford` 子集）

语料：按度数取前 **100000** 节点（保度分布形状），**1524031** 边，分片 100 桶。

| 项 | 读数 |
|---|---|
| 装载（热缓存，重读 10 万） | **64.7 s** |
| ① 谓词三段 | 候选 6｜采用 3｜超预算 3｜**拒收 0（0%）** |
| ② 组合三段 | 待命名 0｜候选 2｜拒收 2（**同量冗余 2**，第 5 次出现同一模式） |
| ③ 方向请求 | **未触发**（最长连续段 0 < N=10），且明说「查了没发现」 |
| ④ 影响分析 | 删 3 ⇒ 空 0｜缩 7｜**预测 == 实测 ✓** |
| ⑤ 索引 | 首次 19.15 s → 二次 17.96 s（**1.1×**）｜命中 100000｜**等价 ✓** |
| **总耗时** | **37 分 54 秒**（其中**建树约 30 分钟**） |

### 13.8 ★ 索引的边界（这条修正了之前的结论）

⑤ 只有 **1.1×** —— 与之前 9.3× / 93× 差了一个数量级。为什么？

    命中索引时，`load_nodes_indexed` 要**反序列化 75 MB 的索引 JSON**、
    并重建 10 万个 `Node` 对象 ⇒ 这 18 秒是**反序列化成本**，不是 IO。

⇒ **索引省的是「读盘 + 解析 front matter」，不是「构造对象」**。
   节点数越大、热缓存越热，索引的相对优势越小：

| 规模 | 场景 | 加速 |
|---|---|---|
| 36692（enron） | 冷缓存 | 9.3× |
| 58228（brightkite） | 冷启动 | **93×** |
| **100000（web-Stanford）** | **热缓存 + 75 MB 索引** | **1.1×** |

⚠️ 所以「索引让大语料能反复跑」这句话要加限定：
   **只在冷缓存/冷启动时成立**；热缓存下索引主要省的是「解析」而不是「IO」。

### 13.9 建树是 10 万节点上的主导成本

37 分 54 秒里，**约 30 分钟花在建树**（24 个键 × 10 万项递归分割），
装载只占 64.7 秒。⇒ 想跑更大的语料，**下一步要优化的是建树，不是 IO**。

### 13.10 建树优化的实际结果：A 落地、B 被自己的判据否掉（2026-10-18）

#### A（三处，纯等价）—— 已落地

| 改动 | 依据 | 结果 |
|---|---|---|
| `keyset.split` 选键改**一次 `Counter` 遍历** | O(候选×成员) → O(成员×avg_keys) | 选出的键逐字相同 |
| `all_directions()` **结果缓存** | cProfile 里 `sorted` 占 **27%** | ⚠️ 失效判据必须用 `(len, _counter)` |
| `_assemble(reuse=False)` | `deepcopy` 占 **13%**（23.9 万次） | 只给探针；生产路径必须留 |

★ **缓存失效的坑（判据当场抓到）**：第一版只在 `_new` 里清空缓存，而 `run_tests` 的
`_DeleteDir` 注入版用 `self._dirs.pop(did)` **直接删**、绕过 `_new` ⇒ 缓存读不到删除
⇒ 三条反向对照全变成「基线=0 注入=0」（空转）。改成比 `(len(_dirs), _counter)` 后，
D6 记录变成「基线 0 → **注入 78**」。

#### B（批量分配）—— **实现完成，但没接线**

`Kernel.bulk_insert()` 已实现：整棵树 `expand` 一遍（分配由 `expand` 自己做）+ 补 `_path`。

实测（CPU 时间）：

| 语料 | 逐个 insert | 批量 | 加速 | 结构 |
|---|---|---|---|---|
| `ext-coauth` 9875 | 5.64 s | **1.86 s** | **3.0×** | 相同 |
| `pypi-deps` 60 | — | — | — | 相同 |
| **默认 36 项** | — | — | — | **不同** |

★ **接进 `_assemble` 的当趟就被判据否掉**：`[P8] ⑧a 接线·等价`（走 `--locked`
与不走，追踪文本逐字相同）立刻红 —— 因为 `locked` 路径走逐个 `insert`，
非 locked 走 `bulk_insert`，而两者在默认语料上**不等价**。

⇒ **结论：`bulk_insert` 保留但不接线。** 等价性**依语料而变**（大语料等价、
小语料不等价），原因在 `_tried`（「分不开只对那次成员集成立」）——
批量版让 `expand` 看到**完整**成员集，逐个版看到**渐进**成员集。
要接，先补一条「三方向 × 多语料逐字等价」的判据。

★ 这条否掉的方式值得记：**不是「我觉得有风险所以不做」，是判据当趟红了。**

#### B 的诊断（2026-10-18 收尾）：**修不成，收益会归零**

按用户要求试了「修成渐进语义」。先诊断差在哪（`evidence/_probe_bulk_diff.py`）：

    默认语料 36 项：批量**少 76 个成员**，同时又**多出一批**成员（不是简单的「漏写」）

逐方向看是**成员错位**（D3 的 con-0001..4 跑到了别的方向，judge-0001..3 又跑回来）。

**根因**：`insert` 做了两件批量版没做的事 ——

    ① 叶上 add：`self._members[d.did].add(item_id)`
    ② **_path 合并**：`_expand_inner` 的「重试分桶」会把项追加到 `_path[item_id]`，
       而 `insert` 结尾要 `merged = path + _path[x]` 合并（覆盖会丢掉那一笔 ⇒ 幽灵成员）

⇒ 要等价，就得**复刻「逐项沿路径 + 叶 add + path 合并」** —— 那就是逐个 `insert` 本身。
   **批量的 3× 恰恰来自跳过这些步骤** ⇒ 修成等价，收益归零。

**结论：B 到此为止。** `bulk_insert` 保留在 `kernel.py`（带完整说明），**不接线**。
想再提速，方向不是「批量插入」，而是**减少方向数**或**降低 `expand` 的单次成本**
（后者 A 已做了一部分）。

### 13.11 反思层的闭环：从「只报告」到「报告 → 人拍板 → 系统真的做」（2026-10-19）

#### 缺的是什么

在这之前，`directions.json` 的 `已批准` **只被用来防重复请求**（`already_handled`）：

    系统报告「这批项分不开，需要新维度」
    人写进 `已批准`  ← 到此为止
    下一趟：**同一批项还是分不开**，而系统只是「不再问」

⇒ **开环**。人以为自己批准过就好了，实际什么都没变。

#### 闭环怎么接

`request.apply_approved(nodes, corpus_dir)`：把 `已批准` 里声明的**维度真的注入成键**。

    人写：  {"信号": "B19：…", "维度": "scope", "取值": null}
    系统：  ① 查材料里**有没有**这个字段（`source.kind` 这种点路径也认）
            ② 有 ⇒ 每个节点加一个键 `scope=<值>`（与 `keys_of` 的枚举字段同形）
            ③ 没有 ⇒ 记「**未生效**：材料里没有这个字段 —— 不假装成功」

键集变大 ⇒ `keyset.split` 的 `universe` 变大 ⇒ **方向数真的变多**。
判据 ㊜ 就是这条硬读数（不是「记账对了」，是「树真的多了一层」）。

#### ★ 红线没动

- 系统**不自己**加维度、不猜、不提优先级 —— 只执行**人写进 `已批准`** 的那一条
- 没写 `维度` 的批准条目**不算**（可能只是「同意这个诊断」，没指定用什么）
- **「未生效」必须报**：批准了但材料里没有 ⇒ 可能是字段还没摄入，也可能是写错了名字 ——
  两种情况都要人看见

#### 默认关（这是刻意的）

`cli --apply-approved` 才生效。理由：键集变大 ⇒ 方向数变多 ⇒ **所有既有读数都会变**。
默认关 = 既有基线**一个字不动**；要看闭环效果，显式开。

#### 六条判据（`test_approved_loop`）

| 编号 | 判据 |
|---|---|
| ㊚ | **没批准 ⇒ 一个字不动**（键集与方向数都不变）—— 对照组 |
| ㊘ | 批准**存在**的字段 ⇒ 真的进键集（`维度=值`） |
| ㊘b | **纯函数**：原 `nodes` 的键集一个都没变（不影响别的调用方） |
| ㊜ | **方向数真的变多** —— 「闭环有没有用」的硬读数 |
| ㊙ | 批准**不存在**的字段 ⇒ 记「未生效」，不假装成功 |
| ㊛ | `取值` 过滤生效：只给等于该值的项算数 |

#### 13.11.1 矛盾报告也走同一条通道（2026-10-19 用户裁定）

一开始我把矛盾报告判成「系统 bug 指示器 ⇒ 不该闭环」。**用户纠正**：

> 矛盾报告对应的修订方式是**增加新谓词或者请求新方向**

⇒ 三类矛盾（边打架 / 子覆盖越出父 / 孤立方向）都指向同一件事：
**当前谓词与方向切不开这批项**。所以修订动作**不是**「系统自己补子列表 / 裁成员」
（那会把 bug 掩盖成绿），而是**产出一条请求**：

    reflect.contradiction_requests(kernel)  ⇒  与 B19 请求**同构**的条目
        {"信号": "矛盾：边打架", "方向": "D17", "涉及的项": [...],
         "请求": "需要一个能把这批项归到正确位置的新谓词（或一个新方向）",
         "判据编号": "矛盾"}

⇒ 请求进 `directions.json` 的 `请求` 段，与 B19 **同一个通道**：
人拍板 ⇒ 写 `已批准` ⇒ `request.apply_approved` 真的用上。

★ 仍然**不自动改结构**：加谓词 / 加方向是**人的决定**，系统只产证据 + 执行决定。

#### 13.11.2 ★ 补上断掉的入口：请求从来没落过盘

查的时候发现：`write_requests` **只在测试里被调用**，磁盘上**从来没有 `directions.json`**。

⇒ 「报告 → 人拍板 → 系统真的做」这条链，**入口就是断的**：报告不落盘 ⇒ 人看不到 ⇒
   无从批准 ⇒ `apply_approved` 永远读不到东西。

接法：`cli --reflect --write-requests` ⇒ 把 **B19 请求 + 矛盾请求合并**写进
`<语料根>/directions.json`（`已批准` / `已拒绝` 段原样保留）。
⚠️ 只在显式给这个开关时写 —— 它会改语料目录，默认不写。
⚠️ `directions.json` 是**运行时产物**，已进 `.gitignore`。

#### 13.11.3 闭环的硬证据（实测）

在默认 36 项语料上手工写一条 `{"已批准": [{"维度": "scope"}]}`，然后对比：

    不开 --apply-approved     初始 **19** 个方向
    开   --apply-approved     初始 **47** 个方向      ← scope 进了键集 ⇒ 树真的多了一层

⇒ 这不是「账记对了」，是**结构真的变了**。判据 ㊜ 钉的就是这个方向。

### 13.12 方向函数：**当前版**（2026-10-19，**标记为可改**）

> 用户 2026-10-19 裁定：「把方向函数暂时敲定下来，标记为可改」。
> 这一节就是那一版。**它不是契约** —— 下一版很可能改，
> 改的时候要连下面「改会牵连什么」一起看。

#### 现在有三个

| 方向函数 | 根 payload | 展开出的子 payload | 一句话 |
|---|---|---|---|
| **`keyset`** | `keyset.merge([])` | `(req, forb)` 各续一个键 | 「按**键**二分」：一半要求有某键，一半要求没有 |
| **`reach`** | `frozenset(init_items)` | `frozenset(锚点)` | 「按**可达锚点**选边」：覆盖当时已知的那批项 |
| **`sequence`** | `frozenset({()})` | 带前缀的序列 | 「按**序列前缀**切」：空前缀覆盖一切 |

共同点（`EXOGENOUS_KEYS` 里那两个外生项）：

    direction_functions    当前装了哪些方向函数
    outermost_intent       最外层意图（「键集包含 —— 最外层意图不约束任何键」）

⚠️ 这两个是**外生量**：`selfopt` **不许改它们**（`EXOGENOUS_KEYS`），
`F3` 判据盯着「逐项未变」。理由：它们是**人给的**，不是系统自己的产物。

#### 为什么 `keyset` 是天然二分，不是 k 叉

方向的 payload 是「一个键要求有 / 一个键要求没有」—— **它的语义分辨率就是二分的**。
多切几刀不会让这一层更细，只会多一层。（`§I4` 改成 k 叉的实测：
`A` 的 `§K2 判空`、叶容量、各层方向数**一个数都没动** ⇒ 动到了就是改错了。）

#### 判它与材料对不对得上（一条读数，不是判据）

默认 36 项语料 vs 3 万节点网页图：

    36 项        31 个方向，叶容量 最大 10 / 平均 2.77
    3 万节点      31 个方向，叶容量 最大 12302 / 平均 1874

⇒ **方向数几乎不变，叶粗了三个数量级**。这说明：在这一版方向函数下，
   `keyset` 对这种材料的**分辨率严重不足**（材料里有差异，但键抓不到）——
   正是 `direction_requests` 该报的场景。

#### 「改会牵连什么」（要改先看这几条）

1. `batch_kernel(which, …)` 按**插件**建整棵方向树 ⇒ 加一个方向函数，
   `run_checks` 的 `(cli)` 组会多几条路径（现在 24 条）
2. `B13` / `§I4` / `§K2` 这些判据全都按「方向图」说话，新函数要能过它们
3. `ENUM_FIELDS` / `keys_of` 只管 `keyset` 的键形状；新函数要有自己的 payload 编解码
   （`encode` / `decode`）
4. `direction_functions` 是外生项 ⇒ 改了它，`F3` 的外生项**列表也会变**，
   基线里的外生断言要同步

### 13.14 方向请求的第二个信号：**叶容量超阈值**（2026-10-19）

三份独立数据逼出来的（§13.11.3 网页图 / §13.12 读数 / §13.13 wiki-Vote）：

| 语料 | 方向数 | 叶容量（最大/平均） | B19 报了？ |
|---|---|---|---|
| 默认 36 项 | 37 | **10 / 2.77** | 否（不该报） |
| web-Stanford-30k | 31 | **12302 / 1874** | **否（该报！）** |
| ext-wiki-vote | 37 | **3187 / 374** | **否（该报！）** |

⇒ B19 判的是「连续 N 次展开**一个项都没分开**」，可这三份都是「**每次都分开了、
分完叶还是巨大**」—— B19 看不见。**这正是不变的分辨率不足：不是切不动，是切了也白切。**

#### 实现

`request.leaf_cap_requests(kernel, cap)`：

- **只看叶**（没有子方向的方向）—— 内部方向成员多是正常的，它还要往下分
- 阈值 `LEAF_CAP = 50` 是**外生参数**（与 `DEFAULT_N` 同性质：人给的，不是学出来的），
  可按调用传 `cap=`
- 一条叶一条请求，带**涉及的项**；请求内容仍是「要一个新维度 / 新谓词」——
  **不提改算法、不提挪对象**（与 R-tree forced reinsert / CondenseTree 都无关）

#### 与死路表的关系（动手前核过）

Push 闸门命中的两条（`§1.2` OverflowTreatment / CT4 收缩父 payload）**与本改动不是同一件事**：
那两条否的是「**分裂分得不好就重新分**」和「**删成员时收缩父覆盖**」；
这里**不挪任何对象、不改任何覆盖**，只是**多一个信号**。死路表 §1.2 那条原文否的是
「把增量≡全量当正确性标准」，并顺手记「当时叶容量逐项相同」—— 那正是**当时叶容量
只被当度量**的痕迹；现在把它当**缺陷信号**用。

#### 效果（wiki-Vote 实测）

    --reflect --write-requests ⇒ 13 条：B19 0 / 矛盾 0 / **叶容量 13**

⇒ 这个语料上 B19 与矛盾**一条都不报**，新信号报 13 条 —— 正是它要填的洞。

#### 判据（`test_leaf_cap_requests`，5 条）

| 编号 | 判据 |
|---|---|
| ㊉″ | 小口径（36 项，最大叶 10）⇒ **0 条**，且**明说查了**（否则「没查」与「查了没发现」一样） |
| ㊉ | **条数对**：cap=3 时，请求条数 == 人工数的超阈值叶 |
| ㊉⁗ | **阈值是外生参数**：cap=3 比默认 50 报得多 |
| ㊉⁗b | 请求**只请新维度/新谓词**，不提改算法/挪对象 |
| ㊉′ | **真语料 wiki-vote 会触发**（最大叶 3191）—— CI 上没有 ⇒ 记跳过 |

★ ㊉′ 那段的 `except` 一开始写成 `except Exception`，把**漏 import 的 NameError**
当成了「语料不在」⇒ 判据报跳过。收窄成 **`except CorpusError`** 后才对 ——
**假的跳过比红更坏**：红会逼你修，跳过只会让你以为没事。

### 13.15 候选维度清单：把「材料里有什么可批」摆在请求旁边（2026-10-19）

#### 为什么需要

请求说「需要一个新维度」，人打开 `directions.json` 只能**自己猜**材料里有没有得批。
实测（enron / coauth / brightkite）都是「**批了也白批**」—— 因为可用字段早就用完了：

    coauth 9863 项：type 3 档 × evidence_status 3 档 = **9 个方向封顶**
    enron 36680 项：同样是 **9 个方向**，叶容量 **20172**（55% 挤在一个叶）
    brightkite 58216 项：同样 **9 个方向**，叶容量 **35884**（62%）

#### 清单长什么样（coauth 实测）

    共 10 个字段；可以当维度的 2 个（notes、scope）
      id         9875 种  → **几乎每项唯一 ⇒ 分出来等于没分**
      title      9875 种  → **几乎每项唯一**
      relations  9364 种  → **几乎每项唯一**
      notes        55 种  → **可以当维度**
      scope        55 种  → **可以当维度**

⇒ 一眼能看出「只有 notes/scope 可批」—— 而不是先猜再跑脚本查。

#### 判定是**离散四类**，不是打分

| 判定 | 规则 |
|---|---|
| 已用作键 | 在 `ENUM_FIELDS` 里，或 `source.kind` |
| **恒定 ⇒ 分不开** | 只有 1 种取值 |
| **几乎每项唯一 ⇒ 分出来等于没分** | 取值数 ≥ 项数的 90% |
| 可以当维度 | 其余 |

⚠️ **只报读数**（取值数 / 覆盖率），**不打分、不算优先级**（`docs/评估标准.md` 的「不作分」红线）。
   按取值数从大到小只是**展示顺序** —— 与 `reflect.report` 的 `展开序` 同性质（外生规则，可审计）。

⚠️ 清单**不判断「这个维度有没有新信息」** —— 那要理解内容，撞红线。
   例如 coauth 的 `notes`/`scope` 都是「出度 N / 入度 M」的派生文本，
   批了只是**把 3 档变 55 档**，信息没增加。**这一步得人看**。

#### 落在哪

`cli --reflect --write-requests` ⇒ `directions.json` 的**新一段** `候选维度`（程序生成，每次重写；
`已批准` / `已拒绝` 照旧保留）。

#### 判据（`test_candidate_dimensions`，5 条）

㊡ 恒定字段标「分不开」 · ㊢ 已用字段标「已用作键」 ·
㊣ 几乎唯一标对（`id` 每项唯一） · ㊤ **不作分**（清单里没有 评分/优先级/score/rank/权重） ·

#### 反向对照：那三条检查**能红**

`evidence/_probe_contra_reverse.py` 用**合成内核**把三类各造一个（正确内核造不出来）：

    ✓ 边打架（声明了父，但不在子列表）      矛盾数 1 → 请求 1 条
    ✓ 子覆盖越出父（子成员 3 不在父里）      矛盾数 1 → 请求 1 条

⇒ 检查本身没坏。**但正确内核永远不会触发它们**，原因在结构上：

    `_children[d.did] = tuple(k.did for k in kids)`   ← 由子方向自己声明的 parent **反推**
    `union(子的成员) ⊆ 父的成员`                      ← 由 payload 收窄（`split`）保证

⇒ **恒 0 是必然，不是「没问题」。** 它查的是**内核不变量**（防内部损坏），
   不是「材料与结构对不对得上」。

#### 真矛盾 = **切不开**，它原来挂在另一个名字下

用户 2026-10-19 的裁定是「矛盾的修订方式是**增加新谓词或者请求新方向**」——
按这个定义，**叶切不开就是矛盾**：

    一个叶里 3191 项，而每次展开都「分开」了 ⇒ 当前谓词与方向**切不开它们**
    ⇒ 修订动作与结构矛盾**完全相同**（加新维度 / 新谓词）

可它原来叫 `leaf_cap_requests`，和「矛盾」并列成两路信号 ⇒ 报告里读成
「矛盾 0 / 叶容量 13」，人看到「矛盾 0」会以为结构没问题、也没什么要批的。

#### 改法：并进同一份清单，但**分组报数**

```python
contradictions(kernel, cap=None)     # cap 给了才查第 4 类「切不开」
    → {"矛盾数": 结构 + 切不开,
       "分组": {"结构矛盾": 0, "切不开": 13},     # ★ 两类不混成一个数
       "检查项": [...], "未查": [...],            # ★ 没查的必须点名
       "覆盖读数": {...}}
```

- **阈值逻辑只有一处实现**：第 4 类直接调 `request.leaf_cap_requests`，不另造「什么叫叶」
- **`cap=None` ⇒ `未查: ["切不开（调用方没给 cap）"]`** —— 「没查」与「查了没发现」分得开
- **请求措辞按类型分**：结构矛盾要「**归到正确位置**」，切不开要「**切开这批项**」
  （修订动作相同，但**证据不同**，读的人得知道该改什么）
- `cli` 不再单独拼 `leaf_cap_requests`（同一批项报两次会虚增条数）

#### 现在的输出

    --reflect --write-requests（ext-wiki-vote）
    ⇒ 请求已写：…（13 条：B19 0 / 矛盾 13（结构 0 / 切不开 13））

#### 判据（`test_contra_merged`，4 条）

| 编号 | 判据 |
|---|---|
| ㊦ | 总数 = 结构 + 切不开；且**结构那三类与不给 `cap` 时逐条一致**（并入不许改旧读数） |
| ㊧ | 没给 `cap` ⇒ `未查` **点名**「切不开」，且 `检查项` 里没有它 |
| ㊨ | 切不开的条数与方向 == `leaf_cap_requests` 的（**同一处阈值**，不许两套口径） |
| ㊩ | 「切不开」也产请求，措辞是「**切开这批项**」而不是「归位」 |

★ 顺带记一个工具事实：`ldv/core/reflect.py` 与 `ldv/cli.py` 是 **CRLF**（不在已知漂移名单里），
补丁脚本必须**按各文件自己的行尾**构造锚点 —— 否则命中 0 次。

### 13.18 方向树的跨进程持久化：**没做**，以及为什么「同一缓存里长期用」不是产品形态（2026-10-19）

#### 现状：三层，只有中间那层是「缓存」

| 层次 | 行为 | 生命周期 |
|---|---|---|
| 每次调用（新进程） | `build(root)` + **逐项 `insert`**（`sorted(init_items)`）⇒ **全量重造** | 一个进程 |
| 同一进程内 | `_fixtures.reusable_build(tag, nodes, edges, _build)`：同 tag **且** `nodes/edges` 对象身份相同 ⇒ 返回 `deepcopy` | 一个进程（`_BUILD_CACHE` 内存字典） |
| 同一次调用内 | 流程 B 插 12 项 / B′ 删 12 项 / D 只调展开顺序 | 一次调用 |

**树上没有任何落盘**（`core/` 里没有 kernel 序列化）。落盘的只有两样：
语料索引（`corpus/index.py`，`cache_root()` 下 `<名字>-<路径哈希>.index.json`）
与视图层 `views.json`。

#### 实测：`--index` 之后，**建树成了唯一的大头**

| 语料 | 装载（`--index`） | **建树（逐项 `insert`）** |
|---|---|---|
| ext-wiki-vote（7115） | 0.6 s | **6.7 s** |
| ext-web-stanford-30k（30000） | 8.8 s | **216.6 s** |
| ext-web-stanford（100000） | 22.1 s | **3239.2 s ≈ 54 min** |

对照：不带 `--index` 时 wiki-vote 装载要 **55.2 s** ⇒ 索引把装载从「比建树贵 8 倍」
压成「可以忽略」，于是**建树暴露成瓶颈**。

#### ★★ 更要紧的是：建树**超线性**

| 项数 | 建树 | **每项成本** |
|---|---|---|
| 7 115 | 6.7 s | **0.94 ms** |
| 30 000 | 216.6 s | **7.22 ms** |
| 100 000 | 3239.2 s | **32.39 ms** |

项数涨 **14 倍**，每项成本涨 **34 倍** ⇒ 这不是「慢一点」，是**规模一上去就不可用**。
（与「叶容量随规模爆炸」是同一件事的两面：叶越粗 ⇒ 每次 `expand` 要扫的成员越多。）

⇒ 所以这条待办的性质不是「省时间」，而是：**不做跨进程快照，10 万节点级别的重复调用
在工程上就不成立**。

#### 为什么「一直在同一个进程内缓存里用」不是产品形态

1. **进程会重启** —— 缓存是内存字典，重启即归零，冷启动回到全量重造
2. **多 worker 各建一份** —— 4 个 worker 就是 4 份树、4 倍内存、4 倍建树时间
3. **内存随语料线性涨** —— 树持有全部项与成员集，10 万节点上不可能一直挂着
4. **跨语言 / 跨进程调用方拿不到** —— 树只活在 Python 进程的堆里
5. **调用之间没有一致性保证** —— 同一个 tag 命中与否取决于「这个进程之前跑过什么」，
   读数会**依赖历史**（与「连续 N 次只在会话内」同一条纪律的反面）

#### ⚠️ 与「进程内 signature 记忆化」不是一回事（别混）

死路表 §3 有一条实测：`signature` 在建造路径被调 **46,695 次**，三臂
**114.80 / 90.54（缓存开）/ 274.48（缓存关）** 秒，结构指纹逐字节相同 ⇒
**进程内缓存不是「可选加速」，是让算法成立的那一半**。

本节说的是**另一件事**：**跨进程快照**。前者省的是「同一次建造里的重复计算」，
后者省的是「下一次建造的整棵树」。前者去掉会慢 2-3 倍，后者不做则**每次都从零**。

#### 要做的话，四件缺一不可

1. **快照格式带版本号** —— 结构变了要能判「这份快照不是这个版本的树」
2. **指纹**：`nodes` 内容哈希（不是 mtime —— 见摄入那两次假绿的教训）
   + 插件名 + `holdout` / `predicates` 等**进装配的参数**
3. **对不上就重建，并如实报**（命中 / 重建 / 为什么失效）—— **不许静默复用**
4. **反向对照**：改语料里**一个字节** ⇒ 必须重建；改插件参数 ⇒ 必须重建；
   什么都没改 ⇒ 必须命中。三条都要有判据

#### 为什么现在不做

- **收益还没到瓶颈**：随仓库那份 36 项语料上建树是毫秒级；7115 项 6.7 s 也能忍。
  真到 10 万节点，问题会先撞上「`bulk_insert` 不等价」那条 —— 那条修好才是更大的收益。
- **代价不对称**：快照做错 = **拿旧树算新语料**，读数全对、结论全错，
  正是 `docs/外生声明标准.md` §6.5 里 A2 / E2 要防的形状。
- **所以它进「已知的未做」，而不是「已实现但默认关」** —— 后者会让人以为能开。

### 13.19 方向树落盘：**已做，默认关**（2026-10-19 `cli --snapshot`）

用户 2026-10-19：「但是这是可接受的吧，把落盘功能做成可选项」⇒ 做了。

#### 代价（为什么值得做）

每次调用都全量重造，而建树**超线性**：

| 项数 | 建树 | 每项成本 |
|---|---|---|
| 7 115 | 6.7 s | 0.94 ms |
| 30 000 | 216.6 s | 7.22 ms |
| 100 000 | 3239.2 s | 32.39 ms |

#### 收益（30k 实测，两次独立调用）

    第 1 趟  [树快照] 新建｜建树 194.504s（还没有快照）
    第 2 趟  [树快照] 命中
            初始：31 个方向（§K2 判空 16），装进 29988 项，事件 62 条 ← 逐字相同

单独测恢复本身：**装载 3.0 s｜算指纹 0.4 s｜恢复 0.4 s｜命中｜31 个方向｜账本 62 条**
⇒ 建树 194.5 s → 恢复 0.4 s，**≈ 486×**。

#### 存什么、不存什么

存：方向（`did/rank/payload(plugin.encode)/witness/origin/parent`）、子表、成员表、
`_expanded`、`_tried`、`_path`、计数器、**账本事件**。
不存：`items` / `ledger` 之**外**的会话态（`_shown` / `_last_frontier` / `usage`）——
那些本来在新调用里就应当是空的。

★ payload 用插件自带的 `encode` / `decode`（§I5）—— **不另造一套格式**。
★ 写盘走 `core/view_persist.commit`（临时文件 + `os.replace`）—— 半份快照比没有更坏。

#### 指纹覆盖什么（少一样就可能用错树）

    ① 每个项的键集      ② 边      ③ 方向函数名      ④ holdout / predicates
    ⑤ 快照格式版本号

⚠️ **内容哈希，不是 mtime** —— 摄入侧两次假绿的教训：格式变了、字节数没变，
   mtime 也照样对得上。版本不符一律重建，**不猜兼容**。

#### 坏了的四种形态，全都要重建且如实报

    文件缺失 / 版本不符 / 指纹不符 / JSON 坏或 payload 解不开 / 恢复后不变量不符
    ⇒ `结果='重建'` + 具体原因；**不抛**（可选开关不许变成可用性炸弹）

恢复后自检三条内核不变量（与 `reflect.contradictions` 前两类同口径）：
父↔子对称、`union(子成员) ⊆ 父成员`、**`_path` 不变量**（破了 ⇒ 删除会留幽灵成员）。

#### ★★ 实现时被自己的实测抓到的两件事

**① 账本漏存 ⇒ 读数变了。** 第一版只存结构，恢复后「事件 N 条」从 **34 掉到 0**
—— 结构没事，但**读数变了**。账本是内核状态的一部分，不还原就不是同一棵树。
⇒ 判据 ㊒ 现在比的是「结构**含账本条数**逐字相同」。

**② 「从没有过」与「变了」必须分得开。** 指纹一变，**路径也跟着变** ⇒ 自然「找不到文件」
⇒ 第一版照实报「还没有快照」。后果：材料已经变过一次之后，每次都读成**首次**，
  人就看不到「指纹正在变化」。⇒ 同方向还有别的快照但都对不上 ⇒ 报「**重建：指纹不符**」。

#### 判据（`test_tree_snapshot`，8 条）

| 编号 | 判据 |
|---|---|
| ㊐ | `_assemble(use_snapshot=…)` **默认 `False`**（`inspect.signature` 查，不是「我记得」）|
| ㊑ | 第一次 ⇒ 新建并落盘 |
| ㊒ | 第二次 ⇒ **命中**，且结构（含账本条数）逐字相同 |
| ㊓ | 改**一个键** ⇒ 重建，且树来自新材料（不是「差不多就复用」）|
| ㊔ | `holdout` 12 → 24 ⇒ 重建 |
| ㊕ | 快照被**截断** ⇒ 重建，**不崩** |
| ㊖ | 版本不符 ⇒ 重建（老版本不猜兼容）|
| ㊗ | 命中的树照样能维护（插 12 + 删 3），终态与从零建**逐字相同** |

#### 遗留

快照**不跨版本**（版本号变 ⇒ 全量重建）；多 worker 会各写各的（同指纹同内容，
但 `commit` 的 `os.replace` 在高并发下会互相重试，见 `MEASUREMENTS` 的 v0.1.26 实测）；
`--locked` 与快照的叠加还没测（`LockedKernel` 不可深拷贝，与快照的深拷贝是两条独立路径）。

### 13.20 持续填充的热启动：快照 + **追加日志**（2026-10-20，方案 A）

#### 动机：`--snapshot` 的粒度是整棵树

`--snapshot` 存的是「**整棵树 + 一个全局内容指纹**」⇒ **加一个节点，指纹就变** ⇒
全量重建。实测（30k）每节点 ≈ 0.3 s（重写 2.56 MB + 重算全局指纹），且**随 n 线性涨**。

⇒ 分成两层：**快照写一次，之后每次 insert/remove 只 append 一行**。

#### 成本模型（30k 实测）

| 动作 | 耗时 |
|---|---|
| 打开（restore + 指纹校验） | **0.51 s** |
| 单节点 `insert`（含 append 一行） | **22.9 ms** |
| 日志体积 | **≈45 B/条**（12 条 = 541 B） |
| 关掉（`close()` 密封：算一次 after 指纹） | **0.153 s** |
| 重开（restore + 回放 12 条） | **0.91 s** |
| 对照：从零重建 | **194.5 s** |

⇒ 重开 **0.91 s vs 194.5 s ≈ 214×**；**每节点 22.9 ms 不随 n 涨**（日志是追加，快照不动）。

#### 一致性怎么守（四道闸）

    快照头：`指纹` = 那一刻**整个项集**的内容指纹
    日志头：`base`（快照指纹）· `ops`（条数）· `after`（密封时整个项集的新指纹）

    ① 快照读不出 / 版本不符 / 恢复后不变量不符 ⇒ 重建
    ② 日志头 `ops` ≠ 实际行数 ⇒ **日志不完整**（写一半崩了）⇒ 丢日志
    ③ 回放逐条校验：insert 的 id 必须在项集里、remove 的必须能摘
    ④ 回放后重算整个项集指纹，必须 == 日志头的 `after` ⇒ 对不上 = **材料变了** ⇒ 全丢、重建

★ ④ 是 O(n)（30k 约 0.15 s），但**只在打开时算一次** —— 用一次 O(n) 换掉每次插入的 O(n)。

#### ⚠️ 三条使用前提（不是缺陷，是契约）

1. **`items` 必须是「当前项集」**，不是全量语料：
   `insert` 之后要加进来，`remove` 之后要减出去（`kernel.remove` 会把它从 `items` 摘掉）。
   对不上 ⇒ 第 ④ 道闸判「材料变了」⇒ 重建（安全，但不快）。
2. **得到的是一棵增量树**，与「全量重造」**不是同一棵**（增量 ≠ 全量，已实测）。
   ⇒ 它**不能与既有基线并列比较**。
3. **不适合 `cli` 的固定实验流程**：A+B+D+B′ 里 B 插 12、B′ 删 12 ——
   **那些变更本身就是被测对象**，记进日志再回放等于重复应用。
   ⇒ 本模块是给**服务 / 持续填充**用的（调用方决定加什么）。

#### 实现时被自己抓到的三个 bug（全在「快照 / 日志」的边界上）

**① `seal()` 用 `os.replace` 重写整个文件 ⇒ 把已追加的条目全冲掉。**
   实测：4 条日志变 1 行（只剩头）。⇒ 头必须与正文**一起写**：`[头] + body`。

**② 日志文件不存在时 `resume` 没写头 ⇒ 第一条被当成头吃掉。**
   实测：12 条变 11 条，打开时报「日志不完整」。⇒ `resume` 见空/不存在就先写头。

**③ 回放顺序 + 快照的 `_members` 仍引用被删项 ⇒ `insert` 时 `KeyError`。**
   快照是**删除之前**的状态，`_members` 里还挂着后来被删的 id；而调用方传的「当前项集」
   已经不含它 ⇒ 回放 `insert` 时若触发 `expand`，内核拿一个不在 `items` 里的 id 取项。
   ⇒ `remove` 那条日志**记下键集**，打开时先补一个**桩项**，等 `remove` 回放时再摘掉。
   ★ 这个 bug 在 `cli` 里永远碰不到（B′ 是最后一步，删完不再 expand）——
      **只有在「删了还要继续加」的会话里才现形**。

#### 判据（`test_session`，6 条）

| 编号 | 判据 |
|---|---|
| ㊱ | 首次打开 ⇒ 新建并落盘，日志 0 条 |
| ㊲ | 关掉再开 ⇒ **命中 + 回放 4 条**，树（含账本条数）与关掉前**逐字相同** |
| ㊳ | 日志被截断 ⇒ **丢弃日志 + 重建**（base 已对不上当前项集），不崩 |
| ㊴ | 材料变了（多一个键）⇒ **状态作废、重建** |
| ㊵ | `commit()` ⇒ 快照换成**当前**项集指纹，日志清空 |
| ㊵′ | `commit()` 之后重开 ⇒ 命中 + **0 条回放**（压过了） |

#### 已知边界

- **日志没有上限**：`commit()` 是手动压缩（把当前状态写成新快照、清空日志）。
  自动压缩（比如 >500 条）还没做。
- **`--locked` + 会话没测**：`LockedKernel` 不可深拷贝，与快照是两条独立路径。
- **`reach` 的区域语义**：payload 是项 id 的锚点集 ⇒ 加项可能改锚点。
  本模块不按区域切，所以不受影响；但**将来若要做「区域快照」**，这条会挡路。

### 13.21 组合谓词：接线 + **共用预算** + 自动命名（2026-10-20）

#### 先修一个真问题：组合谓词**从来没被算过**

`grep "combine("` 只命中 `run_tests.py` 两处 —— **`cli` / `loader` 里一次都没有**。

⇒ 「组合谓词」在生产路径上等于不存在。不是「被挡下」，是**没算**。
文档里那句「现有 6 份语料 + 预算 3 下 `待命名` 是 0 个」，是**探针直接调 `combine()`**
得到的，**不是 CLI 产出的**。

#### 用户裁定（2026-10-20）

> 「组合谓词经过验证以后应该可以使用，而不是等命名后才可使用」
> 「共用预算，可以」

⇒ 三条改动：

1. **接线**：`_fixtures.load(predicates=True)` 里调 `combine()`，不再只活在测试里
2. **共用预算**：`choose_partition(used, combos, budget)` —— 单谓词与「复杂度 ≤ K 的组合」
   一起按**区分度**降序取前 N。**组合赢了就顶掉一个单谓词** ⇒ 总数恒 ≤ N
3. **自动命名**：键名 = `" ∧ ".join(项)`（`出度档>2 ∧ 入度档>5`）。
   `待命名`（复杂度 > K）降级为**提示**，不阻塞 —— 人想改成「活跃作者」再改

#### 实测（5 份语料，组合能不能赢预算）

| 语料 | 单谓词最高区分度 | 组合最高 | 进前 3 的组合 |
|---|---|---|---|
| 默认 36 项 | 0.444 | 0.139 | **0** |
| pypi-deps | 0.450 | 0.333 | **0** |
| snap-email-eu-mini | 0.417 | **0.492** | **1** |
| ext-bitcoin | 0.443 | **0.472** | **1** |
| ext-wiki-vote | 0.476 | 0.174 | **0** |

⇒ **是竞争，不是摆设**：2/5 上组合真的赢了。

#### ⚠️ 但**结构收益实测为 0** —— 这是本节最要紧的读数

| 语料 | 仅单谓词（方向/最大叶） | 加组合后 |
|---|---|---|
| snap-email-eu-mini | 119 / 8 | **119 / 8** |
| ext-bitcoin | 49 / 973 | **49 / 973** |

组合键**确实写进了节点**（bitcoin 1997 项）、**也确实被用作切分键**
（`入度档>8 ∧ 出度档>7` 出现在方向 payload 里）—— 但**方向数与叶容量一个都没变**。

**原因**：两项在语料上**强相关**。在一个已经满足 `出度档>7` 的节点里，
`入度档>8 ∧ 出度档>7` 与 `入度档>8` 是**同一个切分** ⇒ 组合退化成单项。

⇒ 组合谓词的价值取决于**两项是否独立**，而现有判据只挡了**同量冗余**
（`出度>0 ∧ 出度>2` —— 同一个量、后者蕴含前者），**挡不住跨量强相关**。

#### 判据（`test_combine_budget`，4 条）

| 编号 | 判据 |
|---|---|
| ㊷ | **共用预算**：进划分总数 = `min(N, 候选数)`，不是各给一份 |
| ㊸ | 组合赢了就**顶掉**一个单谓词（N 不变、成分可变） |
| ㊹ | **自动命名** = 合取表达式，且**只给交集**加键（加键数 == 满足数） |
| ㊺ | `待命名` 只是**提示**：不进键集，但被报出来 |

#### 独立性判据：两档，性质不同（2026-10-20 补）

冗余的组合**白占预算** —— 它赢了就顶掉一个真能切开的单谓词，而结构一点没变。
所以加了一道 `combination_verdict(inter, base)`：

| 档 | 条件 | 性质 | 理由文案 |
|---|---|---|---|
| **精确蕴含** | `交集 == 最小项` | **定理**（一项 ⊆ 其余项 ⇒ `A∧B ≡ A`） | 「精确蕴含（交集 == 最小项）⇒ 组合与单项等价」 |
| **近似蕴含** | `交集/最小项 ≥ 0.9` | **外生取舍**（`INDEPENDENCE_RATIO`，与 `LEAF_CAP` 同性质） | 「跨量强相关（…≥ 阈值 0.9）」 |

⚠️ 阈值**只用于拒收，不用于打分**（「不作分」红线）：输出只有「拒收 + 理由」与「留」两种。

**实测拒收（5 份语料）**：

    默认        2 条同量冗余（`入度档>0 ∧ 入度档>1` 等）
    pypi        1 条同量 + 2 条跨量（0.606 / 0.565）—— 都没到 0.9，**留**
    mini        `入度档>13 ∧ 出度档>7` **精确蕴含** ⇒ 拒收
    bitcoin     `入度档>1 ∧ 出度档>1`（0.948）、`入度档>3 ∧ 出度档>1`（0.974）⇒ **拒收**
    wiki        2 条同量冗余

⇒ 效果：bitcoin 上**两个组合候选全被拒**，预算回到 3 个单谓词 —— 而结构本来就是 49/973
（组合进来也是 49/973）。**挡掉的是白占的名额，不是结构。**

⚠️ 仍有一条落在 0.9 以下：mini 的 `入度档>8 ∧ 出度档>7`（0.843）**留着**。
   它同样没带来结构变化（119/8 → 119/8）—— 阈值是取舍，不是真理，这里如实记下。

#### 判据（`test_combine_budget` 追加 3 条）

| 编号 | 判据 |
|---|---|
| ㊻ | **精确蕴含**（交集 == 最小项）⇒ 拒收；阈值调到 0.95 时 `(9,10)` 不拒（证明两档独立） |
| ㊼ | **近似蕴含**（0.95 ≥ 0.9）⇒ 拒收；阈值 0.99 时改判「留」⇒ **阈值确实是外生参数** |
| ㊽ | 真独立的组合**不被误杀**：留下的候选**逐个重算**都必须「留」（不写恒真断言） |

### 13.22 人命名谓词：**预算外也能用**、**改名不是新增维度**、**跳过不静默**（2026-10-20）

#### 起因：查重解决不了「用不上」

用户看完查重的方案后问：「这样不还是没办法使用上新谓词吗」——**问对了**。
查重只解决「同一个划分被算两次」，不解决「人想用的谓词根本进不来」。

实测到的真 bug：

    预算内  ['入度档>0', '入度档>1', '出度档>1']
    预算外  ['出度档>0', '入度档>2']
    人命名「我想要」= [出度档>0]（预算外）⇒ 加键 **0** 项，**无任何提示**

`apply_basic` 只用 `used`（预算内那 3 个）解析定义 ⇒ 预算外的项**查不到** ⇒
`missing` 非空 ⇒ `continue` ⇒ **静默跳过**。

⇒ 口径错了：**预算管的是「自动选谁」，不是「人能声明什么」。**

#### 三条修改

**① 解析范围 = 所有推导出来的谓词**（`used + dropped`）
　`_fixtures.load` 与 `cli` 两处都改成传 `used + dropped`。
　实测：同一个「我想要 = 出度档>0」现在**加键 34 项**（之前 0）。

**② 同扩展的命名 = 改名，不是新增维度**
　若 `名` 的满足集与某个**已有派生键**完全相同 ⇒ 删旧键、加新名。
　实测（默认 36 项，`入度档>0` → `活跃`）：

        原键名  方向 41｜成员分布 [1,1,1,1,1]｜父子关系 …
        改名后  方向 41｜成员分布 [1,1,1,1,1]｜父子关系 …
        树形完全相同 = True      键数 27 → 27

　⇒ **改名不需要重构**（划分没变，只是标签换了），但**不能让同一个划分算两次**
　　（会白占预算、切出重复的方向）。

**③ 不静默**
　跳过写 `未生效`（带**缺项**），改名写 `改名`（带**被替换的键**）。
　两者都进调用方的账本，人可以看见「为什么没生效」。

#### 判据（`test_predicate_naming`，4 条）

| 编号 | 判据 |
|---|---|
| ㊾ | **预算外**的谓词也能被命名使用（加键数 == 满足数，且账本无「未生效」） |
| ㊿ | 同扩展 ⇒ **改名**：键数不变、旧键消失、账本留痕 |
| 51 | 改名**只针对派生键**：语料字段键集合前后**逐字相同** |
| 52 | 引用**不存在的项** ⇒ 记「未生效」+ 缺项，**不静默** |

#### ⚠️ 一条设计边界（没有改，但要知道）

**人命名不占预算** —— 人写的 `基础谓词` 是**无条件**加键的，不跟自动选的抢那 3 个名额。

这是刻意的：预算约束的是**系统自动选**，人的声明不该被它挡（否则「人拍板」就成了空话）。
代价是**人加得越多，维度越多，越可能加剧细化**（`B19` 连续没变细）。
⇒ 这是**人的责任**，系统只负责如实报数（方向数 / 叶容量 / B19 读数都在输出里）。

### 13.23 实验：**新增一个维度**能不能把树切细（2026-10-20）

#### 为什么做这个实验

用户 2026-10-20：「我要的就是新多一个维度，实验一下看能不能成立吧，不是去改名，而是去加名」。

前面已经量过：**改名不改划分**（同扩展 ⇒ 树形逐字相同）、**强制切分只改方向数不改叶容量**。
⇒ 唯一可能把树切细的是**真·新维度**。这次直接量。

#### 做法

取每份语料里「**已有、但没当键用**」的字段（不在 `ENUM_FIELDS`、不是 `source.kind`），
挑取值最多、且其中最平衡的那个取值，给它加键 `字段=值`，然后重建成树。

工具：`evidence/_probe_new_dimension.py`。

#### 结果（5 份语料，字段都是 `scope`）

| 语料 | 节点 | `scope` 取值数 | 取值/节点 | 方向 | 最大叶 | 叶占比 |
|---|---|---|---|---|---|---|
| pypi-deps | 60 | 32 | 53% | 17 → **27** | 17 → **12** | 28.3% → **20.0%** |
| snap-email-eu-mini | 120 | 118 | **98%** | 59 → 63 | 13 → **13** | 10.8% → 10.8% |
| ext-bitcoin | 3 783 | 415 | 11% | 33 → 37 | 1998 → **1025** | 52.8% → **27.1%** |
| ext-wiki-vote | 7 115 | 1 434 | 20% | 37 → 39 | 3191 → **2246** | 44.8% → **31.6%** |
| ext-coauth | 9 875 | 55 | 0.6% | 9 → 11 | 5569 → **3460** | 56.4% → **35.0%** |

**⇒ 成立**：除 mini 外，**最大叶全部下降**，bitcoin 上腰斩（1998 → 1025）。

#### mini 为什么不动 —— 系统早就标了

`scope` 在 mini 上有 118 个取值 / 120 个节点 = **98%**，而
`request.candidate_dimensions` 的四类判定里**早就有一条**：

    几乎唯一    取值数 ≥ 项数的 90% ⇒ 分出来等于没分（每项一个方向）

⇒ 这类字段**不是维度，是标识**。它最平衡的那个取值区分度只有 **0.017**（几乎恒定）
⇒ 切不开 ⇒ 结构一点没动。**这不是缺陷，是材料里没有可分的维度。**

#### 代价：键集爆炸

wiki-vote 上实测：

    不加维度   建树 **0.2 s**｜键 **16** 个
    加 scope   建树 **1.5 s**｜键 **1450** 个     ⇒ **慢 7.9×**

⇒ `keyset.split` 要在每个节点上给每个键算出现率 ⇒ **键数线性进成本**。
  1 434 个键的代价是 7.9 倍建树时间。取值越碎越贵。

#### 现在就能用，**不用改代码**

    # <语料根>/directions.json
    {"已批准": [{"维度": "scope", "取值": null}]}

    python -m ldv.cli --apply-approved

`取值: null` = 每个节点用它自己的取值当键（= 把整个字段当维度）；
`取值: "某个值"` = 只切一刀。

⚠️ 默认 36 项语料**一个字段都加不了** —— 能加的都在 `ENUM_FIELDS` 里
（`type` / `evidence_status`）或只有一个取值。⇒ 像「小学/中学/大学」这种维度，
**必须由人写进材料的 front matter**，系统造不出来（撞「禁止模型代填内容」那条红线）。

#### 结论（三条，按重要性）

1. **加维度是唯一能真正把树切细的路** —— 实测 5 份里 4 份叶容量下降
2. **不是所有字段都能当维度** —— 取值数 ≥ 项数 90% 的是**标识**，`candidate_dimensions` 会标
3. **代价是键集与建树时间** —— 1434 个键 ⇒ 7.9× 建树

### 13.24 `period` 小样本实验：字段名能用，**粒度有用**，但**写法不一致会静默出错**（2026-10-20）

#### 造样本

复制 `snap-email-eu-mini`（120 项）到 `_data/_sample-period-*`，往每个节点的
front matter 里插一行 `period: …`（`evidence/_make_period_sample.py`）。
原语料**不动**（`_data/*` 已 gitignore）。

#### 四个样本（基线都是 59 方向 / 最大叶 13 / 10.8%）

| 样本 | 取值分布 | 方向 | 最大叶 | 叶占比 |
|---|---|---|---|---|
| **3 学段均分** | 40 / 40 / 40 | 59 → **113** | 13 → **9** | 10.8% → **7.5%** |
| **6 学段均分** | 20 × 6 | 59 → **145** | 13 → **5** | 10.8% → **4.2%** |
| **3 学段不均** | 96 / 18 / 6 | 59 → **83** | 13 → **8** | 10.8% → **6.7%** |
| **写法不一致** | 小学 / 小学阶段 / 中学 | 59 → **113** | 13 → **9** | 10.8% → **7.5%** |

#### 四条结论

1. **字段名 `period` 直接能用** —— `{"维度": "period", "取值": null}` 批准后，
   键 `period=小学` 正常出现，账本记「已批准 1 条」。**不用改代码。**
2. **粒度越细切得越细** —— 3 段叶 9、6 段叶 5。代价是方向数 113 → 145
   （方向多了要管的东西也多）。
3. **分布不均也能用，但效果打折** —— 80/15/5 ⇒ 叶 8（均分是 9）。
   因为「大学」只有 6 项，切出来的那一支本来就小。
4. **⚠️ 写法不一致会静默出错** —— 「小学」与「小学阶段」被当成**两个学段**，
   同一批人被切成两个方向。**结构上看起来完全正常**（方向数还多了），**语义已经错了**，
   而且**没有任何报错**。

#### 因此加了一道校验

`request.apply_approved` 在批准一个维度时，扫它的取值：

    一个取值是另一个的**前缀**（`小学` / `小学阶段`）⇒ 记进账本的 `疑似重复取值`

只报这一种最典型的形状；取值 >200 不查（`scope` 那种 1434 个取值的字段不是
「少数几个学段」，O(n²) 也不划算）。

#### 判据（`test_dimension_values`，3 条）

| 编号 | 判据 |
|---|---|
| 53 | 「小学」与「小学阶段」⇒ **报**疑似重复取值（带两条取值与原因） |
| 54 | 干净取值（小学/中学/大学）⇒ **不报**（不许误报） |
| 55 | 取值 >200 ⇒ **不查**（不误报、不卡） |
