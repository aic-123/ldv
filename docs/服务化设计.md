**版本** v0.1.42 ｜ **状态**：🟢 **阶段 3.1 / 3.2 / 3.3 / 3.4 全部用真实数据验证**（2026-10-16）—— 最小壳 `serve.py` 落地
并跑通全部判据（等价 / 链路 / 隔离 / 排队 / FIFO / 备份-恢复往返 / 备份即语料 / 反向对照）。
本文件是「**若**要做」的另立设计（`并发接口设计.md` §7 阶段 3 的原定位）。

> **它是什么**：把「一个零依赖的命令行内核」变成一个「可自托管的服务」的**设计 + 流程**。
> **它不是什么**：不是部署手册（没有 IP/端口/证书细节），也不是产品规划（没有路线图日期）。
> 每一节都回答两件事：**怎么做**、**做完怎么验证**。

## §0 三条约束（用户 2026-10-16 拍板）

| # | 约束 | 含义 |
|---|---|---|
| ① | **壳可依赖、内核零依赖** | 服务壳（HTTP/限流/任务队列）可以用任何框架与库；**内核 `ldv` 包一行 import 都不许多** —— 「零第三方」这条承诺只约束内核 |
| ② | **一租户一目录** | 每个租户一个目录，现有文件树（一节点一 Markdown）**原样保留**；备份 = 拷贝目录、迁移 = 拷贝目录 |
| ③ | **结构不进排序** | 检索结果的可核验性 / 权威度**绝不进排序** —— 服务化不改变这条红线（见 §6） |

★ 约束 ① 的理由：内核是**可审计的交付物**（任何人能通读并复现），壳是**可替换的运维层**。
把两者绑在一起，要么内核被框架拖累，要么壳被零依赖绑死 —— **分开才是两条承诺都保得住的方式**。

## §1 ★ 先重裁：四件套在「面 C 存在」之后有没有落点

死路表 §1.2 有一条裁定：**「给本系统上连接池 / 限流 / 异步 / 消息队列 —— 四件都没有落点」**。
那条裁定的前提是「**面 C（对外服务）不存在**」：零第三方 + 纯内存 + 无 socket/DB/HTTP。

⇒ **做成服务，前提就变了** ⇒ 四件必须**逐件重裁**，不能沿用旧裁定。
判据是当初那四问（它池化什么 / 限什么 / 等什么 / 削什么峰），现在逐问重答：

| 件 | 旧裁定（面 C 不存在） | 重裁（面 C 存在） | 落点 | 落到哪层 |
|---|---|---|---|---|
| **连接池** | 没有连接可池 | **HTTP 层有落点，内核层仍无** —— HTTP 连接由壳的服务器/反代池化；内核依旧**没有任何连接概念** | ✅ 采纳（壳层） | 壳 |
| **限流** | 没有服务端入口，限谁的流 | **有落点** —— 有了服务端入口，按**租户**限：每租户同时最多 N 个构建任务 | ✅ 采纳 | 壳 |
| **异步非阻塞** | 纯 CPU 无 I/O 等待，包一层是净开销 | **仍无落点** —— 建树是**纯 CPU**，async 不加速 CPU；请求级并发只能靠**多进程**（GIL 下多线程不加速 CPU） | ❌ 不采纳 | — |
| **消息队列削峰** | 没有外部洪峰，写是结构性的 | **有落点，但形状不同** —— 构建是**长任务**（36 项毫秒级、82168 项分钟级）⇒ 落点是**任务队列**（提交→排队→轮询），**不是**消息总线 | ✅ 采纳（任务队列形态） | 壳 |

★ 三条要记住的：

1. **async 的「无落点」不因服务化而改变** —— 它回答的是「等什么」，内核永远不「等」（纯 CPU）。
   想并发就**多起进程**，每个进程一个内核实例（见 §2 进程模型）。
2. **MQ 的落点是「任务队列」不是「削峰」** —— 没有外部洪峰，削的是**单租户自己提交的长任务**：
   同一个租户连点三次「重建」，第三次必须等前两次（否则撞上单写者约定）。
3. **限流与任务队列在壳层合流** —— 同一个「每租户最多 N 个进行中任务」的计数，
   既限流又排队，**不写两套**。

## §2 架构

### 2.1 进程模型：每请求一个内核实例

| 选择 | 理由 |
|---|---|
| 每请求新建内核（不复用实例） | 内核**不可深拷贝**（持锁）且**构建有缓存**（`reusable_build`）—— 复用 = 把缓存与锁的生命周期绑到请求上，**收益小、泄漏面大** |
| 多进程（非多线程） | 建树是纯 CPU；GIL 下多线程**不加速**，只增加争用 ⇒ **进程数 = CPU 数**，多了也是排队 |
| 每进程独立租户目录 | 进程间**无共享状态** ⇒ 天然隔离，连进程间锁都不需要 |

⇒ 进程池的「池」= **worker 进程常驻 + 任务在进程间流转**（任务表在壳层，见 §4）。

### 2.2 数据布局：一租户一目录（现有结构原样）

```
<data-root>/
├── <tenant-a>/              ← 就是一个完整的 ldv 语料目录，与命令行用法**逐字节同构**
│   ├── nodes/*.md
│   ├── edges/*.json
│   └── spec.json
├── <tenant-b>/
└── ...
```

★ **「与命令行用法逐字节同构」是刻意选择**：租户目录就是用户在自己机器上
`git clone` 下来能跑的那棵树 ⇒ 备份/迁移/审计全部复用现成工具（`cp -r` / `git`）。

### 2.3 请求流

```
HTTP 请求
  → 壳：租户解析（路径第一段 = 租户名）
  → 壳：限流/排队（该租户进行中任务 < N ？否则排队）
  → worker 进程：load 该租户目录 → 构建内核（reusable_build）
  → 壳/worker：跑查询，产出交付物
  → （若写）worker：commit（原子替换 + 双侧重试，v0.1.25/26 已落地）
  → 响应
```

### 2.4 落盘与并发：直接复用，不重做

服务化**不新增**落盘机制，v0.1.25 / v0.1.26 的三件直接继承：

| 已有机制 | 服务场景下的角色 |
|---|---|
| `commit()`（临时文件 + `os.replace` + 双侧重试） | 落盘**唯一**入口 —— 服务里写盘仍走它，不改 |
| 单写者约定 | 由**任务队列**兑现：同一租户同时最多一个构建任务 ⇒ 该租户的写者天然唯一 |
| 读者重试 | 服务里读者 = 查询请求；持柄窗口短（一次性读入再关），重试兜底 |

⇒ **§2.4 是本设计最短的一节，这是好事**：说明并发三面（进程内 / 跨进程 / 对外）
的前两面已经在 v0.1.24–26 做完，服务化只是把「对外」那一面接上。

### 阶段 3.3 —— 限流 + 任务队列 ✅ **2026-10-16 已验证**

- **做**：`TaskTable`（**内存**版，`threading.Condition` + 每租户 running 计数 + FIFO 队列）；
  `POST /<tenant>/run` 提交（202 + task_id），`GET /tasks/<id>` 轮询
  （`queued` / `running` / `done` / `error`）。每租户同时最多 N=1 个进行中任务。
  ⚠️ 内存版只覆盖**单进程**；跨进程要落盘（升级路径，§1）。
- **判据**（★ 探针 `evidence/_probe_service_queue.py`，RC=0，留档 `evidence/_probe_service_queue.out.txt`）：
  - ⑩ **排队生效**（**确定性**，不靠抢窗口）：慢任务租户 `ext-coauth`（9875 节点，
    全流程实测 ~112 s）跑到 `running` 后，同租户再提交一个 ⇒ **必然 `queued`**
  - ⑪ **跨租户不受影响**（**单变量**：只换租户名）：A 还 running 时，另一个租户
    （`pypi-deps`，毫秒级）⇒ **立刻 `running`**
  - ⑫ **FIFO 续跑**：A 完成后排队的 B 自动开始（实测 37.3 s 后 done），最终全 done
  - **反向对照**：`TABLE.max` 改成 ∞（不限流）⇒ 同租户第二个**直接 running**（⑩ 红）；
    跑完还原 + `serve.py` 字节级还原（sha256 `967219bcd5cd`）
- ★★ **这趟验证逼出了壳的一个真 bug**：`_execute` 原来用 `contextlib.redirect_stdout`
  包住 `run_one` —— 而 `redirect_stdout` 改的是**全局** `sys.stdout`，
  **不是线程局部的** ⇒ worker 线程一进 redirect，**同进程其他线程的 print 全被劫持**
  进那个 StringIO（实测：3.1 单线程时不可见，3.3 多线程一开就现形 ——
  探针主线程的判据输出丢了一半）。修法：**删掉 redirect** —— `run_one` 内部
  **本来就不 print**（print 全在 `cli.main` 里），包它是多余的。

### 阶段 3.3″ —— 容量上限与真实消费场景（2026-10-23）

- **容量上限**（原来**没有**，`tasks` / `queues` 只增不减）：

      QUEUE_CAP_PER_TENANT = 8     ⚠️ **暂定值、未经标定**
      QUEUE_CAP_GLOBAL     = 64    ⚠️ 同上

  计数口径 = `排队 + 进行中`。撞上限 ⇒ `QueueFull` ⇒ handler 返回 **429**
  （可重试的拒绝：不是 400「你写错了」，也不是 500「我坏了」）。
  ⚠️ 这两个数由实现方先裁决 —— 要改先定刻度：「一个租户允许积压多少」
  取决于调用方的重试策略与语料规模。

- **真实消费场景判据**（`run_tests.test_service_consumption`）：用**临时租户**
  （内置 36 项复制过去）⇒ **不依赖 `_data/`，新 clone 上也能跑**：

      同步 GET     ⇒ 200 + 文本
      异步 POST ×2 ⇒ 202；1 running + 1 queued（每租户并发 1）
      轮询到 done  ⇒ 结果与同步响应**逐字相同**（㉔）
      名额占满再提交 ⇒ **429**（㉓）

  ⚠️ ㉓ 用**闸门任务**（`threading.Event`）占住名额 —— 不能靠「提交快一点」抢时间：
  36 项的活几百毫秒就完，容量判定会和「跑完了没有」抢，**测不出确定结果**
  （第一版就是这么写的，第三个提交拿到 202）。

- ★ **判据自己崩过一次**：反向对照时接线断了 ⇒ POST 返 404 文本 ⇒
  `json.loads` 抛 `JSONDecodeError` 把整条测试带走。**「判据崩了」比「判据红了」更糟**
  —— 它会吞掉后面所有判据。⇒ 非 202 不许直接解析，`_wait` 也要能接非 JSON。

  ⇒ **教训**：3.1 的单线程验证**证不了 3.3 的线程安全**；阶段判据要按**当阶段的
  并发形状**写，不能拿上一阶段的绿灯当这一阶段的证据。

### 阶段 3.4 —— 运维 ✅ **2026-10-16 已验证**

- **做**：备份 = `cp -r <tenant>`（或 `git`）；恢复 = 拷回 + 每请求重新加载
  （壳**不缓存租户目录** —— `_load_tenant` 每次读盘，所以恢复即时生效，无需重启）。
- **判据**（★ 探针 `evidence/_probe_service_ops.py`，RC=0，留档 `evidence/_probe_service_ops.out.txt`）：
  - ⑬ **备份-恢复往返**（主判据）：备份 → 破坏（删一个节点）→ 整目录拷回 →

  - ⑭ **破坏可检**（防 ⑬ 恒真）：破坏后**未恢复**跑 ⇒ 输出**必然变**。

  - ⑮ **备份即语料**（§2.2 红利的直接证据）：备份目录**换个名字当租户**跑 ⇒
    与基线逐字相同 —— 备份不需要专门格式，**目录本身就是可独立运行的语料**
- ★ 探针自带**残留清理**（`_ops-probe-*` 临时租户 finally 摘掉）——

## §9 只读查询入口（`entry.py`，2026-10-20）

> 用户 2026-10-20：「用户得到的就是**根据需求匹配的对应粗细的节点**即可，
> 本来就不是单纯的检索系统。」随后选 C：「先说横跨 N 支，再列 N 个」。

### §9.1 它和 `serve.py` 不是一件事

| | `serve.py`（§1–§6） | `entry.py`（本节） |
|---|---|---|
| 干什么 | **跑流水线**（建 / 判 / 报告） | **只读查询**：需求 → 这一带 |
| 会写吗 | 会（落盘、账本） | **不会**（不 `insert` / 不 `remove` / 不落盘） |
| 有队列吗 | 有（每租户 N=1） | 没有（一把全局锁，串行） |
| 面向 | 租户 / 运维 | 人（页面）+ AI（JSON） |

⇒ 两件事、两个文件。`entry.py` **不**复用 §1 的租户与队列 —— 那会把「只读入口」
   拖进「写路径」的并发问题里。

### §9.2 一次查询的答案 = 节点（或分叉处的几支）

```
Query(require, forbid)  ⇒  若干节点，每个带：它代表什么 / 多粗 / 往下几个方向
```

**「对应粗细」= 递归下钻，直到每一支都由单一子节点装不下**：

```
在某节点 d 上，P = 答案 ∩ d 的成员
只有一个子节点含 P 的全部  ⇒ 往下（这一支还没分叉）
≥2 个子节点各含 P 的一部分  ⇒ 在 d 切开，每支递归
没有子节点                ⇒ 这一支到底了
```

**正确性判据**：`Σ 各支「含答案」 == 答案总数`（不重不漏）。
判据 `[入口] 52` 在**内置 36 项语料**上跑全部单键 + 全部键对。

### §9.3 ⚠️ 不用 `hit` 定粗细（这条差点写错）

`keyset.hit` 只在**矛盾**时说「否」（`req ∩ q.forbid` 或 `forb ∩ q.require`），
所以根的两个子节点**几乎永远都说「是」**。第一版用「只有一个子节点说『是』就往下」，
实测：**4 条完全不同的需求给出同一对节点**。

⇒ **`hit` 是健全性的界（允许假阳，`§K8`），不是分辨率的尺。** 混用 = 让界冒充尺。

### §9.4 不做语义翻译（`§8 停止条件 4`）

「把「一段处境 → 语义」做成自动的（语义推断 / 模型）」⇒ **停**。
理由不只是红线：**用户无法复核** —— 翻译歪了，他看到的是「0 项」，
与「材料里真没有」长得一模一样。

⇒ 改用三件**确定性**的事：

| | 做法 | 判据 |
|---|---|---|
| **建议** | 键的**子串**匹配（打「出度」能匹配 `type=出度1-3`） | `[入口] 55` |
| **零结果松弛** | 0 结果时逐键试「去掉它有多少」（require / forbid 两侧） | 读数，不进退出码 |
| **示例** | 按**数据形状**挑（覆盖最多 / 最稀 / 两维交叉），**不猜用户想问什么** | `[入口] 56` |

⚠️ 建议**不能**用 `<datalist>`：它只按**开头**匹配，而键是 `type=出度1-3`，
   用户打「出度」永远匹配不到。

### §9.5 拼错的键必须拒收

`type=出度1-4`（打错一个数字）⇒ 答案 0 ⇒ 与「材料里真没有」**长得一模一样**。
⇒ `entry.py` 校验 require / forbid 里的键必须在语料里出现过，否则 `ok:false` +
   最近 3 个候选。判据 `[入口] 54`。

### §9.6 派生维度 `influence` 的落点

`influence = max(它指向的节点的入度)`，分档 `0 / 1-9 / 10-99 / ≥100`。
实测（`ext-wiki-vote`）：方向 **37 → 61**，最大叶 **3191 → 1888**。

**为什么不写回节点的 front matter**：`_data/*` 是所有语料基线的输入，
往 7115 个节点里加字段 ⇒ 键集变 ⇒ 树变 ⇒ **所有基线一起漂**。
⇒ 落在 `_data/<corpus>/derived/influence.json`，`entry.py` 启动时叠加；
   删掉文件即完全回到原状。生成器 `ldv/tools/make_influence.py`，`_meta` 带算法 /
   输入 / 复算命令 / 命名人 / 可逆说明，**不含任何模型填写的内容**。

### §9.7 三条边界（写进代码也写在这里）

1. **只读**：不 `insert` / `remove` / 落盘。
2. **单进程串行**：`query` 会写（`expand`）⇒ 一把全局锁，**不声称线程安全**。
3. **只绑 127.0.0.1**：无鉴权，**不是对外服务**。

用法：

```
python entry.py [--port 8765] [--corpus NAME] [--batch IN --out OUT]
GET  /api                       # AI 的说明书：端点 / 参数 / 返回形状 / 边界
```

## §10 两个 ldv 之间的交流协议（`ldv-msg/1`，2026-10-21）

> 用户 2026-10-21：「设计两个 ldv 系统之间的交流协议，不必将其转化成自然语言，
> 允许直接对 ldv 的输出进行解析。」裁定（同日）：**最小可用**（QUERY/RESULT）、
> **两层都留**（内容层 + 传输层）、先做**查询对等**。

### §10.1 为什么不做自然语言

ldv 的输出**本来就是结构**。翻成自然语言是**双重有损**：

    ① 丢掉「到底是哪 1888 项、哪些方向说『是』、账在哪」——
       一句话装不下一次查询的全部结构；
    ② 丢掉**可核验性** —— 对端收到一句话只能选择信或不信；
       收到结构则能**在本地自己复算**（§10.3 的 `verify_result` 就是给这个用的）。

⇒ 协议 = 现有输出的**信封化**（身份 + 指纹 + 类型）+ 接收方自检。
**不新增语义、不新增计算、不新增任何「理解」。**

### §10.2 内容层（`ldv/protocol.py`，纯数据、零依赖）

信封六键，缺一即拒收：`proto` / `type` / `from` / `fp` / `ts` / `payload`。

| 消息 | 内容 | 说明 |
|---|---|---|
| **QUERY** | `{require, forbid}` | 键约束。**没有自然语言字段，一个都没有** |
| **RESULT** | `App.query()` 的返回 + **原查询回声** + `fp` | 回声是刻意的：没有它一条 RESULT 无法自证。⚠️ 返回里含 `out_of_structure`（**超出结构 ≠ 查不到**，见 §10.2 自检 ④） |
| **ERROR** | `{ok:false, error}` | 拒收时回报，**不回声对方 payload** |

**接收方五查**（`check_envelope`，任一不过 ⇒ 拒收并给理由）：
是 dict · `proto == ldv-msg/1` · `type` 已知 · 六键齐全 · 无禁词字段。

**结果自检四条**（`verify_result`，**不依赖发送方诚信**）：

    ① `n_answer == len(answer_ids)`        谎报项数当场露馅
    ② `Σ 各支含答案 == n_answer`            不重不漏（同 `_check_partition.py`）
    ③ 每支都有 `did`                       「这一带」必须落在具体节点上
    ④ `out_of_structure=True` ⇒ 必须给 `unknown_keys`
                                           防「谎报超出结构」当逃避回答的借口

★ **④ 的理由**（2026-10-22）：`ok=False` 有两种含义 —— 「键拼错了」与「这个问题
**超出本结构的词汇**」。后者必须给出 `unknown_keys` 作**凭证**；否则回答方可以
拿「超出结构」当**逃避**的借口（键明明在词汇表里，硬说超出）。
⚠️ 这一条必须在 `ok=False` 的 `return` **之前**查 —— 第一版写在后面，
   `ok=False` 早就返回了，永远走不到（判据 `[协议] 68c` 守它）。

⇒ 传递抓不到这四条，**本地也能抓到**。这就是「结构可传」相对
「一句话可传」的全部差别。

### §10.3 两条红线（写进判据，不只写在文档里）

| # | 红线 | 判据 |
|---|---|---|
| ① | **只换结构，不换语义** —— 可以回「D27 / 1888 项 / 精确 1.0」，不许回「这些人很有影响力」（模型代填，`§8 停止条件 4`） | 协议没有自然语言字段，**形状上**不可能 |
| ② | **两个系统之间也不排序** —— 消息里出现跨系统可比的标量字段一律拒收（`E-1`/`E-2` 的协议延伸） | `[协议] 65`：嵌套禁词 ⇒ 拒收并指出路径 |

⚠️ **② 的一个实测收窄（判据当场抓到的，值得记住）**：第一版禁词含 `rank` / `order`，
结果 `App.query()` **自己的**结构字段 `nodes[].rank`（第几层）撞表 ⇒
**每一条合法 RESULT 都被拒**。原因：`rank` 在 ldv 里是**骨架**字段
（`rank(d) = 1 + rank(parent(d))`，见 `docs/形式化断言集.md` §1.2），不是排序分。
⇒ **字段名检查分不清「名字像排序」与「真是排序」** —— 这是这种方法的天花板，
如实记在 `protocol.py` 的注释里。保留的四个（`score` / `weight` / `priority` / `rating`）
都是只在评分语境出现的词；拿 ldv 结构字段伪装评分，靠字段名拦不住，
那要靠**人不发**（外生纪律），不是靠这个名字表。

### §10.4 传输层：两层都留（用户裁定）

| 层 | 入口 | 形状 |
|---|---|---|
| **文件** | `python -m ldv.protocol --in in.jsonl --out out.jsonl [--corpus NAME]` | `.jsonl` 一行一条消息 ⇒ **可 `git diff`**，最贴「文本优先」 |
| **HTTP** | `POST /api/msg`（`entry.py`） | 收一条信封回一条信封；客户端 `ldv.protocol.send_msg(url, msg)` |

两层**共用内容层**：`exchange_file` 与 `App.msg` 调同一组函数
（五查 → QUERY → 自检 → 发），差别只在「从哪读、往哪写」。
实测（2026-10-21，`ext-wiki-vote`）：`influence=1-9` 一条 QUERY
⇒ 文件层与 HTTP 层都给 **3 支**（D43 81 项 / D55 / D50），fp 回声一致。

**只处理 QUERY**（收到 RESULT ⇒ 报「对端角色可能反了」，不递归跑）。

### §10.7 对话实验：两个**不同**的 ldv（2026-10-21 实测）

留档：`evidence/_dialogue_two_ldv.py`（可重跑）。
系统 A = `ext-wiki-vote`（7115 项，20 键，fp `648a63fa7ba50ccf`）；
系统 B = `cora-labeled`（2708 项，18 键，fp `3f42b5aea8e023ef`）。
**两个系统不共享词汇、不共享结构** —— 这正是要试的。

| # | 试验 | 结果 |
|---|---|---|
| ① | A 拿**自己**的键问 B（`evidence_status=入度0`） | B 回 **「这些键在语料里不存在」+ 字符串近似建议**（`evidence_status` / `同行评审`）—— 不是 0 条，**如实说词汇不通** |
| ② | A 拿 **B 的**键问 B（`同行评审`） | RESULT：2708 项 / 7 支，verify **True** |
| ③ | B **反问** A（用 A 的键） | RESULT：4734 项 / 8 支，verify **True** —— **对等，没有主从** |
| ④ | 文件层一次三条（B 的键 / A 的键 / 坏信封） | 2 RESULT + 1 ERROR，坏的不拖垮好的 |
| ⑤ | 各问「自己世界最大的那一类」 | A：7115/7115（`source.kind=snap-wiki-Vote`）；B：2708/2708（`同行评审`） |
| ⑥ | HTTP 层 vs 文件层，同一组消息 | `answer_ids` **逐字相同**（True / True），verify 双过 |

**⑤ 的一个附带发现（值得记住）**：实验脚本挑「最大类」时没剔**恒定键**，
于是 A 的「最大类」是 `source.kind=snap-wiki-Vote` —— 它对**全部** 7115 项成立，
**零区分力**。那正是入口 facet 早就剔掉的一类（`meta.n_constant_keys`）。
⇒ 「挑一个键做实验」本身也要过「这一个键有区分力吗」那一问，
**约定和实现都会在同一个地方睡着**。

**② 的边界（必须写下来）**：difflib 给的拼写建议是**字符串近似，不是语义**。

⇒ **跨系统建议只当「可能拼错了」的提示，不许当「换成这个就对」的答案**。

### §10.8 交流记录的沉淀：缓冲区里的**一次性树**（2026-10-21）

用户三句裁定，逐条落地：

> 「把一次交换当成完成……不去评判结果正确，而是记录一次完整的交流」
> 「每段当成一次缓冲区域的新建树，使用完成就可以抛弃」
> 「抛弃机制遵守缓冲区域的规则吧，不去特意设计」

**为什么不直接插进树**（用户在 2026-10-21 早先提过，被挡）：`insert(x)` 的入参是
**项**（`x ∈ U`，要带键），而交流记录是消息列表 —— 类型不成立。合法入口是
**缓冲区**（`docs/谓词推导与反思层.md` §9）：`load_nodes()` 只读 `nodes/`，
`_staging/` 下的东西**默认不进任何结构**。

#### 目录形状（与 `_staging/nodes/` 平级，**两种默认命运分开**）

    <语料>/_staging/
    ├── nodes/              待提交候选（默认：沉淀，走既有 commit）
    ├── rejected/           拒收 + 理由（**永不淘汰** —— 审计链）
    └── exchanges/<id>/
        ├── nodes/          一次交流 = 一棵一次性树（默认：**抛弃**）
        └── rejected/       撞 id 的 + 理由（同缓冲区形状：不覆写、不静默）

#### 工具（`ldv/tools/exchange_staging.py`，四条命令）

    ingest   exchange.jsonl → exchanges/<id>/nodes/*.md（**一条消息一节点**）
    --build  LDV_CORPUS=<该目录> python entry.py   ← 零改动，find_corpus 支持路径
    abandon  显式删目录（抛弃）
    promote  移进 _staging/nodes/ → 之后走**既有** staging commit（四条判据）

#### 五条纪律（每条有出处）

1. **一条消息一节点** —— 整段一个节点会让 `type=`/`round=` 退化成常量（`§K2 判空`）。
2. **内容 = 消息原文 JSON，逐字不改** —— 工具只搬字节 + 数数字，**不生成任何内容**
   （「禁止模型代填」：记录是真实发生过的交换，不是模型写的故事）。
3. **字段全部从信封数出来**（`influence` 手法）：`type` / `who` / `fp` / `round` /
   `reply_to`；`title` 是拼接不是生成。
4. **不进正式结构** —— 既有事实；要“被看见”只能显式指向它。
5. **抛弃与沉淀是两个显式动作** —— 没有一个开关同时做两件事
   （否则又是「看起来一样、其实不同」）。

#### 抛弃机制**不特意设计**（用户裁定）

沿用缓冲区既有规则：抛弃 = 显式删目录；`status` 只报不淘汰（同
`capacity_status`）；`evict` **一行不加**（它只扫 `_staging/nodes/`，
纪律是「只碰未提交候选、按 mtime FIFO、不按访问次数」—— 一次性树照此办理即可，
没有必要为它另造一套）。

#### 实测（`evidence/_e2e_exchange_staging.py`，真语料两个系统，可重跑）

    ① 真实交流 6 条消息（A=ext-wiki-vote，B=cora-labeled，3 轮双向）
    ② ingest ⇒ 6 节点，撞 id 0
    ③ LDV_CORPUS 指向该目录 ⇒ 直接建核 6 项，type=RESULT ⇒ 3 项 / 1 支
    ④ load_nodes(<语料>/nodes) 前后不变 ⇒ 不进正式结构
    ⑤ promote ⇒ 4/6 移进暂存（判据里）⇒ 既有 commit 收
    ⑥ abandon ⇒ 删目录、无残留；不存在时报错不静默

★ **判据抓到两个真问题（都因此修正，不是放过）**：

- **㊲**：`load_nodes(corpus根)` 读到 6（一次性树进了结构）—— 根因是 `load_nodes`
  用 `rglob`（2026-10-18 为 28 万文件分片改的），而“不读 `_staging/`”那句注释的
  推理依赖**调用方传 `<语料>/nodes`**。真实链（`find_corpus`）从不传根 ⇒ 安全；
  但谁传根，谁把缓冲区**静默**读进结构。⇒ 判据改用真实用法，并把这条写进注释。
- **㊴**：`who=A` 查询被拒收 —— `who`/`round` 是**字段不是键**
  （`keys_of` 只认字段名 / `ENUM_FIELDS` / `source.kind`）。⇒ 一次性树可筛的
  维度只有 `type=` 三档；**想按“谁问的”筛，得 promote 后由人声明新维度**
  ——「沉淀是有代价的，代价是人来拍」。

★★ **第三个被抓到的问题，回归级，单独记**：`E.App(<路径>)` 会把
`LDV_CORPUS` 写进 `os.environ`（`App.__init__` 的行为）—— 判据 ㊳ 把它当语料建核后
**没有恢复** ⇒ 本函数之后的 88 条判据全部找不到语料，被 `CorpusError` 兜底
成「跳过」（实测 **748 → 660，跳过 12，而本地本应是 0 跳过**）。
⇒ 修法：判据前后 save/restore，并**验恢复**（`[缓冲] ㊴` 的消息里报「已恢复」）。
⇒ 由此立一条通用规矩：**判据不许留全局状态**——改了环境变量 / 工作目录 /
   注册表，跑完必须还原并验证；否则「判据全绿」可能只覆盖到前 660 条。

#### 判据（`[缓冲] ㉟–㊷`，8 条，CI 可跑、跑完还原并验还原）

    ㉟ 往返（4 消息 ⇒ 4 节点）｜㊱ 内容=原文（逐字段节选在内）
    ㊲ 隔离（load_nodes 前后逐字相同；语料根会读到 —— 如实记边界）
    ㊳ 可当语料建核并查｜㊴ who/round 是字段不是键 ⇒ 拒收不静默
    ㊵ promote 走既有 commit｜㊶ 跑完还原并**验**还原｜㊷ 抛弃无残留

#### ★ 验收抓到的真 bug：RESULT 自称来自提问方的结构（已修）

`build_result` 曾经从 `query_msg` 拷贝 `from` / `fp` ⇒ B 回答 A 的 RESULT，
信封写着 `from=ext-wiki-vote`、`fp=648a63fa…`（**A 的指纹**），

- **为什么旧判据看不见**：66/70 用**同语料**的两个实例 —— 两边指纹相同，
  拷贝谁的看不出来。跨结构一走协议就现形。
- **为什么是 bug 不是特性**：`fp` 的语义是「这是在**哪份结构**上跑出来的」，

  （旁证：`ERROR` 走的一直是 `frm=self.who()` —— 回答方自己；
  两条路径对同一件事给出了两种答案，其中必有一错。）
- **修法**：`build_result(query_msg, result, *, frm, fp)` 改为必传**回答方**的
  身份与指纹；两个调用方（`App.msg` / `exchange_file`）各传自己的；

- **判据**：`[协议] 72`（跨结构，CI 可跑）。
