## §1 结论（七条）

按「改不改设计」排。**前三条要改设计，后四条只是补依据。**

| # | 结论 | 影响 |
|---|---|---|
| **1** | **「空分区要不要留在树里」是一个成熟系统里的显式参数**（SP-GiST 的 `NodeShrink`），而且原文明确说它**不影响路径长度** —— 这与我们 B-4 的「数变了但结构不该变」是同一个区分 | §K2 的裁定**有先例**；但先例把它做成了**参数**，不是固定规则 |
| **2** | **「展开到多深」也是一个显式参数**（SP-GiST 的 `PathShrink`，三档），其中 **`Leaf Shrink` 逐字就是我们现在的 §K2**（「no index node will have one leaf node」），**`Tree Shrink` 逐字就是 ART 的 path compression** | 我们现在的 §K2 是**三档里的中间那档**；另外两档都有名字和实现 |
| **3** | **「分不开」应该由返回值直接说，不该编码成「两个相同的 payload」**（SP-GiST 的 `PickSplit` 返回 `Boolean`） | §I4 的签名要改：加一个显式的「还要不要继续分」 |
| **4** | **`§I4` 的「两个」是 B-tree 遗产** —— 这条判断**有直接前例**：SP-GiST 的 `PickSplit` 返回**一组** partition，扇出由 `NumberOfSpacePartitions` 定 | §10 的留白从「赌注」变成「有依据的改动」 |
| **5** | **「增量且顺序无关」是做到的**（Godin 1995 的增量格；Naor–Teague 的阈值重建） | 「历史相关性是固有的」**不成立**，只能说「当前实现的性质」 |

| **7** | **`§K8` 的不对称契约有正式框架**，而且**逐字**出现在 SP-GiST 2001 的接口文档里（`Consistent`）、GiST 的 `recheck`、GIN 的 `GIN_MAYBE`、certifying algorithms 的 witness + checker | 补引用；且 `B16` 的 checker **不满足**「checker 要比被检查的东西简单」 |

## §2 逐条对照

### 2.1 「不建这一层」—— §K2 的成熟形态，以及它被做成了参数

**声称（本项目）**：展开必须产出下层表达不出的东西，否则**不建这一层**。

**SP-GiST 原论文（Aref & Ilyas 2001）里有三个名字，其中一个就是它。**

原文把「展开到多深」做成了一个参数 `PathShrink`，三档（p.220–221）：

    Never Shrink    「Data is inserted in the node that corresponds to the maximum
                     resolution of the space. This may result in multiple recursive
                     decompositions of the space.」

    Leaf Shrink     「Data is inserted at the first available leaf node. Decomposition
                     will not depend on the maximum possible resolution. In this
                     strategy, **no index node will have one leaf node** as we decompose
                     only when there is no room for the newly inserted data item.」
                     ⇒ **逐字就是我们的 §K2**

    Tree Shrink     「The internal nodes are merged together to **eliminate all single
                     child internal nodes**. This strategy is adapted from structures
                     like the Patricia trie that aim at reducing the height of the tree
                     as much as possible.」
                     ⇒ **逐字就是 ART 的 path compression**（见 2.4）

**而「空分区要不要保留」是另一个参数 `NodeShrink`（p.221）**：

    「**NodeShrink**: This parameter determines if **empty partitions should be kept in
      the tree or not**. When NodeShrink is set to true, the resulting space partitioning
      tree is best described as a **forest**, because only the partitions that have
      subtrees are represented. When NodeShrink is set to false all the partitions are
      kept. In case of shrinking index nodes, the nodes become variable-length nodes. ...
      Note that **NodeShrink has no effect on the path length of the tree** (as opposed
      to PathShrink).」

**★ 这一段对我们的意义有三层**：

    ① 「空分区」不是「有或没有」的问题，是**参数**。同一个框架两种都支持。
       ⇒ 我们前一轮的裁定（「不建」）**有先例**，但先例的形态是**可配置**。

    ② 原文明确区分了「**表示**」（forest vs tree、变长节点）与「**路径长度**」——
       并说 NodeShrink **只动前者**。这与我们 B-4 的「**数变了但结构不该变**」
       是**同一个区分**，而且他们把它写成了参数文档里的**一句提醒**。

    ③ 它把「退化」当作**要解决的问题**，不是要接受的代价：
       「solving the problem of **long degenerate quadtrees** when the workload is
         highly skewed」（p.237，`Tree Shrink` 的动机）

**判定**：✅ 已核。**我们的 §K2 是 `PathShrink` 三档里的 `Leaf Shrink`**；
「代价落到叶容量」这件事，在 SP-GiST 里对应 `Never Shrink` 的代价，
而 `Tree Shrink` 是**已经给出的解法**。

### 2.2 「分不开」怎么交出去 —— 返回值该是布尔

**声称（本项目 §I4）**：分不开 ⇒ 返回两个**相同**的 payload，内核判 §K2 平凡 ⇒ 这个方向成为叶。
插件不抛异常 —— 抛异常会中断遍历，效果等于假阴。

**SP-GiST 的 `PickSplit` 签名（p.222）**：

    「**PickSplit(P, level, splitnodes, splitpredicates): Returns Boolean**, where P is
      a set of BucketSize+1 entries that cannot fit in a node. PickSplit defines a way of
      splitting the entries into a number of partitions equal to NumberOfSpacePartitions
      and **returns a Boolean value indicating whether further partitioning should take
      place or not**.」
    「PickSplit will return the entries of the split nodes in the output parameter
      splitnodes, which is an **array of buckets**, where each bucket contains the
      elements that should be inserted in the corresponding child node.」

**⇒ 两个差别，都值得抄**：

    ① **「还要不要继续分」是一个显式的布尔返回值**，不是「返回两个相同的东西」让内核去猜。
       我们的编码方式（相同 payload）**语义上等价但更脆**：
       它把「判定」藏进了「内容」里，而 §K2 的判空事件恰恰要求「判定」是可记账的。

    ② **partition 是一组（array），不是两个**。扇出由 `NumberOfSpacePartitions` 定。

**判定**：✅ 已核。**这是一处签名改进，有直接前例。**

⚠️ **但有一处我们与它不同，而且是刻意的**：SP-GiST 的 `PickSplit` **直接返回元素到 partition 的分配**
（`splitnodes` 里是**元素**），而我们的 §I4 **刻意不返回分配** ——
因为我们的 `§I1 命中` 允许假阳，插件给的归属**不可信**，所以归属必须由内核按 `§I3 代价` 重新算
（见设计文档 §I4 的「否则这条『必须』是空转的」）。**这个差别要写进文档，别抄错。**

### 2.3 `§I4` 的「两个」—— 直接前例

**声称（本项目 §I4）**：「两个」是 B-tree 的遗产 —— 能装下，但不是所有方向的最自然形状。
有序方向最自然的是 trie（一个节点按「下一个符号」分出 k 个）。

**SP-GiST**：扇出是设计维度之一。原文把「分解扇出」列为结构性差异 `SD2`：

    「– SD2: The decomposition fan-out (the number of partitions).」（p.217）

并在限制里点名了这个问题的**后果**：

    「Space-partitioning trees suffer from **limited fan-out**, e.g., the quadtree has
      only a fan-out of four. So, space-partitioning trees can be **skinny and long**.」（p.217）

**ART（Leis / Kemper / Neumann 2013）**：扇出**自适应**，且明确说它**不改结构**。

    「we use a **small number of node types**, each with a different fanout.
      Depending on the number of non-null children, the appropriate node type is used.
      When the capacity of a node is exhausted due to insertion, it is replaced by a
      larger node type. Correspondingly, when a node becomes underfull due to key
      removal, it is replaced by a smaller node type.」（p.4）
    「**adaptive nodes do not affect the structure (i.e., height) of the tree, only the
      sizes of the nodes.**」（p.4）
    —— 节点类型是 `Node4` / `Node16` / `Node48` / `Node256`（p.4）

**★ 三条可直接搬的工程结论**：

    ① 扇出变化**只改空间、不改高度** ⇒ 「返回一组方向」是**节点表示问题**，不是结构问题。
    ② 别要求插件给「最优 k」—— 给**一把小梯子**（4/16/48/256 那种），按成员数选。
       理由原文给了：「In order to efficiently support incremental updates, **it is too
       expensive to resize nodes after each update**」⇒ **离散化**把频繁 resize 摊掉。
    ③ 扇出**两个方向都动**（涨了换大的，掉了换小的）。我们只有涨的方向（没有删除流程）。

**判定**：✅ 已核。**§10 的 `§I4` 留白从「赌注」升级为「有依据的签名改动」。**

### 2.4 增量维护、顺序、失效、重构

这一节是四篇文献的交叉，逐条列。

#### (a) 新节点什么时候才建 —— Godin 1995

**声称（拟核）**：FCA 的增量更新算法在插入一个新对象时，若它不产生新概念，则不新建节点。

**正文**：Godin 把更新分解成**四个方面**，并给出四类节点（p.8，Table 2）：

    「The updating is decomposed into four aspects: **the X set, the X' set, the parents
      and children**.」
    类型 3「Old node non generator」的四个维度全部是 **No change**。
    新节点只在这些条件下产生：
    「These new pairs are always in the form (Y ∪ {x*}, Y' ∩ f*({x*})) for some pair
      (Y, Y') ∈ G. They **correspond to new X' sets with respect to G**.」（p.6）
    Algorithm 1 的判据（p.10）：
    「IF ¬∃ H1 ∈ C'[||int||] such that X'(H1)=Int THEN {H is a generator}」

**判定**：✅ **成立**。新节点当且仅当交集产生一个**格中还没有的 X'**。
机制上，判据在**交集**上，不在「新对象」上。

#### (b) 增量与顺序无关 —— Godin 1995

**正文（p.2）**：

    「the concept hierarchy is a lattice, not restricted to a tree hierarchy, and
      although the algorithm is incremental, **the resulting hierarchy does not depend on
      any tunable parameters, algorithm specifics, or the order in which the instances are
      acquired**.」

**判定**：✅ 已核。⇒ **「增量」与「顺序无关」不是二选一。**
（我们能不同的原因是**结构类不同**：格 vs 树，见 §5。）

#### (c) 边的删除与重连 —— Godin 1995

**正文（p.8）**：

    「This implies that **some old children may have to be removed** if the new children
      fall in between the old child and the modified pair. This is the case when the new
      pair falls between a generator and one of its parents. The result is that the edge
      from that parent to the generator (e.g., edge(#3,#8) in Figure 2) **is replaced by
      two edges**, one from the parent to the new pair ... and one from the parent to the
      generator (e.g., edge(#17,#8)).」
    Algorithm 1（p.10）里有 `eliminate edge Ha->H`。

**判定**：✅ 已核。⇒ **成熟做法会删边。我们的 `_children` 是单调的（只增不删）。**
这是第二处刻意偏差（第一处是顺序无关），要写进文档。

#### (d) 删除流程 —— Godin 1995 §3.4

**正文（p.15，§3.4 Removing instances）**：

    「Removing an instance from the lattice might also be considered for some
      applications. **This problem is much easier than adding an instance.** One simple
      method is to start from the lowest pair containing the instance to remove and to
      search upwards recursively, **verifying if the parents are still necessary**. When
      deleting a parent, **care must be taken for relinking nodes, if necessary**.」

**判定**：✅ 已核。⇒ **这正是我们 `§M2 情形③` 缺的那一环**，
而且它给了两条我们没写的判据：
    ① 「父是否仍然必要」—— 删除可能让**上层**变得多余；
    ② 「重新连接」—— 删掉一个节点要接边。

#### (e) 构建顺序必须被记录 —— Acar 2002

**正文（p.2）**：

    「It is not enough, however, to maintain only this dependency graph connecting
      readers to writers. It is also **essential to maintain an ordering on the edges**
      and keep track of which edges (reads) are within the dynamic scope of which other
      edges. We call this second relationship the **containment hierarchy**. The ordering
      among the edges enables us to **re-evaluate readers in the same order as they were
      evaluated in the initial evaluation**. The containment hierarchy enables us to
      **identify and remove edges that become obsolete**. This occurs, for example, when
      the result of a conditional inside a reader takes a different branch than the
      initial evaluation.」

**判定**：✅ 已核。⇒ 两条：

    ① **求值顺序必须记下来并重放** —— 否则增量维护没有良定义。
       这是「历史相关性」在别人的系统里**不是缺陷、而是必须记录的输入**的直接证据。
       ⇒ 我们的账本（§K4）**方向是对的**，但「重放」这一层还没做。
    ② **containment hierarchy 的用途之一是「识别并删除失效的边」** —— 同 (c)/(d)。

**另**，原文对**静态**依赖图的批评（p.2），逐字命中我们的设计：

    「A crucial difference between this previous work and ours is that the previous work
      is based on **static** dependency graphs. ... Another difference is that they don't
      have the notion of **forming the initial graph/trace by running a computation**, but
      rather assume that it is given as input (often it naturally arises from the
      application).」

⇒ 我们的「方向由使用涌现」（§2：用它本身就是在确认）**是**「by running a computation」，
   而账本就是那个 `trace`。**这条给了 §I7 记录一个明确的上位理由。**

#### (f) 增量必须等于全量 —— Acar 2002 / Godin 1995

**正文（Acar, p.1）**：

    「we formalize the change-propagation algorithm and **prove that it is correct, that
      is, the adapted output is the same as the output of a complete re-evaluation
      with the changed inputs**.」

**正文（Godin, p.1 摘要）**：

    「Results of empirical tests are given in order to compare the performance of the
      incremental algorithms to **three other batch algorithms**.」

**判定**：✅ 已核。⇒ 两篇独立文献都把「增量结果 = 全量结果」当作**正确性标准**。
**我们的实测不成立**（`C7` §3.1.3：尺度相同、指纹不同）。
⇒ 这条要么变成检查（做了重建就能进退出码），要么在文档里**明确承认**这是选择。

#### (g) **记忆化**改不改答案 —— Acar 2002 §2 末「Side Effects」

**声称（本项目）**：覆盖 oracle 是**纯**的，所以「同一个 payload 只算一遍」不改变答案。

**正文（Acar, p.12）**：

    「Also, **the memoization of the kind done by lazy languages will not affect the
      correctness of change-propagation, because the value remains the same whether it
      has been calculated or not.**」

**而且同一节紧接着给了反面**（这一点更要紧 —— 它说明「纯」是**前提**不是顺带一提）：

    「**Function Caching.** As mentioned in the related work section, it might be useful
      to add function caching to our framework. We believe this is a promising extension,
      but should note that **it is not trivial to incorporate this feature**. The problem
      is that function caching and modifiables interact in subtle ways — **function
      caching requires purely functional code**, but our framework involves side-effects
      in its implementation.」

**判定**：✅ 已核。⇒ 三条：

    ① 「值算没算都一样」是**理由**，不是同义反复：它把「去重是否改变答案」**归约**
       成「`cover` 是不是纯函数」。归约之后可以逐项验，不必论证。
    ② 「function caching requires purely functional code」⇒ **纯是前提**。
       前提必须被**检查**，不能靠读代码断言（见 4.10）。
    ③ ⚠️ Acar 说的是**增量框架里的**记忆化。我们的情形更弱：`cover` 的入参就是
       payload，闭包住的 `nodes` / `edges` / `rev` 构造后不再变 ⇒ 纯得**更直接**。
       **不要**把这条引成「增量算法的正确性定理」—— 那是 (f)，是另一件事。

#### (h) 数据装不下时：**新建节点**，还是**加宽已有节点** —— Godin 1995 / ART 2013

**这一节是 §10.2 A′ 的全部内容。** 三条独立的派生机制，答案一致。

**Godin 1995** —— 新节点的 intent 是**交**，不是并：

> These new pairs are always in the form **(Y ∪ {x\*}, Y' ∩ f\*({x\*}))** for some pair
> (Y, Y') ∈ G.
> — §3.1

而且**已存在的节点从不改 intent** —— Table 2 第 1 类「Modified node」的 `X'` 一栏
写的就是 `No change`：

> 1. **Modified node** (Y, Y') ∈ G ｜ X: **Add x\*** ｜ X': **No change** ｜ parents: No change
> — Table 2

⚠️ **唯一一次把两个 intent 并起来**在 Algorithm 1 第 8 行：

> 8. Add new pair H {becomes sup(G\*)}: **(Ø, X'(sup(G)) ∪ f({x\*}))**

它的 extent 是 **`Ø`** —— 图 2 里那个 `(Ø,{a,b,c,d,e,f,g,h,i})`，是**格底**。
⇒ **「并 intent」在 Godin 里是格底元素的构造，不是一个装数据的节点。**

**ART 2013** —— 新键装不下时**新建一个节点**，前缀取两条键的**公共前缀**：

> insert (node, key, leaf, depth)
>   15  p = checkPrefix(node, key, depth)
>   16  if p != node.prefixLen   // prefix mismatch
>   17    newNode = makeNode4()
>   18    addChild(newNode, key[depth+p], leaf)
> — 附录 A（`checkPrefix` 的定义： 「compares the compressed path of a node with the key
>   and **returns the number of equal bytes**」）

⇒ 老节点的**有效键一个字节没变** —— 新父节点拿走公共前缀，老节点保留剩下的那截。
变的只是**存储怎么分配**。**没有一处把已有节点的键加宽。**

**空间分解**（k-d tree / quadtree / SP-GiST）—— 「子区域 ⊆ 父区域」是**分解的定义**，
不是一条可以商量的性质。

⇒ **合起来**：已知的派生机制**一律收窄**；数据装不下时**一律新建节点**。
**「子 payload 加宽到父 payload」在盘上的文献里没有前例。**

⚠️ 但要分清一件事：**加宽本身不违反 §K8。** 假阳是允许的，代价记在**性能**上 ——
   所以「加宽」在**契约**这一层站得住。它撞的是**另一条**：§7.7 的进步量（`B19`）——
   覆盖永不细化 ⇒ 每一层展开的细化量都是 0 ⇒ 连续 N 次就红。
   ⇒ 代价不在**正确性**，在**「这个结构还叫不叫分层」**。

**「加宽」的前例有，但方向是反的**：

    GiST `AdjustKeys` (PR2)   父的键 := 子们的并 —— **加宽父**，自下而上
    PostgreSQL BRIN          块范围的 min/max := 覆盖页面的并 —— 同上，且**有损**
    X-tree supernode         节点**变大**，键不变 —— "only if there is no other possibility"

⇒ 三条都是**自下而上**，而且都**不改「子比父细」这个方向**。
   `§10.2 A′` 的出路 (3) 要的是**自上而下**的加宽 —— 与前例**方向相反**。

#### (i) 删除流程：四条前例给的**不是四选一**，而是「谁治哪个病」

**这一节是 §10.2 C 的全部内容。** 四份文献都在说「删了之后怎么办」，
但它们治的**不是同一个病** —— 先分开，才谈得上选。

**① 账本：删了要留痕 —— Bε-tree 的 tombstone**

> Bε-trees **delete items by inserting "tombstone messages" into the tree**. These tombstone
> messages are flushed down the tree until they reach a leaf. When a tombstone message is
> flushed to a leaf, the Bε-tree discards both the deleted item and the tombstone message.
> Thus, **a deleted item, or even entire leaf node, can continue to exist until a tombstone
> message reaches the leaf**. Because **deletes are encoded as messages, deletions are
> algorithmically very similar to insertions**.
> — §「Inserts and deletes」

> … if a query for key k finds an entry (k, v) in a leaf and a **tombstone message for k in
> the buffer of an internal node**, then the query will return **"NOT FOUND"**, since the entry
> for key k has been **logically deleted** from the tree.
> **Note that the query need not update the leaf in this case** — it will eventually be updated
> when the tombstone message is flushed to the leaf.

⇒ 三条可直接搬的形状：

    · **逻辑删除 ≠ 物理删除**（「can continue to exist」）
    · **删除编码成一条消息** ⇒ 走**与插入同一条路**（「algorithmically very similar」）
    · **查询不必更新被查的一方**（lazy）

⚠️ 第四条**不能搬**：Bε-tree 有**冲刷**（flush）—— 墓碑最终落到叶、条目才真消失。
   我们**没有冲刷** ⇒ 我们的「墓碑」是**永久**的。这一条要自己说清（见 §4.7）。

**② 结构：三条前例治三种不同的病**

| 前例 | 它治的病 | 触发条件（逐字） |
|---|---|---|
| Guttman 84 `CondenseTree` CT6 | **孤儿项无处可去** | CT3：「If N has **fewer than m entries**, delete EN from P and add N to set Q」 |
| ART 13 `Path Compression` | **单子节点冗余** | 「**removes all inner nodes that have only a single child**」 |
| SP-GiST `Tree Shrink` | 同上 | 「The internal nodes are merged together to **eliminate all single child internal nodes**」 |

**Guttman 84** —— 压掉欠满节点之后**把项重插回树**（复用 `Insert`）：

> **CT4 [Adjust covering rectangle]** If N has not been eliminated, adjust EN.I to **tightly
> contain** all entries in N.
> **CT6 [Re-insert orphaned entries]** **Re-insert all entries of nodes in set Q.** Entries
> from eliminated leaf nodes are re-inserted in tree leaves as described in Algorithm Insert,
> but **entries from higher-level nodes must be placed higher in the tree**, so that leaves of
> their dependent subtrees will be on the same level as leaves of the main tree.

★ **CT4 那一句，是我们的 `B18` 在删除路径上的对应物。**
   删除让 `∪覆盖(子)` 变小 ⇒ `覆盖(父) ⊆ ∪覆盖(子)` 会破
   ⇒ 父的覆盖**必须跟着收缩**（「Adjust all covering rectangles on the path to the root,
   **making them smaller if possible**」）。
   ⇒ 删除流程里**有一条硬要求**，不是可选的整理动作。

而它把「与兄弟合并」**逐字排除**掉了：

> … a B-tree-like approach is possible for R-trees, although **there is no adjacency in the
> B-tree sense**: an under-full node can be merged with whichever sibling will have its area
> increased least … We chose re-insertion instead for two reasons: first, it accomplishes the
> same task and is easier to implement because the Insert routine can be used. … The second
> reason is that **re-insertion incrementally retries the spatial structure of the tree, and
> prevents gradual deterioration that might occur if each entry were located permanently under
> the same parent node**.

**ART 13** —— 压单子**不是免费的**，被压掉那段带的区分信息**不能丢**：

> **Path compression** … **removes all inner nodes that have only a single child**. … Of course,
> this partial key **cannot simply be ignored**. There are two approaches to deal with it:
> • **Pessimistic**: At each inner node, a variable length (possibly empty) **partial key
>   vector** is stored. It contains **the keys of all preceding one-way nodes which have been
>   removed**. During lookup this vector is compared to the search key before proceeding to the
>   next child.
> • **Optimistic**: Only the **count** of preceding one-way nodes … is stored. Lookups just
>   **skip this number of bytes without comparing them**. Instead, when a lookup arrives at a
>   leaf its key must be compared to the search key to ensure that no "wrong turn" was taken.
>
> **Both approaches ensure that each inner node has at least two children.**

删除那一侧：

> **Delete**: The implementation of deletion is **symmetrical to insertion**. The leaf is
> removed from an inner node, which is **shrunk if necessary**. **If that node now has only one
> child, it is replaced by its child and the compressed path is adjusted.**

⇒ 两条可搬：**① 删除对称于插入**；**② 压单子 = 用孩子替代它 + 调整被压掉那段的信息**。
   而「**信息不能丢**」有**两条**成熟做法（存进父 / 到叶重验）—— 我们得**选一条**。

**③ 遍历骨架：向上递归 + 重新连接 —— Godin 1995 §3.4**

> Removing an instance from the lattice might also be considered for some applications.
> **This problem is much easier than adding an instance.** One simple method is to start from
> **the lowest pair containing the instance to remove** and to **search upwards recursively**,
> **verifying if the parents are still necessary**. When deleting a parent, **care must be taken
> for relinking nodes, if necessary**. **The number of pairs to examine is limited to pairs
> (X, X') where X' ⊆ f({x})**, x being the instance. This process will therefore be **much more
> efficient than adding an instance**.

⇒ 三条：

    · **从最低的含该项的方向起、向上递归**（遍历次序）
    · **验证父是否仍然必要** + **必要时重新连接**（两条判据）
    · ★ **工作量被限定在 `X' ⊆ f({x})` 的 pair 上** —— 这就是我们的 `Cone(x)`。
      它与 `B8`（插入路径的「变动 ⊆ Cone(x)」）是**同一个界**，只是路径不同。

⚠️ **一处必须写清的偏差**：Godin **删** pair（「When deleting a parent」），
   而 `§M2 情形③` 明写**不删**（「**标记**……—— **不删**」）。
   ⇒ 我们借的是它的**遍历骨架**，不是它的**处置动作**；处置动作借 Bε-tree 的。

**合起来：四条前例治四种病，一条都不多余**

    病                        前例                  我们要不要
    ──────────────────────────────────────────────────────────────
    账本要留痕                Bε-tree tombstone     **要**（§K4 / B9 直接要求）
    向上递归 + 重新连接        Godin §3.4            **要**（遍历骨架）
    父的覆盖要收缩             Guttman CT4           **要**（`B18` 的硬要求）
    单子节点冗余               ART / SP-GiST         **看 `§M2 情形③` 怎么落地**（下）
    与兄弟合并                 B-tree                **排除**（Guttman 逐字：no adjacency）

⚠️ **一个必须先摆出来的冲突**：「压掉单子方向」与 `§M2 情形③` 的「不删」互相顶。

    单子方向**只在删掉节点之后**才出现（ART 逐字：「If that node **now** has only one child」）
    而 `§M2 情形③` 明写**不删**
    ⇒ 若一条方向都不从树里摘掉，**就永远不会出现单子方向** ⇒ 菜单第三条**空转**

⇒ 这两条不可能同时成立，得挑一个。见 §4.7。

#### (j) ★ 「入度是否常数」—— Driscoll 1989，以及**两条边**的坑

**要答的问题**（`§10.2 D` 的前置）：方向节点的入度是不是常数？
它决定持久化能走哪条路 —— 常数 ⇒ node-copying（**O(1) 访问**），
无界 ⇒ 只能 fat node（**O(log m) 访问**）。

**正文（§2.3 的假设，p.7）**：

    「Let d be the number of pointer fields in an ephemeral node and let **p be the
      maximum number of predecessors of an ephemeral node in any one version**.
      We assume that **p is a constant**.」

**正文（§2.3，node-copying 的动作，p.6）**：

    「We must also store pointers to the new copy in **all predecessors** of the copied
      node in the newest version. If there is no space in a predecessor for such a
      pointer, the predecessor, too, must be copied.」

**正文（§6 未解决问题之四，p.29）**：

    「(iv) Find a more efficient way than the fat node method to make linked structures of
      **unbounded in-degree** persistent. **The node-copying and node-splitting methods
      completely break down in this case**; the fat node method needs only O(1) space per
      update step but increases access times by a **logarithmic factor**.」

**判定**：✅ **成立，但「入度」这句话本身不完整** —— 它取决于**把哪条边物化成指针**。

    Driscoll 的 `p` 是「一个节点**有多少前驱指针**」。
    而本设计**同时物化了同一个关系的两条边**：

        `_children[父] = (子, …)`   语义边：**父 → 子**  ⇒ 每个子方向恰好 **1** 个前驱（常数）
        `Direction.parent` / `witness`  存储边：**子 → 父**  ⇒ 「前驱」= **扇出**，不常数

    两条边**各自自洽**，所以「入度是 1」和「入度是扇出」**同时为真**。
    实测（`outputs/_probe_degree.py`，36 项语料 / 三个方向）：
    语义入度 max **1**、扇出 max **7**（`sequence`；§I4 是 k 叉）。

    ⇒ copy 一个方向要改它**所有前驱**的指针 ⇒

        按**父→子**物化 ⇒ copy 子 ⇒ 只改 **1** 个父     ⇒ 摊还 **O(1)** ✓
        按**子→父**物化 ⇒ copy 父 ⇒ 要改**扇出**个子     ⇒ **O(扇出)**，扇出不常数 ⇒ **断掉**

**⚠️ 这一条与本设计自己的措辞有冲突，必须摆出来**：`§K5` 的原文是
`rank = 1 + max(rank(父))` —— 那个 **`max` 是为 DAG 写的**（一个方向多个父），
而 `B13` 只查「无环 / 无自环 / 见证更粗」⇒ **对 DAG 照样放行**。
实测（`outputs/_probe_b13_gap.py`）：把一个子方向再挂到第二个父下面
（语义入度 1 → 2），`B13` 仍报「是」。

⇒ **前提成立与否，判据上长得一模一样** —— 这正是本仓库一直在防的那个形状。
⇒ 处置见 §4.12。

### 2.5 不对称契约 —— 有名字，有四层

#### (a) SP-GiST 2001 的 `Consistent` 文档串 —— **逐字就是我们的 §K8**

    「• **Consistent**(Entry E, Query Predicate q, level) : A Boolean function that is
      **false when (E.p ∧ q) is guaranteed unsatisfiable, and is true otherwise**. This
      method will be used by the tree search method as a **navigation guide** through the
      tree.」（p.222）

⇒ 拆开看，逐字对应：

    「false when ... guaranteed unsatisfiable」  ↔  §K8 的「假阴禁止」（false 必须是保证）
    「and is true otherwise」                    ↔  §K8 的「假阳允许」（true 不必真的满足）
    「navigation guide」                         ↔  §I1 的「否 / 未展开」用作剪枝

**这是 §K8 最强的先例** —— 它不是我们发明的措辞，是 2001 年一个已落地框架的接口文档。

#### (b) GiST 的 `recheck`（官方文档 65.2.3）

    「When the result is true, a **recheck** flag must also be returned. This indicates
      whether the predicate is **certainly true or only possibly true**. If recheck = false
      then the index has tested the predicate condition exactly, whereas if recheck = true
      the row is only a **candidate match**. ... This convention allows GiST to support
      both **lossless and lossy** index structures.」

⇒ 这就是我们的 `§K8`：**索引允许给超集**，代价是**再查一次**（recheck）。

#### (c) GIN 的三值（官方文档 65.4.3）

    「instead of Booleans in the check vector, there are **three possible values** for each
      key: `GIN_TRUE`, `GIN_FALSE` and `GIN_MAYBE`. ... the function **must return
      GIN_FALSE only if the item certainly does not match**, whether or not it contains
      the GIN_MAYBE keys.」

⇒ 这就是我们的 `§I1 命中 → 是 | 否 | 未展开`：**三值，且「否」必须是真的**。

#### (d) certifying algorithms（McConnell 等 2011）

    「A certifying algorithm is an algorithm that produces, with each output, a
      **certificate or witness** (easy-to-verify proof) that the particular output has not
      been compromised by a bug.」（p.1）
    「**A formal proof of correctness of the implementation of the certifying algorithm may
      be out of reach, however, a formal proof of the correctness of the checker may be
      feasible.**」（p.4）
    「We want to stress that it does not suffice for the checker to be a simple algorithm.
      It is equally important that **it also easy for a user to understand why w proves
      that y is a correct output** for input x.」（p.4）

**判定**：✅ 已核（且本节多挖出一条**比 Simplicity 更直接的判词**）。⇒ 四条：

    ① 我们的 `§B1–§B19` **就是** checker；「用检查代替证明」这个立场**有出处**。
    ② 「假阴禁止」的理由**不是约定**：一个「否」是「此处不存在」的断言，而断言**不存在**
       没有小见证。McConnell 把它写成**代价**（§5.8 + Lemma 5，p.32）：

       「Following the suggestion would have the undesirable consequence that
         only problems in NP∩coNP could have certifying algorithms.」

       （"restrict the length of and the computation time required to check the witness
         ... to a polynomial in the length of the input"）
       ⇒ 要求两侧见证都短，问题就被压到 NP∩coNP。**给不出见证的答案只能禁止、不能允许** ——
       `§K8` 的不对称性由见证的可检查性决定，不是约定。
    ③ **`B16` 现在不满足 Simplicity**：它按 `§I3 代价` 重算归属，**复用了内核的分配逻辑**，
       属 `false-green` 形状 3「共享盲点」。Simplicity 的正式定义在 p.22（§5.1 强认证）与
       p.24（§5.2 认证）；p.27（§5.5）把它展开成两条要「有初等证明」的蕴含式。
    ④ **§12 有一句比 Simplicity 更直接的判词**（p.77）：

       「We will also see that a checker that wants to catch errors **immediately**, must
         incur an amortized logarithmic overhead per operation. This is also the cost of
         priority queue operations. In other words, **priority queues are hard to check and
         a checker that wants to catch errors immediately must essentially implement a
         priority queue by himself.**」

      ⇒ **复用内核逻辑的 checker 不是 checker。** 这是 `B16` 的**修法方向**：
      要么让 checker 独立重实现一遍分配逻辑（贵），要么把它降级成「只报不判」的弱版本。

#### (e) ★ **checker 的运行时间** —— 有要求，但它是「Ideally」

**声称（本项目）**：`§B1–§B19` 是 checker，而覆盖族随语料**超线性**增长。

**正文（McConnell 等 2011 §6，p.32）** —— 设计 checker 时要看四个方面，逐字：

    「When designing checkers, there are several aspects that we are interested in:
     1. **Correctness:** Checkers must be correct.
     2. **Running time: Ideally, the running time of a checker is lin ear in the size of
        its input, i.e., the size of the triple (x,y,w).**
     3. **Logical complexity:** Checkers should be simple programs.
     4. **Required randomness** (see Section 10): Checkers may use randomness. Most users
        will prefer deterministic checkers over randomized checkers.
     **Correctness is the crucial issue.**」

⚠️ 第 2 条的**开头是 `Ideally`** —— 这是**理想**，不是硬要求。同一篇 §2（p.7）的另一句
同样留了余地：

    「Moreover, the checker has usually **lower asymptotic complexity** than the program」

—— `usually`（通常），不是 `must`。**而且它说的是「渐近复杂度」更低，不是「常数更小」。**

**★ 而且有**反例**，而且反例被原文当成**开放问题**而不是缺陷（Mehlhorn & Schweitzer 2010 §3，p.2）：**

    「An undirected graph is 3-connected if the removal of any two vertices does not
      disconnect it. **Linear time algorithms for this problem are known [6,10], but none
      of them are certifying. The fastest certifying algorithms have quadratic running
      time O(n²)**, see [12,9].」

以及同节末：

    「**It remains a challenge to find a linear time certifying algorithm for
      3-connectivity of graphs.**」

⇒ **「有线性算法、但 certifying 版本只能到 O(n²)」是有前例的**，而且成熟做法是
**把它记成开放问题**，不是假装修好了。

**★ certifying 程序的资源上限被写成「一个常数因子」**（Mehlhorn 2005，p.4 第 3 条）：

    「the resource consumption (time, space) of Q on x is at most **a constant factor**
      larger than the resource consumption of P.」

⇒ **常数因子的冗余是被明确许可的**；渐近的差距是另一回事。**两者不能混为一谈。**

**★ 还有一条分工原则**（Mehlhorn 2005 p.9「Cooperation of Verification and Checking」）：

    「a sorting routine working on a set S (a) must not change S and (b) must produce a
      sorted output. ... **the first property is hard to check (provably as hard as
      sorting) but usually trivial to prove**, e.g., if the sorting algorithm uses a
      swap-subroutine to exchange items. **the second property is easy to check by a
      linear scan over the output, but hard to prove** (if the sorting algorithm is
      complex).」

⇒ 一个性质**难检查但易证明**、另一个**易检查但难证明**，两者的正确出路不同：
前者靠**证明**，后者靠**检查**。

**判定**：✅ 已核（三篇正文都读过；`mehlhorn05` 的抽文有字形缺陷，见 `.prior-art/README.md`）。
⇒ 四条：

    ① 「checker 应当线性」**有出处**，但措辞是 `Ideally` ⇒ 我们把它当**方向**，不当**门槛**。
    ② **超线性有前例**（三连通性的 O(n²)），且原文把它写成开放问题
       ⇒ 我们的做法是：**把渐近问题写清楚，不声称解决**。
    ③ 常数因子的冗余（同一 payload 被反复要、同一段遍历被重复走）
       落在「一个常数因子」的许可范围内 ⇒ **可以优化，而且应当优化**。
    ④ 「难检查但易证明」的性质，出路是**证明**而不是**检查**
       ⇒ 这是「哪些硬要求只能进度量、不能进退出码」的**上位理由**（§1 硬要求表的四行，
       第三/四行就是这样：它们的 checker 与算法同阶）。

#### (f) `§K8` 的两个方向**有正式名字** —— Barr 等 2015 §2.3

**声称（本项目）**：`§K8` 的不对称契约 —— **假阳允许**（代价是性能）、**假阴禁止**（破坏正确性）。

**正文（Barr / Harman / McMinn / Shahbaz / Yoo, TSE 2015 §2.3，p.4）**：

    「**Definition 2.7 (Soundness).** The test oracle D is **sound** iff
        D(a) ⇒ G(a)
     **Definition 2.8 (Completeness).** The test oracle D is **complete** iff
        G(a) ⇒ D(a)
     While test oracles cannot, in general, be both sound and complete, we can,
     nevertheless, define and use **partially correct test oracles**.」

⇒ 逐字对应（`G` 是 ground truth）：

    sound（假阳禁止）       D 说「是」⇒ 真的「是」     ← **我们不要求这个**
    complete（假阴禁止）    「是」⇒ D 说「是」          ← **§K8 要求的是这个**

**同一篇还给了「oracle 贵」的正面陈述与出路**（§2.2 p.4；§5 p.16）：

    「**Test oracles are typically computationally expensive**, so probabilistic
      approaches to the provision of oracle information may be desirable even where a
      deterministic test oracle is possible [125].」

    「**Invariant detection can be computationally expensive**, so **incremental** [22],
      [171] and light weight static analyses [39], [63] have been brought to bear.」

**判定**：✅ 已核。⇒ 三条：

    ① `§K8` 不是我们发明的措辞：**soundness / completeness** 是测试文献的标准定义，
       而「一般做不到两者兼得，所以用**部分正确**的 oracle」正是我们的立场。
    ② 「oracle 通常计算昂贵」是**领域共识**（不是我们的实现没写好）。
    ③ 出路给的是 **incremental**（增量）—— 与 §2.4(f)/(g) 指向同一个方向。

### 2.6 结构不能泄露历史 —— Naor & Teague 2001

    「data structures that are **history independent**, i.e. it is impossible to deduce
      from the memory representation of the data structure any information not revealed by
      its current state」（p.1）
    「This problem was **first explicitly considered by Micciancio [13]** who showed a
      variant of **2-3 trees** with this property.」（p.1）
    Definition 2.1（p.3）：「A data structure implementation is history independent if any
      two sequences S1 and S2 that yield the same content **induce the same distribution on
      the memory representation**.」
    Definition 2.2（p.3）：强版本 —— 在**多个时间点**取内存快照也要不可区分。
    手法（p.3）：「One is to ensure that **the representation of the structure is
      determined by its current content**」
    规模阈值重建的代价（p.11）：
      「Lemma 18 ... costs **expected amortized time O(1)** per insertion or deletion.」
      「Lemma 19 The expected amortized time spent on top-level rehashing due to |S|
        reaching any of the ρi ... is **O(1) per insertion and deletion**.」

**★ 还有一条与我们直接相关的开放问题（p.14）**：

    「It is interesting to note that **all the strongly history independent data structures
      we have found have the property that each data structure content (in the sense
      defined in section 2) has a unique representation**. We would be interested to know
      whether **unique representation is necessary for strong history independence**.」

⇒ **我们的树没有唯一表示**（分批维护 ≠ 一次建完，`C7` §3.1.3）。
   所以我们是**主动放弃**了 history independence。

⚠️ **但动机不同，别把结论搬错**：Naor–Teague 的动机是**隐私**（对手能从内存镜像反推操作序列）；
   我们的动机是**可复现性**（同一批数据两次建，树形该不该一样）。
   **手法可借**（规模阈值重建），**安全结论不适用**（我们没有对手）。

⇒ 我们能做的是：**把顺序显式记进账本（不藏）**，并规定**树本身不作为顺序的证据**。
   这是「主动放弃 + 显式化」，与 Naor–Teague 的「隐藏」是**不同**的立场。

## §4 翻译成工程需要

**每条都写成「改哪里 + 判据 + 怎么验证能红」。** 这是本文的主要产出。

### 4.1 `§I4` 的签名：加一个显式的布尔 + 允许一组

> ✅ **已落地**（`ldv/C10-签名改动复核.md`）。实际取的不是「再加一个布尔返回值」，
> 而是把「分不开」编码成 **`None`** —— 一样是**显式判定**，但不必扩成二元组：
>
>     `劈开(父方向, 一组项) → None | 一组方向（≥2 个）`
>
> **父方向**也递进去了（见 §4.1 的 ⚠️ 与设计文档 §I4）：子方向要成为父的**可证细化**，
> 不能靠从项里重新猜。实测 A 的覆盖嵌套 14 次越界 → **0**，假阳率 56.7% → 49.4%。
> ⚠️ **少给（< 2）判违约**，不静默当成分不开 —— 否则「插件的判定」与
> 「候选切不动」又会长得一样。

    改：`劈开(一组项) → 两个方向`
    为：`劈开(父方向, 一组项) → None | 一组方向（≥2 个）`

    判据：返回 `None` ⟺ 插件**声明**分不开；非 `None` 时必须 ≥2 个且构成划分
    验证能红：让一个插件返回**只有 1 个**方向 ⇒ `PluginContractError`（不是「分不开」）；
              另有一条注入验「子方向把父的 `forb` 丢了」⇒ 覆盖嵌套越界（0 → 14 次）

    ⚠️ 别抄错：SP-GiST 的 PickSplit **返回元素到 partition 的分配**；我们**不返回分配**
       （因为 §I1 允许假阳，插件给的归属不可信）。这条差别要留在文档里。

### 4.2 扇出：一把小梯子，不是任意 k

> ✅ **已落地**（`C10` §2）。实测：C 从 **21 方向 / 7 层 → 16 / 5**，
> 叶容量（10）与假阳率（0.0%）**一个数没动**；A / B 的方向数 · 层数 · 扇出 · 叶容量
> **一个数没动**（反向判据）。
> ⚠️ 但 ART 的「扇出只改空间、不改高度」在 C 上**不成立**（7 层 → 5 层）——
> ART 的节点是**定长**的（同批键、按占用选节点类型），我们的 `劈开` 是**按需**的、
> **一次定形**的（§K2）⇒ 扇出大 ⇒ 一次把符号分完 ⇒ **少一层**。

    改：`§I4` 的返回值从「两个」放宽到「一组」，但**不要求插件给最优 k**
    为：内核按成员数在一把梯子上选（起点：1 / 2 / 4 / 8）

    依据：ART「it is too expensive to resize nodes after each update」
          ⇒ 离散化把 resize 摊掉；且「adaptive nodes do not affect the structure」
          ⇒ **只改空间，不改高度**，所以这一步**不动遍历**。
    验证能红：构造一个「成员数 5 却选了 k=1」的分配 ⇒ 应红（叶容量暴涨）

### 4.3 惰性展开的**两半**

    ART 需要**两个**机制才能维持「每个内节点 ≥ 2 个子」：
        建的时候：lazy expansion（只在需要区分至少两个叶时才建）
        维护的时候：path compression（删掉只有一个子节点的内节点）
    —— 因为**删除会造出单子节点**。

    我们现在只有**前半**（§K2 是建的时候判的）。
    ⇒ 加删除流程时，必须同时加后半。

    验证能红：建一棵树，删掉一个成员使某方向只剩一个孩子
              ⇒ 若不压缩，会出现「有子层但只有一个孩子」的方向 ⇒ 应红

    怎么升级成判据：做了 4.6 的重建之后，若同构，就能进退出码。

### 4.6 「规模阈值重建」作为可选策略

    加：`|items|` 每翻一倍整体重建一次（阈值策略，不是随机 —— 我们没有对手）
    依据：Naor–Teague 的 Lemma 18/19（摊还 O(1)）
    代价：一次重建 = 一次 `build()`，摊到每次插入是常数
    验证：重建后与「一次建完」**是否同构** ⇒ 这就是 4.5 的升级判据

### 4.7 ★ 删除流程（§M2 情形③）：先定「不删」管的是账本还是结构

**前提**：§2.4(i) 的四条前例。

#### 要定的那一条

`§M2 情形③` 的「**不删**」，管的是**账本**，还是**结构**？两个读法互斥，
而且**决定了菜单里还剩几条**：

| 读法 | 含义 | 菜单还剩 | 前例 |
|---|---|---|---|
| **甲（推荐）** | 「不删」**同时管住结构**：方向不从树里摘掉 | **只剩 CT4（收缩父覆盖）** | Bε-tree「can continue to exist」 |
| 乙 | 「不删」只管账本，结构上可以摘 | 三条都在 | Godin「When deleting a parent」 |

**推荐甲**，三条理由：

    ① `§M2 情形③` 的理由句是「「这个方向不再被强制」和「这个方向从来没存在过」
       必须分得开」—— 而**分得开**靠的是**方向还在**（`_dirs` 里查得到 + 账本有记录）。
       把方向从树里摘掉，这两条历史就**合并**了 ⇒ `§K4` / `B9` 直接破。
    ② Bε-tree 逐字给了「逻辑已删、物理还在」的成熟形状，且**查询不必更新叶**。
    ③ 乙会让 `_children` 不再单调 —— 那是 §2.4(c) 记的第二处**刻意偏差**。
       能不动就不动。

**甲之下，菜单三条的裁决**（一条都不剩，且各有逐字依据）：

| 办法 | 裁决 | 依据 |
|---|---|---|
| 把项重插回树（Guttman CT6） | **不发生** | CT6 的前提是 CT3 压掉了节点；甲不压 ⇒ **没有孤儿** |
| 与兄弟合并（B-tree） | **排除** | Guttman 逐字：`there is no adjacency in the B-tree sense` |
| 压掉单子方向（ART / SP-GiST） | **不发生** | 单子只在**删掉节点之后**出现（ART 逐字「**now** has only one child」）；甲不删 ⇒ 不产生单子 |

⇒ **甲之下，删除流程只做三件事**，一件都不多：

    ① 把 `x` 从 `items` 与 `members(D)`（`D ∈ Cone(x)`）里去掉
    ② 对 `x ∈ witness(D)` 的方向追加一条**失效事件**（账本只增不改 —— `B9`）
    ③ **向上收缩父的 payload** —— Guttman CT4 的对应，**硬要求**，不是整理

#### ⚠️ 第 ③ 件为什么会破 `B18`

`覆盖(父) ⊆ ∪覆盖(子)`。删掉 `x` 后 `members` 变小；若 `payload` 跟着收窄，
`∪覆盖(子)` 就变小 ⇒ **父的 payload 不跟着收窄就红**。

⇒ 收缩**有下界**：不许收到 `members(父)` 之外，否则 `members(父) ⊆ 覆盖(父)`（`B16`）破。
⇒ **收缩被两条判据双向夹住**：`B16` 给下界、`B18` 给上界。

#### ⚠️ 一处必须单独写：**失效的方向还能不能答查询？**

**能，而且必须能。**

    若「失效」被实现成「不参与检索」⇒ 它的成员还在语料里、查询可能命中
    ⇒ 那一条就变成**假阴** ⇒ §K8 的**唯一**禁令被破

⇒ **标记只影响账本，不影响 `命中`。** 不写这一条，实现的人几乎一定会写成
「把失效方向跳过」—— 那看起来像「删除生效了」，实际是造了一个假阴。

#### 与前例的两处偏差（要写进文档）

    ① **没有冲刷。** Bε-tree 的墓碑最终落到叶、条目真的消失；我们**没有冲刷**
       ⇒ 墓碑**永久** ⇒ 「失效」只增不减。代价：账本单调增长。
       这与 `§K4` 的「只增不改」一致，**但要明说**。
    ② **`§I4` 的 `None` 在删除路径上「不适用」，不是「同义」。**
       删除路径**不调 `劈开`** —— 三件处置里没有一件需要重新划分：
         · 标记   不碰结构
         · 收缩   payload 变**小**，不是重新划分
         · 重插   若将来启用，走的是 `插入`，那里的 `None` 仍是「分不出」
       ⇒ `§10.2 C` 里那条「口径要先定」的问题**消失**（不是「相同」，是「不适用」）。
       要写进文档，否则下一个人会以为漏了。

#### 要配的检查（六条，都跑在**删除路径**上，每条都能红）

    D1  空方向必须带失效记录
        `members(d) == ∅` ⇒ 该方向必须有一条「已失效」账目
        能红：造一个空方向而不记账

    D2  删除后 `覆盖(父) ⊆ ∪覆盖(子)` 仍成立          ← `B18` 的删除路径版本
        能红：删掉一个成员后不收缩父 payload

    D3  删除后 `members(父) ⊆ 覆盖(父)` 仍成立         ← `B16` 的删除路径版本
        能红：收缩过头

    D4  变动集合 ⊆ `Cone(x)`                          ← `B8` 的删除路径版本
        依据：Godin「limited to pairs (X, X') where X' ⊆ f({x})」
        能红：删除动了 `Cone(x)` 之外的方向

    D5  账本只增不改                                  ← `B9` 的删除路径版本
        能红：删除时改写历史记录

    D6  「已失效」与「从来没存在过」分得开            ← `§K4`，**本节的重点**
        能红：把失效方向从 `_dirs` 里摘掉 ⇒ 两条历史合并

⚠️ **D2 / D3 是「同一族判据跑在第二条路径上」**，与 §10.2 B 那次
（`B16` 只跑批建、没跑维护）是**同一个教训**：一条硬要求写在 §7 的表里、
是绿的，**不等于它跑在了会出问题的那条路上**。

⚠️ **本节原来的那条「验证能红」是错的**（已删）：

    原文写「删掉使某方向变空的最后一个成员 ⇒ 若不删该方向，`members(d) ≠ ∅` 应红」
    —— 而甲之下**就是要不删** ⇒ 这条判据在**正确实现上也会红**。
    ⇒ 基线就红的判据过不了注入验证。改成 D1（**空方向必须带失效记录**）。

#### 不声称的

    · 不声称删除**顺序无关**。Godin 的增量顺序无关，我们的不是（已知偏差）。
      「先删后加」与「先加后删」是否同构 ⇒ **要量**，不是要断言。
    · 不声称删除是 O(1)。「much easier than adding」是**相对**说法。
    · 不声称甲之下 `_children` 永远单调 —— 只声称**本流程不删边**。

### 4.8 `B16` 的 checker 要重写

    改：`B16`（members ⊆ 覆盖）现在按 `§I3 代价` 重算归属 —— 复用了内核逻辑
    为：**独立**的检查器（不复用内核的分配代码）
    依据：McConnell 等 2011 p.4 ——「it does not suffice for the checker to be a simple
          algorithm」且 checker 必须**能被第三方看懂为什么它证明了结论**；
          Simplicity 的正式定义在 p.22/§5.1、p.24/§5.2、p.27/§5.5；
          p.77 还有更硬的判词：「a checker that wants to catch errors immediately must
          essentially implement a priority queue by himself」

    为什么这是真缺陷：复用内核逻辑 ⇒ 内核的分配 bug 会**同时**让 checker 通过
                      ⇒ `false-green` 形状 3「共享盲点」

### 4.9 「进步量守卫」

    加：插件声称能分、却连续 N 次没让 payload 更细 ⇒ 红
    依据：SP-GiST「the SP-GiST core will raise an error if the leaf datum does not
          become any smaller within **ten cycles**」
    注意：这与 §K2 判空是**两条不同的检查** ——
          一条判「这次分不开」，一条判「反复声称却分不出东西」

### 4.10 ★ 检查层的超线性：**拆成「常数因子」与「渐近」两件事**

    **要做的**（有依据、能验收）
      ① 覆盖 oracle 按 **payload 的规范形**去重
         —— 同一个 payload 在覆盖族里被反复要（实测 3907 项 / reach：39650 次调用
            ⇒ 只有 7818 个不同 payload，约 **5.1 倍**），去重是**纯**函数的直接后果
      ② `reach` 的单次调用改走**反向**闭包
         —— 覆盖的定义就是 `∪_{a ∈ payload} rev[a]`，按锚点逐个并，
            不必逐项扫一遍 `fwd[x] & anchors`
      ③ `run_one` 里 `leak_obs` 的**重复计算**去掉（同一份 profile 算了两遍）

    **买到了什么**（3907 项 / reach，`ldv/MEASUREMENTS.md` 结果七）
      覆盖族整族（四条块 × 两条路径）   49.71 s → **0.69 s**（×72.4）
      其中 oracle 自己                   49.65 s → **0.63 s**
      臂 0 vs 臂 1 逐项比对             39650 次调用，不同 **0** 处
      ⚠️ 同一次审计还拆出一个**读数缺陷**：原先那句「一块 cover 度量 115.8 s」
         的计时块里**含内核重建**（96%），真正的 profile 只有 0.45 s。
         ⇒ **含建造的读数不能按块相乘。**

    **依据**
      常数因子的冗余       Mehlhorn 2005 p.4 第 3 条：「at most **a constant factor**
                           larger than the resource consumption of P」
      去重不改答案         Acar §2 末 p.12：「the value remains the same whether it has
                           been calculated or not」
      **前提是纯**         Acar 同页：「function caching requires purely functional code」
      oracle 贵有出路     Barr 等 §5 p.16：「**incremental** ... have been brought to bear」

    **不声称的**（写清楚，别把常数因子说成渐近）
      渐近问题**没解决**。McConnell §6 第 2 条是 `Ideally`；Mehlhorn 2010 §3 的
      三连通性就是「线性算法有、certifying 只能 O(n²)」的先例，原文把它记成
      「remains a challenge」。⇒ **本项目的渐近缺口照实写进文档，不当成已修。**

    **必须配的检查**（前提不许靠读代码断言）
      ① 生产 oracle 与**参考实现**（改动前逐字：正向闭包、不去重）逐项相同
      ② `dedup=True` 与 `dedup=False` 逐项相同
      ③ 注入「键取错（按 `len`）」⇒ ①② 必须对不上
      ④ 去重**确实在发生**（命中 > 0）—— 度量，不进退出码
      ⑤ ⚠️ **对照的顺序**：必须先算参考值，再让每个臂各跑一遍 ——
         否则「证明非空转」的那一步会把缓存烤热，**变异被掩盖**（实测踩过）

    **为什么键不能取 `did`**
      `did = f"D{内核计数器}"`，**每个内核各自从 0 开始** ⇒ 批建内核的 `D3` 与维护
      内核的 `D3` 是**两个不同的方向**。按 `did` 去重会把两份覆盖**串台**
      ⇒ 判据拿错的覆盖去比 ⇒ **假绿**。所以键取 `coverage_of` 本来就要做的那一步
      规范化 —— **不引入新假设**，也因此跨内核共享是**定义上**成立的。

    **读数的形状**
      两个数都要报：`调用 / 命中 / 不同 payload`（去重有没有真的发生）
      与 `缓存元素数`（代价落到内存上多少）。
      ⚠️ **只报「快了 N 倍」不够**：一个「从来没命中」的缓存与一个「全命中」的缓存，
      在**判据的结论**上长得一模一样。

### 4.11 ★ 出路 (3)「子 payload 从父派生」落地前要定的事

**先给结论**：盘上的三条派生机制**一律收窄**，数据装不下时**一律新建节点**。
「加宽已有节点的键」在盘上的文献里**没有前例**（出处与正文见 §2.4(h)）。

    Godin 1995     新节点 `(Y ∪ {x*}, Y' ∩ f*({x*}))` —— intent **交**；已有节点 `X'` 一栏是 `No change`
    ART 2013       `checkPrefix` 不符 ⇒ **新建节点**，前缀取公共前缀；老节点**有效键不变**
    空间分解        子区域 ⊆ 父区域 —— 这是**分解的定义**
    加宽的前例      GiST `AdjustKeys` / BRIN / X-tree —— 全部**自下而上加宽父**，不改「子比父细」

**要做的**（落地前必须先定）

    ① `payload(d)` 分成两半：`这一层自己声明的锚点` ∪ `从父继承来的锚点`
       —— 否则「加宽」会把 `B19` 的「有进步」一起抹掉（细化量恒为 0）
    ② `members ⊆ 覆盖` 的证明改走**归纳**：`覆盖(子) ⊇ 覆盖(父)` 沿路径传，
       链顶由出路 (1) 的**根记账**守住
    ③ `§I4` 签名 / `encode` / `decode` 复核 —— `payload` 从「一个集合」变成「一个有序对」

**依据**

    派生 = 收窄        Godin §3.1：`Y' ∩ f*({x*})`（§2.4(h)）
    已有节点不动       Godin Table 2 第 1 类：`X'` = `No change`
    唯一一次「并」      Godin Algorithm 1 第 8 行 —— 产出的节点 extent 是 `Ø`（**格底**）
    装不下就新建       ART 附录 A 第 15–18 行
    假阳是允许的       §K8（Barr 等 2015 的 Def 2.7，见 §2.5(f)）—— 所以加宽**不违反契约**

**不声称的**

    「加宽可行」**没有**文献支持 —— 本文只给「它撞的是 §7.7 而不是 §K8」这一条定位，
    以及「要落地就得把 payload 分两半」这一条形式。
    ⇒ **这是裁定，不是实现细节**：`§10.2 A′` 已把状态从「待落地」改成「**待裁定**」。

**必须配的检查**（落地时才写）

    ① `B19` 只算**自有**那半 ⇒ 注入「把继承那半也算进去」⇒ 必须红
    ② `B16` / `B1` 在两条路径上仍绿（继承那半不许把假阴带进来）
    ③ `B18` 覆盖不漏的 baseline **一个数不动**（出路 (3) 修的是健全性，不是它）

### 4.12 ★ 持久化的前提要**写进不变量**，而且要**说清是哪条边的入度**

见 §2.4(j)。两件事要落地，**顺序不能反**。

**第一件：把「树性」写进 §K5，并并进 `B13`**（不另开一条判据）

    理由：`§K5` 的 `max(rank(父))` 与「树」是**两个不同的形状**，
          而 `B13` 原来只查无环 —— **两者它都放行**。
          分开写会出现一个「无环但有多父」的中间态，而那个中间态**没有设计含义**。

    四条断言（对应 `§10.2 D` 的 P1–P4）：
        无自环 · 见证更粗 · 父链终止 · **非根方向恰好一个父**
        （末条含：`parent` 与 `_children` **互为转置**、`witness == (parent,)`）

    ⚠️ **注入必须改在「父 → 子」那条边上**（`_children`）。
       只改 `parent` 字段会让两条边**打架**（那是另一组断言），而入度本身没变 ⇒ 测不到树性。

**第二件：把「持久化层只认哪条边」写成规则**（`§10.2 D` 的 P6）

    `_children`（父 → 子）  = **权威边**
    `parent` / `witness`   = **派生索引**，落盘/读回时**从 `_children` 重算**，不独立存

    ⚠️ **这不是可选项**：`B13` 只保证**内存里**两条边不打架。
       一旦落盘时各存一份，两者就可能**漂移** —— 而漂移之后的症状正是
       「node-copying 悄悄按错了那条边」：检查还在、还绿，代价已经换了。

**第三件（留白，不是待办）：多父（DAG）的价格要写在留白旁边**

    `Direction.witness` 是**元组**、`ORIGIN_EMERGENT` 已声明、§I2 的 `合并({细})` 收**一组**
    ⇒ 合并涌现那条口子**还在**。启用它的价格：node-copying → fat node（O(1) → O(log m)），
      且 §K5 的 `max(rank(父))` 要**回改**。
    ⇒ 当前**没有买家**（§M2 情形④ 已落地为 `split`，不是 `merge`）⇒ 声明为树。

## §5 没有先例的部分

**这一节回答「哪些是我们自己的」。**

| 我们的东西 | 为什么没有先例 |
|---|---|
| **「层 = 方向」，且层由**使用记录**决定** | Godin 的格由**给定的二元关系**算出；ART / SP-GiST 的层由**数据分布**决定；HNSW 的层由**随机**决定。**没有一个是「由使用记录决定层」** |
| **不对称契约被写成「判据 + 度量」两条**（§K8 + §7.1） | GiST 有 `recheck`（契约），但**没有把它拆成一条判据和一条度量** |
| **「§K2 判空」作为一级度量** | ART 的 lazy expansion 是**同一条规则**，但 ART **不度量**它 |
| **「方向数 = 有子层 + 叶」（无空壳）写成检查** | ART「each inner node has at least two children」是同一条性质，但不是检查 |
| **「押错」与「实现 bug」的区分纪律**（§9.0） | 没找到把这两者写成**判据**的文献 |

⚠️ 但要说清**边界**：SP-GiST 是**换框架**（新 access method），不是「GiST 的一个新 opclass」。
   所以「框架层失败」这件事**确实发生过**，而且它发生时**恰好命中 §9.1 的两个症状**。

**而且有一条更强的证据：SP-GiST 自己的方法集，从论文到实现，长了一倍。**

    2001 年论文的接口（3 个方法，p.222）
        Consistent(Entry, Query Predicate, level) → Boolean
        PickSplit(P, level, splitnodes, splitpredicates) → Boolean
        Cluster()                                    ← 存储映射

    当前 PostgreSQL 实现的接口（5 个必需 + 2 个可选，官方文档 65.3.3）
        config · choose · inner_consistent · leaf_consistent · picksplit
        （可选：compress · options）

    差集：
        Consistent   →  inner_consistent + leaf_consistent    ← **拆成两个**（§9.1 症状②）
        —            →  config                                ← **新增**（§9.1 症状①）
        —            →  choose                                ← **新增**（把「导航」职责独立出来）
        Cluster      →  从接口**移出**，进内核

**最后一行尤其值得抄**：`Cluster` 从插件接口**移到内核**，理由是
「The SP-GiST core is responsible for **efficient disk mapping** and searching the tree
structure. It also takes care of **concurrency and logging** considerations.」（65.3.3）

⇒ **「每个方向都要、且每个方向都一样」的东西进内核；「每个方向不一样」的留在插件。**
   这与我们 §4.1 的内核 / 插件分界**是同一条原则**，而且他们是用「移出一个已有方法」来执行的。

⇒ 结论：**§9.1 的两个症状不是凭空定的 —— 它们在同一个框架的两代之间就响过。**
   但它们是**框架层**的症状。我们的三轮判定（三个方向都只写插件）**不受影响**。

## §6 未核（**不得作为依据**）

| 线索 | 为什么未核 | 与哪条需求相关 |
|---|---|---|
| R\*-tree（Beckmann 等, SIGMOD 1990）的 forced reinsert | 原文无开放副本，只见到二手描述 | N1 的**另一条**路：延迟分裂、先重插再分裂 |
| X-tree（Berchtold 等, VLDB 1996）的 supernode | 原文无开放副本 | N5 的**另一条**路：为避退化而**放弃二分** |
| Driscoll / Sarnak / Sleator / Tarjan 1989, *Making Data Structures Persistent* | 只见到二手的三策略描述（path copying / node copying / fat node） | §K4 + 持久化留白 |
| 机制设计（Myerson / Maskin）作为 §4.3「没有全局目标函数」的出处 | 未去拿正文 | §4.3 现在没有引用，读起来像偏好陈述 |
| ANN-Benchmarks（Aumüller / Bernhardsson / Faithfull） | 未去拿正文 | N10：跨设计的质量口径 |
| CRDT / join-semilattice（Shapiro 等） | 未去拿正文 | N3 的**另一条**路：靠 join 拿到顺序无关 |
| 抽象解释 / Galois 连接（Cousot） | 未去拿正文 | §K1–§K9 的上位框架 |
| Pugh 1990, skip list | 未核 | 结构泄露历史 |
| AddIntent, LNCS 2961 (2004) | 闭源，无开放副本 | Godin 的改进版 |
| Harinarayan / Rajaraman / Ullman 1996；Gupta, *Selection of Views to Materialize* | 未核 | §I3 / §I4 的权衡来源 |

**未核单列一节的收尾**：

> **文献支持我们要写的东西吗？** 支持 —— 而且支持得比预期强。
> `§K2` 的裁定（「不建这一层」）逐字对应 SP-GiST 的 `Leaf Shrink`；
> `§K8` 的不对称契约逐字对应 GiST 的 `recheck` 与 GIN 的三值；
> `§9.1` 的两个症状在 GiST → SP-GiST 的真实演进里**都响过**。
> **哪些部分没有前作？** 四件事：① 层由**使用记录**决定（别人的层由给定关系 / 数据分布 / 随机决定）；
> ② 把不对称契约拆成**判据 + 度量**两条；③ 把「层是否表达了下层表达不出的东西」当成**一级度量**；
> ④ 把「押错」与「实现 bug」的区分写成**判据**。
> **未核项里最该下一轮去拿的**是 R\*-tree 的 forced reinsert 与 X-tree 的 supernode ——
> 它们分别对应 N1（延迟分裂）与 N5（放弃二分避退化），是最贴的两个工程前例。
