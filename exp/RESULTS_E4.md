# RESULTS_E4 —— ldv 失效边界：三类材料（预注册 PREREG_E4 + V2–V6 增补）

> 判分 score.py v4 · deepseek-flash · N=3（每 run：84 段 = 24 truth 对〔类1/2/3 各 8〕+ 36 填充）
> 结果无论正负写第一节。本实验预注册的**预期方向被数据证伪**。

## §1 结果（先说结论）

| 臂 | 类1 无键矛盾 | 类2 方向反转 | 类3 同义改写 | 均值 |
|---|---|---|---|---|
| M-ldv（流式 remember→取回收尾） | **0.875**（1.0/0.75/0.875） | **1.000** | **1.000** | 0.958 |
| B-full（84 段一次在窗） | 0.583（0.50/0.50/0.75） | 1.000 | 0.917 | 0.833 |

### 预注册条件判定

- **E4-F1（"三类全 ≥0.9 ⇒ 未能找到失效边界"）：未触发但逼近**——类 1 = 0.875，
  距 0.9 差 0.025。实质处于规范所称的"可疑信号区"边缘。
- **E4-F2（键取回失效：类 1/3 上 ldv 低 ≥0.15）：不成立且方向相反**——
  类 1 上 M-ldv **高出** B-full 0.29，类 3 高 0.08。预注册的失效方向没有出现。
- **E4-F3（信念覆盖吞矛盾）：不成立**——类 2 两臂均 1.000。
- **E4-F4（B-full 类 1 < 0.6 ⇒ 该类结论无效）：触发**（0.583）——类 1 的组间
  差异解释力受限：裸 agent 在无键材料上本身就接近做不动。

### 结论一句话

**"画出 ldv 会输的地方"失败了：三类材料上 ldv 组全部 ≥ 裸组，类 1 反而 +0.29。**
结合 E3，三组实验拼出统一图景：

> **ldv 的全部优势来自"整理"，不来自"存储与取回机制"。**
> E1：R-L ≈ 规则被预先整理；E3：整理成 CSV 直给即可复现（0.972）；
> E4：逐段 remember = 强制分段整理，其产物（84 条清洗后的短要点表）
> 比 84 条原始长句更易比对——M-ldv 赢的是整理，不是记忆机制。

### 机制解释（备择假设，如实标注）

M-ldv 的 remember 阶段是 84 次独立的小型 LLM 调用（每段一次，单独提取要点），
天然"分而治之"；收尾取回的是要点表而非原始长句。B-full 一次吞 84 条原始句，
注意力稀释。**但这解释同时暴露设计缺口**：若裸 agent 也"先逐段整理再比对"
（不用 ldv），大概率同样好——E3 的 CSV 臂就是静态版证据。M-ldv 的
~7 分钟（84 次调用）对 B-full 的 1.5 秒，**成本差 280 倍**，换来的
0.125 类 1 优势是否值当，是经济问题不是能力问题。

### 一次被放弃的"幸运误读"（诚实记录）

r1 试点（V3 之前）M-ldv 曾得 0.375/0.25/0.375，与终局 0.875/1.0/1.0 同代码
不同结果——终局三次 rem=84/84 的 run 方差仍大（类 1 0.75–1.0）。
N=3 的均值在此噪声下解释力有限，"类 1 +0.29"以**方向**而非精确值采信。

## §2 harness 战役记录（V2–V6，全部先于计入数据）

E4 的执行被同一个底层 bug 反复击穿，最终根因修复在 **ldv-mcp 内核**：

1. V2：收尾指令模糊 → 模型不取回直接交空卷（harness 措辞，已修）。
2. V3：ask 全量返回 2.1 万字被 [:5000] 截断 → 放宽 [:30000]。
3. V4：client reader 线程被解码异常杀死（Popen errors="replace"）。
4. V5：server 长跑随机停止回传响应 → 单次调用隔离（每 call 前重启 server）。
5. **V6（真正根因，内核修复）**：`server.py::_send` 用 `ensure_ascii=False` 写
   stdout——Windows 管道下 server 进程 stdout 默认 locale 编码（GBK），
   响应含 GBK 外字符（如 ⇒，LLM 生成的要点爱用箭头符号）即
   `UnicodeEncodeError`——单响应丢失且异常传播杀死 main 循环。
   **表象是"server 僵住、一切调用超时"；E1/E2 的"server 中途死"（OSError 22
   管道断裂）与此同根**。修复：协议输出纯 ASCII（ensure_ascii=True），
   client 侧 `_send` 同步修复。修复后 rem 84/84 稳定复现。

**这条修复对 ldv 产品本身是实质贡献**：内核 v0.1.47 的 MCP stdio 通道在
Windows（GBK locale）下对含特殊符号的内容不稳定，E1–E4 全部实验都受其
间歇性影响。
