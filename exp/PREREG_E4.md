# PREREG_E4 —— ldv 失效边界：三类材料（规范 §7，P1）

> 预注册纪律：本文件写于 E4 任何数据之前。脚本冻结 sha256 见 §5，跑完只许追加 RESULTS 节。
> 判分沿用 exp/score.py v4（确定性、无 LLM 裁判）。

## 1. 目的

规范原文："画出 ldv 会输的地方，否则会被质疑'自己出题自己答'。"
E3 之后本实验多一层意义：E1/E3 的材料全部是**强键**（标题精确一致），
ldv 的取回从未被弱键/无键材料考验过。E4 专测键失效。

## 2. 三类材料（规范 §7.1 原文）

| 类 | 定义 | ldv 预期失效机制 |
|---|---|---|
| 1 非结构化矛盾 | 两段话语义打架，**无任何键可对齐** | remember 建不出可 ask 的键 → 取回失败 |
| 2 跨实体矛盾 | A 说 X→Y，B 说 Y→X（方向反转） | 键对齐但语义反向 → 信念覆盖/归并吞掉矛盾 |
| 3 同义改写重复 | 同一事实换说法，entity/year 键对不上 | 精确键匹配把同一事实存成两个实体 → 重复检测失败 |

**类 3 等价判定**：按 DESIGN_V2 T8，改写必须词面不同、语义等价，
判等价的**人工表逐条预注册**——全部改写对的原文在材料构造脚本中
写死（`e4.py` 顶部 `CLASS3_PAIRS` 字面量），PREREG 冻结脚本即冻结等价表。

## 3. 设计

- **两臂**：M-ldv（流式：材料逐段给出，每段 agent 先 remember（内容自定），
  最后收尾指令"从你的结构找出所有矛盾/重复对，输出 JSON"）；
  B-full（裸：全部段落 + 同一收尾指令一次在窗，无工具）。
- 材料：每任务 = 24 个 truth 对（每类 8 对）+ 36 段无关填充，共 60 段〔S01…S60〕。
  所有句子由 `e4.py` 构造器从固定模板+seed 生成，seed=run 号。
- 收尾指令（两臂完全一致）：
  "以下是若干编号陈述。请找出所有【互相矛盾的陈述对】或【描述同一事实的陈述对】，
  输出 JSON {"pairs":[{"ids":["Sxx","Syy"], "kind":"矛盾|重复"}]}。"
- 判分：对每类分别报 recall/precision（truth 对带类别标签）；复用 score.py
  的配对逻辑（两 id 都对才算命中）。kind 不参与判分（宽容口径），
  另行统计 kind 正确率作参考。
- N=3 runs（seed=1,2,3），每 run 1 任务（60 段内 24 对，规模已足够检验）。

## 4. 证伪条件（先写死）

**E4-F1（规范原文）**：若 ldv 组三类 recall 全部 ≥ 0.9
⇒ 如实写"**未能找到 ldv 的失效边界**"——这是可疑信号，不是好成绩；
同时追问材料是否构造得太容易。

**E4-F2（预期假设）**：类 1 与类 3 上 ldv 组 recall 比 B-full 低 ≥ 0.15
⇒ "**键取回失效**"成立：ldv 的 remember/ask 协议依赖显式键，
无键与改写键材料上输给全窗裸 agent。

**E4-F3（类 2 专属）**：检查 ldv 组结构终态——若矛盾对中至少一方的值
在 remember 链中被后续陈述覆盖（结构中已查不到），且该对 recall 显著低于 B-full
⇒ "**信念覆盖吞矛盾**"成立（E2 的 B-full 陷阱 Q4 在写入侧的镜像）。

**E4-F4**：若 B-full 在任一类上 recall < 0.6 ⇒ 该类的"ldv 失效"结论无效
（裸 agent 也做不好，说明是任务太难而不是键机制问题），改述为"两类都不能"。

## 5. 冻结

- 实验脚本：exp/e4.py（构造器 + 两臂执行器 + 判分，seed 参数化）
- 脚本 sha256 在首次试点运行前记录于 RESULTS_E4 §0
- 落盘：exp/runs/E4-<ts>.jsonl，字段含每段 remember 的键与取回轨迹

## 6. 不许做的事

- 不许因 ldv 组分低而修改 remember 协议重跑（协议即被测对象）。
- 不许把 kind 判错算不命中之外再罚分（口径只用 recall/precision）。
- 结果无论正负写 RESULTS_E4 第一节。

## V2 增补（写于收尾指令修正之前、M-ldv 试点空卷之后）

M-ldv 试点显示：remember 84/84 成功写入，但收尾阶段模型在看到 orient 目录后
**不调用 ask 直接输出 {"pairs":[]}**（tool_rounds=0）。这是收尾指令模糊
（E1 R-L 明确给出 ask require 用法，E4 初版只说"用工具取回"）造成的
harness 问题，不是键失效证据。修正：收尾 system 提示改为 E1 同款明确指引
（告知 ask/require/with_body 可用）。此修正先于任何 M-ldv 计入数据。
B-full 试点数据不受影响（无工具）。

## V3 增补（harness 容量修正，先于任何 M-ldv 计入数据）

第二次试点发现：ask 全量返回 84 条 ≈ 2.1 万字，被工具返回截断 [:5000]
削到 ~20 条，模型 6 轮内拿不全（每轮重复同样截断）而放弃交空卷——
这是 harness 窗口容量参数问题，不是键失效。修正：工具返回截断
5000 → 30000 字。V2（收尾指令明确化）与 V3 均不改变协议本体
（remember 全部 → orient+ask ≤6 轮 → pairs）。

## V4 增补（E4 卡死根因与 harness 修复，先于 M-ldv r2/r3 重跑）

- 根因确诊：client reader 线程被 server 输出中的 GBK 字节（0xd3…）的
  UnicodeDecodeError 杀死 ⇒ 一切调用超时（"server 僵住"的真相）。
  r2/r3 M-ldv 因 reader 死亡 rem 不全 + 空卷，该两条数据作废（B-full 不受影响）。
- 修复：Popen 加 errors="replace"；reader 线程兜底不死（死亡时投递 _reader_dead 标记）。
- 此修复属 harness 鲁棒性，不改变协议本体；r1 M-ldv（84/84 健康）保留。

## V5 增补（单次调用隔离，先于 M-ldv r2/r3 第二次重跑）

V4 修复后重跑仍复现"客户端超时但 server 实际写入成功"（e4-r2/r3-210926x
nodes 各 84 个 = remember 全部落盘，client 却报 35/84、84/84 超时）——
server 长跑会**随机停止回传响应**（写入不受影响），重启是唯一恢复手段。
V4 的"超时后重启"在批量 remember 场景恢复不彻底。改为**单次调用隔离**：
每次 sess.call 前强制 recycle（重启 server + 握手 ~0.5s，84 次约多 1 分钟）。
协议本体不变。r1 M-ldv、B-full 三条维持保留。
