# 实验四（附录）：成本曲线 —— token 消耗 vs 材料量

作用不是证明 C 强，是**堵住"你是用更多算力换性能"的质疑**。数据全部来自实验一/二/三的
usage 落盘与 C 组本地计时（无新增 API 调用，除一个 4,017 节点的本地测量点）。

---

## 1 A 组：每个问题都要重新付全款（线性，且每轮对话重付）

| 材料规模 | A 单题输入 | 冷成本※ | 热成本※※ | 来源 |
|---|---|---|---|---|
| 8.2k tok | 8,247 | ¥0.009 | ¥0.009 | 实验二 0% |
| 21k tok | 21,360 | ¥0.024 | ¥0.024 | 实验二 60% |
| 97k tok | 96,930 | **¥0.10** | ¥0.003 | 实验一 |
| 117k tok | 117,345 | ¥0.12 | ¥0.003 | 实验三 |
| **359k tok** | 358,681 | **¥0.36** | ¥0.008 | 实验三（合成干草堆） |

※ 冷：全部输入按 ¥1/M。※※ 热：前缀缓存命中部分按 ¥0.02/M——**只对逐字相同的前缀生效**；
新问题/新文档 = 重新冷。计价：输入 ¥1/M（空闲时段）、输出 ¥4/M。

三条要写进文章的性质：

1. **线性**：冷成本 ≈ 0.000001 × token 数，没有惊喜——这意味着 O(n) 是结构性的，不是实现浪费。
2. **每轮重付**：多轮会话每 turn 重放全史。实验三的 85 条消息会话，40 个灌水轮合计 ≈6.5M 输入
   （缓存命中价 ≈¥0.13，**冷口径 ≈¥6.5**）。对话越长，单位问题成本越接近"每次都全文重读"。
3. **时间也是钱**：359k 档单次三问 227–300 秒。A 不是贵，是**慢且贵**。

## 2 C 组：一次建库，之后每题 0 token / 10ms

| 节点数 | 写盘+建库 | 装载 | 每次查询 | token |
|---|---|---|---|---|
| 250 | 0.7s（含建库） | — | ~1ms | 0 |
| 2,500 | — | 17.5s（含装载） | ~1ms | 0 |
| 4,017 | 2.6s | 25.2s | **0.010s** | 0 |

- 建库+装载 ≈ **7ms/节点，一次付清**（本地 CPU，无 API）；
- 之后每题 0 token、毫秒级——**问题数越多，摊销越接近零**；
- 装载也随 n 涨（25s @ 4k）⇒ C 不是"无成本"，是**成本在前端且可摊销**。长驻服务一次装载
  后就是常量；每次冷起进程则要重付——服务层 P1 的租户 `AppCache` 正是为此。

## 3 交叉点（写文章用的一句话）

> 在 10 万 token 材料上：A 每问 **¥0.10 + 10 秒**（对话里每轮重付），
> C 一次 **28 秒建库** 后每问 **0 元 + 10ms**。
> **问 100 个问题 = A ¥10+17 分钟 vs C ¥0 + 1 分钟** —— 差距随问题数线性拉大，
> 随材料量线性拉大，且 A 的问题数成本无法摊销。

## 4 没说的不说

- 热缓存是真实存在的工程手段：同一份材料反复问答时 A 的实际成本可以低 30–50 倍——
  **但每个新问题仍要付增量，且"新问题"恰恰是 agent 的常态**。
- C 的建库成本在**人侧**（声明维度、写 sidecar）：那 7ms/节点不含"谁来决定 year 是个维度"。
  这是本仓库反复声明的人工税，不隐藏。
- 全部四实验 API 总花费 ≈ **¥3.8**（58 + 12 + 8+8 + 若干次调用）。
